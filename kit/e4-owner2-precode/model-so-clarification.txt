Preserve every other field, including unknown fields and nested metadata. An unchanged unknown additive field need not be rejected merely for being unknown: the existing spread/clone and whole-record comparison retain it. But any addition, removal or change relative to the prepared snapshot must remain distinguishable and refuse as a conflict. Do not compare a whitelist, strip unknown fields, or ignore output/data/metadata differences.

The bounded implementation remains:

1. Read and locate the raw selected target inside the existing transaction.
2. Apply existing deleted/team/output safeguards and the selected-row stamp/metadata refusal described above.
3. Normalize that selected row transiently with the existing read helper.
4. Compare its complete value against wanted, then expected.
5. Retain the raw list and replace only the selected row when the comparison permits it.

This guard must precede the idempotent-success comparison too. Otherwise an unsupported target could be falsely acknowledged as already installed. Refusals must leave stored bytes untouched; successful installation must preserve unrelated rows’ raw field representations.
