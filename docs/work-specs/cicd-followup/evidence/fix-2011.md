# Fix #2011: a manual-only workflow is not a run per landing

Scoped fix in the cicd-followup plan run (run issue #1967), outside its numbered phases.

## The defect

`cadence()` in `scripts/growth-controls.mjs` gave any trigger it does not know at least one run per
landing. A workflow whose only trigger is `workflow_dispatch` was therefore priced as running on
every landing: 6 runner-minutes per landing in the overhead tier for each new job. That refused
PR #2005 (adds `.github/workflows/jev-svg-eval.yml`, manual and main-only) on CI runs 41595861313
and 41602018224, and mispriced cf01's `alarm-test.yml` the same way.

## The change

- `cadence(shape, e, { dispatched })`: a workflow whose only trigger is `workflow_dispatch` costs
  0 runs per landing, unless `dispatched` says a per-landing workflow starts it. Every other
  trigger keeps its price. Not knowing counts as dispatched, so a caller that passes no repository
  view still gets the old, higher price.
- `landingDispatched({ workflows, read }, e)`: the workflow files a per-landing workflow starts.
  From each per-landing workflow it follows what the steps run: repository files named by path
  and the files those name or import (outside `src/`, `e2e/`, `api/`, `docs/`, `public/`,
  `supabase/`, `contracts/`), `npm run <name>` through package.json, and local actions
  (`uses: ./.github/actions/...`). A text that makes a dispatch call (`gh workflow run`, also as
  `gh` with an argument array `['workflow', 'run', ...]`, `createWorkflowDispatch`, a `.../dispatches` API path, or a reusable-workflow
  `uses: ./.github/workflows/...`) starts each workflow named in it, in a file that imports it
  directly, or on a command line that leads down to it at any depth (a script handed the workflow
  as an argument). A file name counts anywhere in those texts; a display `name:` counts only
  right after `gh workflow run`. Comment lines are skipped. It repeats until nothing new is found,
  so a workflow that a landing starts can start another. Past 2000 files for one workflow it
  stops and counts every workflow as started.
- `priceAdditions` takes `repo: { base, head }` and works this out on both sides. A manual
  workflow the change does not touch, which a landing starts after the change and did not before,
  is priced as well (a change to ci.yml or a script alone is enough).
- `scripts/e2e-capacity.mjs` gets `repoView(base, root)`: the base workflows and files from git,
  the head ones from disk, passed to `priceAdditions`. This wiring is outside `cadence()` itself,
  but the fix needs it: `cadence()` sees one workflow, and whether something else dispatches it is
  only visible from the rest of the repository. The base side is searched only when its answer can
  change a price (a manual-only workflow is priced, or a landing starts one at the head), so the
  capacity step still takes about 1 s locally.

No ceiling, estimate, budget, exception or ledger value changed. `growth-ceilings.json` is
untouched.

## What it can and cannot see

Sees: dispatches written in a per-landing workflow's steps, or in a repository script that the
workflow runs (by a `scripts/...` path) or that such a script imports by a relative path.

Sees: the routes listed above.

Does not see: a dispatch from outside the repository (a person, an agent session such as
`/queue-merge` starting `cloud-queue-merge.yml`, another repository), a dispatch by numeric
workflow id or by a name built at run time, a script reached by a path that is not written out,
and a name that only a distant importer (not the direct one) passes in. When a session or such a
route dispatches per landing, the weekly growth report still measures those runs, as it does for
every other run.

It errs toward pricing where it can: a dispatching text that only mentions a file still counts
as starting it. On current `main` it marks `ci.yml`, `configured-suite.yml`, `nightly.yml` and
`quarantine.yml` as started. Each already has its own per-landing or scheduled trigger, so its
price does not change.

Why this is a correction and not a looser limit: the old rule charged one run per landing for a
trigger that, on its own, never fires on a landing. The new rule keeps that charge whenever the
repository shows a per-landing route to the workflow, and fails closed when the search is cut
short. No ceiling, estimate or budget moved.

## Evidence

Tests (`node --test scripts/growth-controls.test.mjs scripts/e2e-capacity.test.mjs`, all pass).
New case `(b) a manual-only workflow costs no run per landing unless a per-landing workflow
starts it`:

- a dispatch-only workflow that nothing starts: no item (0 per landing);
- a `gh workflow run` in a comment, or in a scheduled (not per-landing) workflow: still 0;
- started by a `gh workflow run <file>` step, by `gh workflow run "<name>"`, by a script that a
  per-landing step runs and that imports a `.../dispatches` caller, or through a chain of two
  workflows: one run per landing (6 runner-minutes);
- an existing manual workflow that the change makes ci.yml start: priced as new runs;
- a manual workflow that also has `workflow_call`: keeps its price.

New case `(b) the dispatch search follows what a landing runs and names only what it starts`
(from the review of the first cut): a common display name such as `test` in an unrelated step,
or a distant importer that mentions the file, does not count; an `npm run` script, a local
action, a script run by a script, an argument handed down through a command line and an import,
and a title with a trailing comment all count; past the file limit everything counts; and an
untouched manual workflow that a change to ci.yml makes a landing start is priced.

New case in `scripts/e2e-capacity.test.mjs`: `repoView` on a real temporary git repository
reads the base from git and the head from disk, and a script change that starts an existing
manual workflow is priced at one run per landing.

The existing cases are unchanged, including `a job on an unpriced trigger is never free`, where
a dispatch-only workflow priced with no repository view stays at one run per landing.

change to ci.yml or a script, went unpriced; that a common display name matched anywhere; and
that `npm run`, local actions, script-to-script calls and arguments passed down were not
followed. All are fixed and tested above. Simplify then removed duplicate null handling and a
second regex-escape, cached each file's edges, and made the base-side search lazy.

price `alarm-test.yml` again (scripts/alarm-owner.mjs names it in an issue body) and
`jev-svg-eval.yml` (PR #2005's own scripts/jev-svg-eval.mjs names it), which is the defect this
fixes. Not taken: one `git cat-file --batch` process for base reads, since the lazy base side
already keeps the step at about 1 s.
