# V5 evidence for the vMix clip clock and reload

Previous verified main is `1b7e067c537d567e119c5f886b22f521b2a80503` (#2378). V5 covers AC-11 and the V5 Windows Bridge release in AC-6. Trim, fades, levels, clip sequences and operator-device verification belong to later phases.

## Rules

- A paired production using vMix and a Bridge advertising vMix media reads one vMix player snapshot at a time. It applies the snapshot only to the players its current cues or live state use. It keeps the existing hot and idle cadence, wakes after a player action or when the page becomes visible, and performs reads without sending any mixer, overlay or output command. CasparCG keeps its channel readings.
- A read belongs to the same live production, playout system and pairing from request to fold. A production switch, unmount or delivered pairing change retires pending reads even if the old credentials later return. Before applying the answer, read the current rundown and confirm the current player binding. A deleted, reassigned or mismatched cue cannot regain authority.
- vMix Take writes the production and cue identity into the existing opaque cue field the Bridge echoes. Copies can retain a cue ID, and two cues can name the same file. Recovery requires a Bridge instance from the reported session, the exact production and cue, a current vMix media item on that player, and the item's relative file identity. A legacy unscoped Take cannot be adopted on reload or by another production. The old page that accepted it can keep its in-memory ownership under the existing rules. CasparCG cue IDs keep their current format.
- The paired player reply must have valid HTTP and protocol fields, one well-formed row for each player, a Bridge session and observation time, and internally consistent generation, playback and identity fields. Missing, duplicate, malformed or contradictory evidence makes no change. For the same session ignore a player generation below the last accepted action or previous admitted observation and ignore backwards observations. A new Bridge session can start its counter over, and its readings cannot confirm the retired process's instance.
- A clip matching its known or recovered instance is on air on that player. Its clock reads the Bridge's position, duration, pause and loop. Changes in time alone do not change ownership. A valid empty reading clears the player row. A held file that no current cue owns is never inferred from its filename. When it supplants a known cue in the same session, the old row says `replaced` and loses transport authority. A Bridge restart cannot attest to the earlier instance.
- An action in flight excludes observations of its player while it settles. An observation begun before that action, or while it was pending, cannot later restore ownership after an unknown outcome. Clear uncertain ownership and require a newly issued, valid observation or another accepted action. A stale success cannot supersede later admitted evidence. The two players keep separate authority, and the ordinary same-player command serialization and pairing checks still apply at send and fold.
- Out, Pause and Resume by an owned vMix cue act only on the exact instance still held by the mixer in the Bridge's serialized turn. This applies equally to an accepted Take and to a recovered row. Reuse the existing guarded Out and add explicit guarded wire verbs for Pause and Resume, rejected by older Bridges instead of silently dropping the instance. An older Bridge can be read for timing, and its supported guarded Out remains available. Legacy command names remain available for existing callers. A player reading on its own sends no action.
- Bridge `0.12.0` is the next media release after both main and the published `0.11.0`. The current independent `bridgeVersion` and `release-bridge.yml` replace earlier recipes that coupled Bridge and CLI bumps. V5 adds operator notes and incremental Bridge documentation. The exact merge's automatic Windows release and download are independent acceptance checks.

## Baseline reproduction

On Windows at the starting SHA, a focused Node harness started the real production Bridge watch with a fake paired Bridge. The current rundown had one vMix movie cue. The Bridge advertised vMix media and was ready to return a valid playing clip at position three of ten seconds. After status and an explicit wake, the watch made zero player reads and ownership and timing were empty. The assertion that an eligible vMix cue player is read failed. No vMix device was used.
