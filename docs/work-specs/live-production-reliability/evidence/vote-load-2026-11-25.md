# A room of 100 and 200 phones voting on staging, 2026-11-25

P1 AC-4 ("the cap is sized for the largest room a production expects, measured") and the AC-6 counts,
for a live production with about 100 phones the week after.

## How it ran

- **Staging only**, through `.github/workflows/hosted-latency.yml` with `spec=e2e/instruments/vote-load.ts`
  on branch `noacg/nice-wozniak-hp8gzj`, shard 1 (the other shards skip, so one room loads the
  database at a time). Production was not read or written.
- **Phones**: `scripts/vote-load.mjs`, one Node process on a GitHub runner. Each phone has its own
  device token and sends what `src/audience/audienceData.ts` sends: `audience_join_by_slug` every
  5 s with 10% jitter either way, `audience_vote` with the round and revision it last read, a re-read
  after every send, the publishable key only. A tenth of the room arrives during each run, a fifth
  changes its vote 2 to 6 s after voting, everyone else votes within 5 s of seeing the question. A
  phone that sees "Not sent" or "Too many votes at once" presses Vote again, twice at most.
- **Operator**: the real Interaction tab on a published staging production of a throwaway account,
  pressing Go live, Stop, Continue the count and Start a new count.
- **The six readings compared after each Stop**: the script's own count (each phone's last vote the
  server answered 200 to), the panel's counts, `audience_tally`, `audience_votes_export`, the CSV
  the panel downloads, and the result cue's values after Add results to rundown. Each phone's
  "Your vote" read-back is compared with what it sent.
- **Host**: the staging database's privileged metrics endpoint, every 5 s (CPU, disk, memory, load,
  connections). Staging is the free tier: 434 MiB of memory, shared CPU.

## Counts: every vote counted exactly once

| Room | Run | Votes | Script = panel = tally = export = CSV = result cue | Phones reading back another vote | Refused or not sent |
| --- | --- | --- | --- | --- | --- |
| 100 | First count | 100 | yes, all three runs (run 1 and run 3) | 0 | 0 |
| 100 | Continue the count | 110 | yes | 0 | 0 |
| 100 | Start a new count | 120 | yes; the earlier count stayed 110 | 0 | 0 |
| 200 | First count | 200 | yes (run 3) | 0 | 0 |
| 200 | Continue the count | 220 | yes | 0 | 0 |
| 200 | Start a new count | 240 | yes; the earlier count stayed 220 | 0 | 0 |

Votes are per question: Continue the count added the late phones and kept the changed votes as
changes; Start a new count started from zero and every phone voted again. The export had one voter
key per counted phone in every run. No phone needed a second press in any run.

## Response times

Run 3 (`45685469647`), measured from the runner, per run from Go live to Stop:

| Room | Run | Votes: median / p95 / slowest | Join reads: median / p95 / slowest |
| --- | --- | --- | --- |
| 100 | First count | 187 / 479 / 579 ms | 184 / 472 / 556 ms |
| 100 | Continue | 210 / 603 / 703 ms | 215 / 553 / 990 ms |
| 100 | New count | 192 / 490 / 1049 ms | 189 / 275 / 586 ms |
| 200 | First count | 192 / 250 / 585 ms | 185 / 227 / 632 ms |
| 200 | Continue | 183 / 220 / 322 ms | 183 / 218 / 570 ms |
| 200 | New count | 188 / 229 / 524 ms | 189 / 7885 / 12003 ms |

The one slow stretch in run 3 came after the 200 phones had voted: the instrument's own check makes
every phone read once more inside two seconds (about 140 requests a second with the polls). Join
reads then queued for up to 12 s for about ten seconds, and so did the operator page's reads
(`audience_tally` up to 9.9 s, `audience_list` up to 10 s). Votes in the same run stayed under
0.6 s. The database host was not busy: about 10% CPU and 12% disk over the whole run, load under
0.4, 19 connections, memory 339 of 434 MiB. So requests waited in front of the database (the API
gateway or the REST server's connection pool on the free tier), not in it.

Run 1 (`45680478315`, 100 phones) was slower throughout with the same counts: votes median 132 ms
but p95 13 s, in the Continue run median 24 s and slowest 28.8 s; one join read failed with
"canceling statement due to statement timeout" (HTTP 500; a vote failing that way shows "Not sent"
and the phone presses again). The host's load average reached 3.95 then, against 0.04 in run 3 at
the same size; nothing in the vote path explains it, and runs 3 and 4 did not repeat it.

## What it means for about 100 phones

- Counting is right: across 1,000+ counted votes in seven runs, every vote a phone was told went in
  was counted once, and all six readings agreed every time.
- The burst cap (3000 phone votes per question in 10 s) is far above this room: 200 phones sent at
  most 240 votes in a run and none was refused.
- The risk is time, not loss: on a slow backend a vote can take seconds to come back, and the phone
  greys its Vote button meanwhile with nothing said. The vote is still counted when it lands.
