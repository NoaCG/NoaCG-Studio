These are not launch blockers. They should go into ci01/ci18 acceptance.
1. Timing ceilings will rarely trigger as written. The rules need 12 comparable completed phases per category, stratified three ways, within a 28-day window. A serial run of 18 phases over 6 to 8 weeks will almost never reach that, so the percentile rule stays “provisional” for good.
   - Make per-item age ceilings the enforced control: an unfinished PR or phase older than its ceiling is actionable now.
   - Pool the categories for the sustained-breach rule, and keep categories for reporting only.
2. The aggregate cost gate can be dropped as a separate per-PR gate.
   - Make build, factory and tooling a fixed-overhead tier.
   - Require all tier ceilings to sum within the envelope at calibration.
   - The aggregate then becomes a calibration check plus a weekly report line, one less moving part.
3. Slowdown of unedited tests should be detected after landing, not refused per PR. Single-run durations near 95% would flip PRs between pass and refuse. The existing e2e-capacity.mjs header already says it cannot see this drift before merge.
   - Detect it on post-landing and weekly evidence and attribute it to a landing range.
   - Then refuse additive growth on the next PRs.
   - Reword AC-9’s “executable gates demonstrate ... indirect slowdown” to match.
4. The resource envelope figure is inconsistent. e2e-capacity.mjs budgets 13 runners out of the account’s twenty concurrent runners. The spec says a 60-job envelope that was not remeasured. ci01 must measure the actual concurrency limit and freeze it. Moving from 20 to 60 must not quietly triple any ceiling.
5. The weekly refresh is already drifting. Bot PR #1503 (“Re-record the E2E shard durations”) has been open since 2026-10-19, and e2e-durations.json was last updated that day. ci01 should record this, and ci18 should alarm when the durations table is too old.
6. Close two gaps:
   - Forbid renewing a budget exception for the same scope without a repayment receipt.
   - Define the PR-ready clock’s start as an observable event, for example the first worker receipt reporting all gates green, or else the first stamp.
7. ci03 is narrower than described. Configured-suite checkout already uses github.sha, which is fixed when the dispatch happens. The real gaps are:
   - the dispatch call returns no run ID, so a run can’t be matched to its request;
   - schedules and main dispatches share one concurrency group;
   - a newer dispatch on the same branch replaces one that is still pending.
