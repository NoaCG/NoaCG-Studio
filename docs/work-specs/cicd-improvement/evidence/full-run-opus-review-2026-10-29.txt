LAUNCH-BLOCKING FINDINGS

1. If the deadline passes, the run restarts from phase 1.
   Where: runbook "Waits" bullet 1 says a selection correction resets the 14-day window "even if this crosses the authorized deadline. No automatic deadline extension."
   Why it breaks: the deadline is fixed inside the project (immutableProject, validateAuthorization). run-recovery.mjs:299 activeProject skips any project past its deadline, so `continue` answers `open`. A new project starts a fresh ledger at phase 1 and loses every PASS and failure count.
   Scenario: row 12 corrects a mapping on day 20 of a 28-day authorization. The window cannot close in time, and every pass on the record is stranded.
   Fix: size the deadline to the real critical path plus at least one reset (suggest 6-8 weeks). Write the expiry rule into the runbook now: stop and report. Any continuation is a new owner authorization whose project lists only the rows not yet passed and cites the old project's PASS receipts. That conflicts with plan-run's "copy exact phases", so state the exception explicitly.

2. Row 13's "accept the evidence before narrowing" step has nothing enforcing it.
   Where: runbook row-13 paragraph, "Before row 13 lands any narrowing, a fresh reviewer must accept...".
   Why it breaks: the runner only knows build, land, then an independent check after landing (plan-run.mjs 300-340). The pre-landing review is a step inside the builder's own work, with no ledger event. If it is skipped, narrowing is live on main before anyone has accepted the qualification evidence.
   Fix: split row 13.
   - 13a: evidence only. It closes the audit and judges the row 8/9 receipts. Its independent PASS is the gate.
   - 13b: activation only, one revertible change.
   This also keeps rollback clean: reverting 13b cannot undo the integrity or hardening fixes.

3. "Selection correction" is undefined, and the serial order wastes the 14-day window.
   Ambiguity: rows 7 and 10-12 each "restart the clean window". Any product PR that adds a spec header changes selection. If that counts, the window can be reset indefinitely, or argued away.
   Define it: a reset is any landed change to selector code, header/list semantics, the critical/shared sets, or a mapping changed in response to a miss. New spec headers in ordinary PRs do not reset the window; the audit covers them.
   Waiting problem: the window starts at the last correction, today row 12. Rows 13, 14 and 15 then sit behind roughly two idle weeks. Rows 8 and 9 need several days of real schedule runs and change no selection, yet they run before the window opens instead of inside it. See the phase order below.

4. The final row can only pass or stop, and AC-7 can never be closed.
   Where: runbook row 15; work.json.
   What I found: I ran `work-spec scope` read-only. Scope mode only validates the IDs. Completion still requires a review entry for every AC, so AC-7 keeps the record "open" forever. Nothing can mechanically show that AC-1..6 and AC-8 are complete. Also, if the ten risky rows or the cohort targets never arrive, row 15 can only fail and then stop.
   Fix:
   - Move AC-7's text out of the ### AC-n headings into the Optional follow-ups section. The record then holds exactly the initial criteria, and converge can honestly reach evidence-complete.
   - Make row 15's acceptance an independent verdict per AC: met, not met, or pending with a reason.
   - Row 15 PASS then means "the hand-off report is correct", not "the targets were met". Claim initial success only when converge is evidence-complete.

5. There is no plan for keeping the coordinator going between work blocks over several weeks.
   Where: runbook "Coordinator/worker permissions...", "Qualify wake/continuation before relying on it".
   Why it matters: each block lasts at most 24 hours. The preparation runbook says nothing wakes a stopped coordinator except a plan's own check-in. Production-page section 9 names one cloud coordinator session, an hourly send_later check-in with a live receipt, and a preflight checklist. This plan names none of these, so every block end (roughly 30 or more over the run) needs the owner to type the line again.
   Fix:
   - Adopt production-page section 9's coordinator home, check-in and preflight list by reference, and re-prove the check-in live for this project at launch.
   - For waits with a known date (the window's end, nightly receipts), save the run state and pause with a dated owner resume instead of 14 days of hourly check-ins.
   - Usage limits and closed sessions already stop the check-in, so state that owner resumes are the fallback.

6. Exact acceptance lists are not written down, and work.json is a draft.
   Acceptance lists: each runbook row mixes acceptance and environment in prose. Whoever launches derives the acceptance[] and environment strings, and that decides what every PASS needs. Write the phases array into the runbook now, without any authorization data.
   Draft record: `work-spec scope` returns invalid ("scope is not backed by agreed intent"). Add "set authority.status to agreed, citing the owner's source" to the launch admission list.

ROW-LEVEL CORRECTIONS (make before launch; not launch-blocking)

C1. The selected backend check (row 5) is not complete enough yet.
   - 15 of the 73 configured spec files have no `covers:` header (for example account, analytics, audience-live, homebase, bridge-real-server), so a header-based selection can never pick them. Offline specs are refused without covers; configured specs have no such rule.
   - The planner returns only a yes/no `configured` flag (e2e-affected.mjs 563-579), not a list of specs.
   - `.github/` is ignored by the planner (e2e-affected.mjs:285), so a change to configured-suite.yml or the shared setup selects nothing.
   Fix in row 5: require covers or `none - why` on every configured spec. A change to e2e/configured/** helpers, playwright.live.config.ts, the setup code or the workflow runs the full configured set. The CI gate reads the plan's flag rather than trusting a skipped job.

C2. Quarantine can quietly take tests out of the critical set.
   In merge groups, the ci.yml gate turns a fail-then-pass into success, and after-gate writes the spec into quarantine.json, which removes it from the blocking plan. A critical journey or an affected graphics contract can leave pre-merge protection with no review.
   Fix in row 7: a quarantined critical-set member is an incident with an owner and a bounded repair, and AC-4/AC-8 count it. No new retries.

C3. The 24-hour detection bound is not credible as scheduled.
   - The existing alarm (nightly-drift.yml) only checks that some run started within a 26-hour window, and it runs on a schedule twice a day. That is a missed-schedule alarm, not a per-landing coverage deadline.
   - The nightly is scheduled for 00:20 UTC but starts around 04:41-05:47. A landing just after it starts waits about 24 hours plus delay plus run time, which breaches the bound even with no failure.
   - The midday catalog-gates run covers only affected designs, so it cannot certify designs the selection left out.
   Fix:
   - Measure per landing, from merge time to a completed verdict that covers that commit for every design left out, and compute breaches from the run records.
   - Make the midday pass a whole-catalog run (designs=all). The full catalog job takes 9-11 minutes.
   - Keep the existing alarm and add a check of the oldest landing that still lacks full coverage.

C4. If row 9 cannot qualify, the whole run stops, stalling rows that do not depend on scheduled detection.
   Fix: let row 9 PASS with an honest outcome, either "qualified" or "not qualified: full pre-merge catalog retained, blocker named", and let 13a forbid narrowing in the second case. The gate stays in 13a, so this is not a false PASS.

C5. Every row's PASS waits for every exact-merge check.
   Nightly and configured runs flake (4 of the last 10 nightlies failed). An unrelated red can hold a CI row indefinitely. See owner decision 3.

C6. Smaller items.
   - Rows 1 and 14 read many Actions records. They share the 5,000-requests-per-hour GitHub API limit with other plans' landings, so cache the reads and keep the read budget small.
   - Row 9's test dispatches of nightly and catalog-gates should carry the requested-commit input that row 2 adds, so an uncertain dispatch can be matched to its run.
