# G3: Automatic updates, whole publishes

Design gate for phase 6 (W4, O1, S3, E2, E4, AC-4) of `../spec.md`. It covers every point the spec
lists for G3: the saved revision for personal and team productions; an atomic check that a
publication never replaces a newer one; durable pending publication and E4's executor; new outputs
re-reading the whole published copy on boot, on reconnect and periodically, with retries; E2's
transition for old outputs, never reloading one with something on air; switching on per production
only after the guards are in place; and keeping Takes unblocked. It also takes the publish's own
work off the Take's path (owner, 2026-11-12 on #2361, for AC-4) and starts an output preparing at
once (the same decision, for D1). Written against `main` at 814f1059, on top of phase 4 (G1,
production copies, the `production_copies` switch on in production) and phase 5 (G2, run reports,
held Takes, the honest light). Nothing here is built yet; the build is the next pull request.

Whole publishes stay: every publish still writes the whole output payload and an output that takes
a change still reads the whole published copy. Sending only what changed is phase 7 (G4).

## Terms

- **Record.** A production's stored document: a `documents` row of kind `show` (personal, synced
  by `src/backend/sync.ts` as a whole-record upsert, `supabaseProvider.ts:140-148`) or a
  `team_productions` row (team, saved by compare-and-swap through `team_production_save`,
  `teamProductions.ts:256-270`).
- **Saved revision (`rev`).** A number the server gives a record each time it stores it (section 1).
  "The newest save" is the record's current `rev`.
- **Publication.** The `control_shows` row's published columns (`output`, `panel`, `title`,
  `bindings`, `sources`, `collections`, `profile`) as one publish wrote them. Its **stamp** is
  `output.ver` (`payloadVersion.ts`): `n` counts publishes, `h` and `g` name what the outputs render.
  G3 adds `ver.r`, the saved revision the publication was built from, and `ver.c`, a digest of
  everything the publish writes (section 3); `readPayloadVersion` learns to keep both.
- **Published revision (`published_rev`).** The newest saved revision the publication is known to
  show: a new column, kept by the server (section 2).
- **Pending.** A published production whose record `rev` is greater than its `published_rev`: a
  save the outputs do not have yet. Derived from two stored numbers, so it is durable by itself: it
  survives any page closing (E4).
- **Automatic mode.** The `auto_publish` switch is on and the production's `published_rev` is set:
  a new page has published it naming its revision. Then every save is published with no press
  (O1).
- **New output, old output.** An output page built with this phase reports `au: 1` in its Presence
  entry (section 6). An output built before reports none: it is an old output (E2).
- **New page, old page.** A production page built with this phase, or before it. An old page is the
  phase 4 or phase 5 build: it sends the production-copies mark (G1) but writes no `ver.r`.
- **Take path.** As in W1: a press to the start of sending, and on the output, the command's arrival
  to its run (G2's "ran").

Today: publication checks only the stamp's `n` it read (`hostedControl.ts:619-632,971-974`), so a
publish built from an older save can land after a newer one; personal sync is a whole-record upsert
with no server revision; outputs prepare only when the page's Presence entry asks
(`main.ts:459`), marked handled before the fetch (`prepare.ts:196,261`), at most every 15 s
(`prepare.ts:36`), and never compare versions on reconnect (`main.ts:1279`); old outputs learn of a
new build only inside a request (`prepare.ts:190-205`); a publish builds the payload and
stringifies 6 to 20 MB on the page's main thread, which made a Take 100 ms slower at p95 on the
typical fixture and 200 ms on the large one (phase 2 evidence).

## 1. The saved revision, personal and team

One server-assigned number for both kinds of record, so a revision can be compared whichever table
the record lives in:

- A sequence `public.production_revision` and a column `rev bigint` (nullable, no default, so adding
  it does not rewrite the table) on `documents` and on `team_productions`.
- A `before insert or update` row trigger on each table sets `new.rev := nextval(...)`:
  on `documents` only for `kind = 'show'` and only when the statement writes `body` or `deleted`
  (the 0107 pattern: an update of other columns pays nothing); on `team_productions` when it writes
  `doc`. A client never chooses the number: a value it sends is overwritten.
- A before-row trigger runs after the row is locked, so two saves of one record get increasing
  numbers in the order they are stored. The sequence is shared, so a production moved from personal
  to team (`teamProductions.ts`, "move one of yours into a team") gets a team `rev` greater than
  every personal one it had: nothing restarts.
- Every writer is covered, old pages and the agent functions that write documents included (0107's
  list), because the trigger is on the table.

How a page learns the `rev` of what it saved:

- **The server says which revision a record is**, in two small columns read by id, never the body:
  `rev`, and the record's identity as stored. For a personal record the identity is the client's
  `updatedAt` inside the stored body, which 0107 already keeps as `body_updated_at` and which the
  sync engine already uses to tell versions apart; for a team record it is the compare-and-swap
  token `updated_at`. When this tab's record carries the same identity, its content is that stored
  revision (`src/backend/savedRevision.ts`). The sync engine needs no new state.
- **Team.** `team_production_save` (`0054`, `0088`) is replaced with the same signature and the same
  answer plus a `rev` member, read from the row it stored. A new member in a `jsonb` answer is
  ignored by old pages.
- **The record a publish is built from** is the local record whose identity is the stored one: for
  personal, the local record's `updatedAt` equals `body_updated_at`; for team, the record is
  neither dirty nor in flight nor saving (`dirty`, `inflight` and the save state in
  `teamProductions.ts`) and the cache's token equals the stored `updated_at`. Otherwise the answer
  says what to wait for: this tab's own save on its way, or a newer save on the server to bring in
  first. The publisher takes that record object and its `rev` together, at one synchronous moment,
  and builds only from that object. A local edit after that moment is a newer save and gets its own
  publish (section 3).
- A record read before the migration has `rev` null. A page never publishes in automatic mode from
  a record whose `rev` it does not know (section 8).

## 2. The publication guard (the atomic check)

Two columns on `control_shows`, both nullable, added without a default:

- `published_rev bigint`: the saved revision the publication shows.
- `published_ver jsonb`: a copy of `output->'ver'`, so a page or output can read the stamp without
  the server decompressing the whole payload (reading one key of a `jsonb` value reads all of it;
  0107 measured that cost on `documents`).

Two row triggers on `control_shows`, `control_publication_guard_a_rev` (`before update of
published_rev`) and `control_publication_guard_b_output` (`before insert or update of output`),
decide under the row lock the write already holds, so the check and the write are one step. Because
they name their columns, a statement that names neither (a Take's heartbeat, a report, a Pause,
`writePublishedSources`) never runs them, and they never compare two `jsonb` payloads (which would
decompress 6 to 20 MB). Two triggers rather than one, because a trigger cannot tell which columns a
statement named, and comparing the payloads to find out is the cost to avoid:

1. An insert, or an update naming `output`, copies `new.output->'ver'` into `published_ver` (the
   incoming value, not yet stored, so this costs nothing), then reads
   `r := new.output->'ver'->>'r'`:
   - `r` present and greater than the production record's current `rev`: **refused** ("This publication names a
     save that does not exist"). A client cannot name a future revision, so one faulty write can
     never freeze later publishes behind a huge number. The record's revision is the greater of
     both tables' `rev` for the row's id (`control_record_rev`: `documents` of kind `show` and
     `team_productions`, primary-key reads; one production has one id in every table, 0008 and
     0054), never chosen by `team_id`: a production being moved to a team still reads right mid-move.
   - `r` present, `old.published_rev` present and `r < old.published_rev`: the row is **skipped**
     (`return null`). Nothing is written and the request matches no row, so the writer reads the
     row again (section 3). A publication never replaces a newer one.
   - `r` present otherwise: `new.published_rev := r`.
   - `r` absent (a publish from an old page, or from a new page that cannot know the revision, for
     instance before 0117): when the `auto_publish` switch is on and `old.published_rev` is set, it
     is **refused** with "Reload this page to edit" (errcode P0001, hint "This page was opened
     before automatic updates. Takes still work; reload it to edit the production."), the words S2
     uses and the old page already shows as "Publish failed: Reload this page to edit"
     (`useProductionPublish.ts:509`). Otherwise it passes as today and **clears**
     `published_rev` (`null`): the content now on the row comes from no known revision, so the
     production is pending again and the next new page that may publish republishes the newest save
     (review on #2469: with the switch off, an old page's publish must not leave a revision
     claim on content it replaced).
2. An update naming `published_rev` and not `output` (the **revision-only update**, section 3)
   passes only when the new value is not null, not lower than the old one and not greater than the
   record's `rev`; otherwise it is skipped.

What the writer adds, as today a filter on the same statement:

- A full publish keeps `writeControlShow`'s condition on the stamp it read, so two publishes built
  from the same revision still land one at a time and the second learns it raced. The new page
  filters on `published_ver->>n` (a small column) where the column exists, and on
  `output->ver->>n` as today where it does not.
- A revision-only update carries `published_ver->>c = c`: it lands only while the stored content is
  exactly the content this publisher built. A publish that lands in between changes `c` and the
  update matches nothing.

Why a trigger and not a new RPC for the write: the publish keeps its one `PATCH` by id, which takes
`FOR NO KEY UPDATE` and so never blocks a Take's `KEY SHARE` (`0071_command_sequence.sql:373`,
`hostedControl.ts:969`, section 5). The trigger takes no lock and reads no other table except
`system_settings` for the switch, through a `security definer` function as `production_copies_on`
does (0115), and the record's `rev` by primary key.

**Every publish from a new page names its revision.** The first Publish press, Publish changes
(automatic updates off, or not yet on for that production) and every automatic publish all write
`ver.r` whenever the page knows the record's `rev`, whatever the switch says. So the guard's order
holds with the switch off too, and a first Publish needs no second upload to enter automatic mode.

## 3. The publisher on the page (O1, S3, E4)

A plain module, `src/control/autoPublish.ts`, decides; it takes the browser (the save layer, the
server reads and writes, timers, the clock) through an `io` argument and is Node-tested
(`scripts/auto-publish.test.mjs`). The production page runs one per production it shows, only in
automatic mode (section 8).

### What it publishes and when

- **Single flight, newest wins.** At most one publish of a production is in flight on a page. A save
  confirmed while one runs marks the publisher **owed**; when the running publish ends, whatever its
  outcome, the publisher starts again from the newest confirmed record. Saves in between are never
  published one by one: publishing catches up with the newest save (S3).
- **Its own saves.** A publish starts as soon as this page's save of the production is confirmed
  (section 1): for a personal production when a sync pass ends synced, for a team one when its save
  is no longer pending. The personal sync's 2.5 s push debounce (`syncController.ts:334`) and the
  team save stay as they are. A revision counts as pending only once it is confirmed and found
  newer than the published one, so a sync of another record lights nothing.
- **Anyone's saves (the executor, E4).** The page reads two small numbers: the record's `rev`
  (`documents.rev` or `team_productions.rev`, by id, no body) and `published_rev` with
  `published_ver`, by id. It reads them when it opens, every 30 s while open, and right after each
  of its own publishes. When the record is ahead (pending):
  - right after the page opens: it brings its local record to that revision (a sync pass, or a team
    refresh) and publishes at once. This is "the next page opened publishes it" (E4, AC-4);
  - while open: it waits 20 s from when it first saw that revision pending, so the page that saved
    it publishes first, then brings its record up and publishes. Two pages publishing the same
    revision are harmless (the stamp condition lets one land; the other reads `published_rev`, sees
    it already shown, and stops).
- **Only a page that may publish.** The same account gate as Publish (`useProductionPublish.ts`
  `accountBlocks`) and the row policy decide: a signed-out page or an account the row refuses never
  executes, and its light says what it sees (section 9).

### One publish, step by step

1. **Take the record.** The confirmed record object and its `rev` `r` (section 1). If the local
   record is ahead of the confirmed one, nothing starts: the save in flight confirms first and owes
   a publish.
2. **Read the stamp.** `published_ver` and `published_rev` by id (two small columns; no payload, no
   panel). If `published_rev >= r`: nothing to do (a newer or equal save is already published).
3. **Build.** The payload from the record's own copies, as today (`buildOutputPayload`, the gate,
   adjustments measured by `appearanceFor`), in steps on the main thread (section 5). Each graphic's
   digest is computed as today (memoized by copy), and `c` is the digest of a small text: the
   per-graphic digests `g`, the resolution, and everything else the write carries except graphic
   bodies (cues, playout cues, scenes, output setup, rundown colours, sound list, panel entries
   without their code, title, profile). `c` never stringifies a
   graphic body.
4. **Decide.**
   - Stored `c` equals the built `c`: nothing on the outputs would change. A **revision-only update**
     writes `published_rev = r` under the `c` condition (section 2), together with the record's
     `bindings`, `sources` and `collections`, as every full publish does. Those three are left out of
     `c` on purpose: Connect, Disconnect and Pause write them to the row with no publish
     (`writePublishedSources`), so the stored `c` cannot speak for them, and writing them with the
     revision keeps the row's source configuration that of the revision it names (review on #2469).
     No payload is sent, `n` does not move, no output reads anything.
   - Otherwise a **full publish**: the stamp as today (`stampPayload`, `n + 1`), plus `r` and `c`,
     written with the condition on `n` (section 2). The publish-guard "never an older design" check
     (`olderDesigns`, `hostedControl.ts:648-657`) does not apply to a publish that names its
     revision: it was written to stop a page whose copy had not caught up from publishing over a
     newer one, and the revision order now stops exactly that, from the server, for every writer.
     A newer save that holds an older design is what someone saved (an undo of an Update, say): the
     production's copy is the only truth (O4), so it publishes. A publish with no revision keeps the
     check as today.
5. **Answer.**
   - It landed: the page now knows `published_rev = r` and the new stamp; it puts a prepare request
     in its Presence entry (`onPrep`, the same request Publish changes sends today) so every output,
     old ones included, starts at once (sections 6 and 7); and it ends.
   - It matched no row: read the stamp again. `published_rev >= r`: a newer save is published, the
     publish ends as done. Otherwise the stamp moved under it: write again with the new `n` (no
     rebuild; at most 3 times in a row), then count a failed attempt.
   - An error: a failed attempt, of the class below.
6. **Failed attempts.** The save is never undone (S3): nothing in the record is touched by a publish.
   What happens next depends on why it failed:

| Class | Examples | Retried | Header (red) | Panel line |
|---|---|---|---|---|
| Transient | no answer, a timeout, a server error (5xx), a lost connection, an expired session refreshed and still refused once | after 2, 4, 8, then every 15 s while pending and open | Saved, not on the outputs | "The newest save is not on the outputs yet: the server did not answer. Trying again in <n> s." |
| The production cannot go on air | the gate refuses a graphic (`assertProductionGate`, `hostedControl.ts:633`), a package fails its check (`foreignSpec`) | no; the next save of the production tries again, from any page | Saved, not on the outputs | "<graphic> cannot go on air: <reason>. Fix it and the next save publishes." |
| Not allowed | the row matches nothing for this account, RLS refuses, the production is not this account's | no; again only after this page's account changes | Saved, not on the outputs | "This account cannot publish this production. Open it on a device that can." |
| Refused by the guard | a revision the record does not have (section 2) | no; the next save tries again | Saved, not on the outputs | "This save could not be published. The next save tries again." |

   A refusal of these last three kinds is a fact about the production or the account, so retrying
   it would only repeat it; a new save is the only thing that can change it, and every page that may
   publish tries that save. Because publishes are whole, a graphic that cannot go on air holds back
   every later change until it is fixed or removed, which is why its line names the graphic and the
   action.

### What a publish never does

- It never writes the production record. Today's first publish writes the slugs, the published record
  digest and the output setup into it (`useProductionPublish.ts:430-470`). In automatic mode those
  values do not change after the first publish, and a bookkeeping write whose value is unchanged is
  not made, so a publish never causes a save and a save never loops into another publish. The
  publish-guard's reader record (`recordOwnReaderStops`, C6) writes only when a reader stops, a real
  change, after which the next publish finds nothing new and makes a revision-only update.
- It never publishes a record whose `rev` it does not know, a draft not yet saved, or another
  production.
- It never inserts a row: the first publish of a production is the Publish press (O1). An automatic
  publish finding no row (unpublished meanwhile) stops and leaves automatic mode for that production.

### The page's words for it (section 9 has the tones)

- Pending for under 20 s, or a publish running: amber "Updating outputs", panel line "Publishing
  your changes".
- A transient attempt failed twice, a refusal of the other three classes (at once), or a revision
  pending for 20 s or more with no publication: red "Saved, not on the outputs", with the class's
  panel line (E4). It stays red until a revision at least as new is published, then the light is
  judged again as G2 says.

## 4. Durable pending publication

Nothing new is stored to remember a pending publication: the record's `rev` and the row's
`published_rev` already say it, on the server, whichever page saved it and whichever pages have
closed since. So:

- A save whose page closes before it publishes stays pending until any new page that may publish
  opens the production (section 3), and the outputs keep the previous version meanwhile (E4).
- A page open on another device sees it within 30 s and publishes it 20 s after first seeing it.
- Unsaved edits are D6's: they stay in that browser and are saved when the production page opens
  there again, and then published like any save.

## 5. Keeping Takes unblocked

Three places, each with its own rule.

### On the server

- A publish stays one `UPDATE` by id that leaves the key out of its `SET`, so its row lock is
  `FOR NO KEY UPDATE`, which a Take's `KEY SHARE` passes (0071). The new trigger runs inside that
  write, takes no lock of its own and touches neither `control_heads` nor `control_events`, which a
  Take locks. A revision-only update is the same shape. A Take never waits for a publish, and a
  publish never waits for a Take.
- The output's version read (section 6) reads `published_ver` and `published_rev`, two small columns.

### On the page: the publish's own work comes off the Take's path

The publish runs as a series of short steps, so a press is never stuck behind it:

- **No whole-payload text on the main thread.** Today supabase-js stringifies the whole 6 to 20 MB
  row in one task. The new write builds its body from parts, each made in its own step and each
  turned into its own `Blob` in that step: a graphic spec without its assets is one part, each asset
  (a data URL, which can be megabytes) is a part of its own, and each panel entry is one. Turning a
  string into a `Blob` encodes it on the main thread, so no part is bigger than one asset. The body
  is then `new Blob(parts)` over those `Blob`s, which only references them: no step encodes or
  copies the whole payload. It goes with `fetch` as a `PATCH` to the same PostgREST address and
  filter `writeControlShow` uses, with the headers the client sends today (the key, the session's
  current token, the production-copies mark); a 401 refreshes the session once and sends again.
  The answer is `select=id`, a few bytes. The published panel is read only when this publisher's
  library lacks a graphic's record: that graphic's saved entries live in its author's library and
  stay as published (issue #779, `buildPanelSpec`); otherwise the panel is not read at all.
- **Steps, each a separate task.** Gate check, measuring, building and digesting run one graphic or
  one cue per task, each followed by a yield to the event loop (a `MessageChannel` message), so a
  click waits at most for one step. The published-record digest (`publishedRecordDigest`, a canonical
  text of the whole record) is not computed in automatic mode: nothing reads it there.
- **Takes first.** Before each step the publisher waits while a send of this page is in flight
  (graphic verbs, folder, picture, server cue, quick button, Next, panel command: one count of
  sends not yet answered, kept where those paths send, `seqSend.ts` and `serverVerbs.ts`). A press during a publish runs its handler
  and its send with nothing of the publish in between. The upload itself runs in the browser's
  network process and needs no main thread.
- **The target.** No publish step takes more than 16 ms on the large fixture on a production build;
  the build measures every step (section 11) and AC-4 judges the result.

### On the output: reading the published copy off the main thread

An output that takes a new version reads 6 to 20 MB. Parsing that on its main thread delays every
command it runs meanwhile. So:

- The new output reads the published copy in a **worker** (a classic worker built from plain text,
  ES2017, Chromium 71, `src/output/payloadReader.ts`): the worker fetches `control_output_resolve`
  with the output's public key, parses it and posts back its `output` member. The main thread
  receives a copy of the parsed objects (a structured clone: no text to parse), and the swapper,
  the stage and the cues take exactly the payload they took before, so nothing downstream changes.
- No worker (it fails to start, or it errors): the output reads on its main thread as today.
- **No new frame while a Take waits (Q1).** The swapper does not start building a changed or added
  graphic's new frame while this output holds a Take waiting to run (G2 section 3, a hold), except
  the frame that Take itself is waiting for (G2's demand, which still goes first). It starts once
  every waiting Take has run, failed or been cancelled.
- Building a changed graphic's new frame stays main-thread work in the output: that is the change
  itself, not the publish. It happens only when a graphic's design changed (section 13).

## 6. New outputs find the published copy by themselves

A new output checks the published stamp itself, with no page needed:

- **When.** On boot (it reads the whole copy, as today); at once when its log or command channel
  joins again after being down (today nothing happens, `main.ts:1279`), and when the browser goes
  back online; at once on a page's Presence prepare request; and every 30 s.
- **How.** A new function `control_output_version(p_output_slug)` answers `published_ver` and
  `published_rev` for the output's production (the same slug check as `control_output_resolve`;
  anon, like the output's other functions). A stamp whose `n` or `h` differs from the version the
  output holds or is taking starts a preparation. An equal stamp does nothing.
- **Retries.** A probe or read that is not answered is asked again after 2, 4 and 8 s, then at the
  next period. A read whose answer is not the probed version (another publish landed between)
  prepares what it read: an output only ever moves onto what the server holds (`prepare.ts`).
- **At once, newest wins (D1, owner 2026-11-12).** A request for a version other than the one held
  starts preparing at once: the 15 s spacing (`prepare.ts:36`, `PREPARE_EVERY_MS`) no longer applies
  to it. One preparation runs at a time; a newer version asked meanwhile replaces any request still
  waiting and starts the moment the running one ends. A request for the version already held (Check
  now's re-check) keeps the 15 s spacing, so a stream of presses cannot keep a playout box busy.
  G2's demand (a held Take of a graphic the output does not host) is unchanged and still goes first.
- **Within 90 s.** With no page open and no Presence request, a new output reaches a new publication
  within one period (30 s) plus the retries (14 s) plus the read and build (phase 2: up to about
  33 s for the large fixture throttled), so within 90 s, on the typical fixture with margin.
- **Missing function.** An instance without the migration answers PGRST202: the output stops
  probing for this page load and behaves as today (Presence requests only). It still reads at once
  on a request.
- **The `au` mark.** A new output's Presence entry carries `au: 1`. Pages read it (section 7).

### A new build of the renderer, for new outputs

So a later phase's transition needs no page either: every 5 minutes, with the stamp probe, a new
output asks whether its own URL serves another build (`prepare.ts` `newBuild`, bounded by
`PROBE_MS`). A new build is taken by a reload only through `reloadWhenClear` (its URL answers, and
nothing is on air at the last moment) and, on this periodic path only, when no command has reached
it for 60 s. A request-driven check keeps today's rule.

## 7. Old outputs (E2)

An output built before this phase has none of section 6: it prepares only on a Presence request,
spaced 15 s, and reloads onto a new build only inside such a request when nothing is on air
(`prepare.ts` `newBuild`, `reloadWhenClear`). So:

- **Updates still reach it while a page is open.** Every automatic publish puts a prepare request
  in the publishing page's Presence entry (section 3, step 5), exactly as Publish changes does today.
- **It switches over by itself.** The first such request after this phase is deployed tells it a new
  build is served; it reloads onto the new build once nothing is on air there, and comes back as a
  new output. With something on air it waits, and `tick` retries every 15 s once air clears
  (`prepare.ts` `tick`, `reloadForBuild`). It is never reloaded with something on air.
- **The light.** A page sees an expected output without `au` and says amber "Reload <output> when
  nothing is on air", panel line "<output> was opened before automatic updates. It takes changes
  while this page is open, and switches over by itself the next time nothing is on air there." The
  amber clears when the output reports `au`. G2's row for an output with no `run` (built before
  phase 5) already has these header words and keeps its own panel line.
- With every page closed and no request, an old output keeps what it holds until a page opens: the
  executor's publish or the opening page's request reaches it then.

## 8. Switching on, per production, only after the guards are in place

Order, each a separate step:

1. **Migrations land** (section 12): the revision column and triggers (ordinary), then the
   publication guard and the version function (live-path, applied by post-land in a quiet window,
   supabase/AGENTS.md). Installed, they change nothing visible: `rev` numbers start counting, the
   guard's refusal needs the switch, and its skip needs a `ver.r` nobody writes yet.
2. **The app is released.** New pages and outputs carry the code. Automatic updates stay off: pages
   show Publish changes as today.
3. **The switch.** A `system_settings` row, key `auto_publish`, value `{"on": true}`, read through
   `auto_publish_state()` (signed-in pages only, like `production_copies_state`), which also answers
   whether the guard is installed. Turned on by the owner, or by the coordinator with his permission,
   after the app is live and the state function reports `installed: true` on production. Off or
   unreadable means off.
4. **Per production.** A page runs the publisher for a production only when all of these hold: the
   state function says installed and on; the production is published; the page may publish it
   (section 3); and the page knows its record's `rev`. Then its first automatic publish writes
   `ver.r`, and the guard sets `published_rev`: that production is in automatic mode, and from then
   on the guard refuses an old page's publish of it. Productions move one by one, each when a new
   page that may publish it opens it. A production a new page published (with `ver.r`) while the
   switch was off is already in automatic mode the moment the switch is on.

The first automatic publish of a production also publishes any saved change someone had held back
until a later Publish changes, possibly mid-show: from then on a save is a publish (O1). Outputs
take it as any change (O3: a graphic on air keeps its frame until its next Take).

What the page shows depends only on these facts: in automatic mode there is no "Publish changes"
(O1); the first press is still Publish; Check now stays. Off, or not yet on for that production, the
page is today's page.

**Back out.** Switch off (delete the row or set `"on"` to false): pages stop publishing by themselves
at their next state read (every 30 s) and show Publish changes again; the guard stops refusing old
pages. A new page's Publish changes still names its revision, so a publication still never
replaces a newer one; an old page's publish clears `published_rev` (section 2), so when the switch
is on again that production reads pending and the newest save is published. No deploy, nothing
persisted to repair.

## 9. The light (O2, E4, E2)

`src/control/playoutStatus.ts` and G2's `runConfirm.ts` gain three rows; the worst tone wins, as G2
says.

| State | Tone | Header words | Panel line |
|---|---|---|---|
| A save the outputs do not have: a transient failure twice, a refusal, or pending 20 s | red | Saved, not on the outputs | the refusal class's line (section 3) |
| A save pending under 20 s, or a publish running | amber | Updating outputs | "Publishing your changes" |
| An expected output without `au` | amber | Reload <output> when nothing is on air | section 7's words |

- Red outranks every amber and grey, so a failed publish is never hidden by an output loading.
- The line is the failure's class in plain words (section 3's table); it is never a code.
- After the publish lands, G2's rows judge the outputs taking it ("Updating outputs" while they
  prepare, then green or the O3 line "<graphic>: new design at next Take").
- A page that may not publish (signed out, no right) and sees a revision pending reads the same red
  row with the reason "Open it on a device that can publish", so a pending save is never green.

## 10. Old pages

A page built before this phase (phase 4 or 5) keeps playing out exactly as today and saving as today
(its saves get a `rev` from the trigger and are published by any new page that sees them pending).
Its Publish changes press, once the production is in automatic mode and the switch is on, is refused
by the guard with "Reload this page to edit", the S2 words, and changes nothing stored: its build
cannot say which revision it publishes, so it could replace a newer publication. Before automatic
mode, or with the switch off, it publishes as today. While the `production_copies` switch is on (it
is in production), an old page's publish is already refused with the same words by the 0115 guard
if it lacks the build mark; this rule matters for pages that carry the mark but no revision (the
phase 4 and 5 builds), which 0115 admits.

## 11. Rules

Observable lines the build is tested against. Section numbers say where each is designed.

- **R1** Every store of a production record gives it a `rev` from one server sequence, greater than
  every `rev` that record had, personal or team; a client cannot choose it (1).
- **R2** A new page's every publish (first Publish, Publish changes, automatic) is built from a
  record whose content is exactly a confirmed saved revision and names it in `ver.r` whenever the
  page knows it, whatever the switch (1, 2, 3).
- **R3** A publication carrying `r` lower than the stored `published_rev` changes nothing stored
  (2). Two publishers finishing in reverse order leave the newer revision published (AC-4).
- **R4** A publication writing no `r` is refused with "Reload this page to edit" and changes nothing
  stored while the switch is on and `published_rev` is set; otherwise it lands and clears
  `published_rev`, so the newest save is published again by the next new page (2, 10).
- **R4a** A publication or revision-only update naming a revision greater than the record's current
  `rev` is refused (2).
- **R5** A revision-only update lands only while the stored content digest equals the built one and
  its revision is not lower, and it writes the record's bindings, sources and collections with the
  revision, so the row's source configuration is the revision's (2, 3; review on #2469).
- **R6** At most one publish per production is in flight on a page; a save confirmed meanwhile is
  published after it, and the publish after it is built from the newest confirmed record (3).
- **R7** A failed publish never changes the record. A transient failure is retried after 2, 4, 8,
  then every 15 s while pending; a refusal (the production cannot go on air, not allowed, refused
  by the guard) is not retried until a new save, or for "not allowed" a new account, and reads red
  at once with its own line naming the graphic or the action (3, S3).
- **R7a** A publish that names its revision is not stopped by the publish-guard's older-design
  check; one with no revision still is (3; owner decision Q2, section 15).
- **R8** A pending revision is published by the first new page that may publish and opens the
  production, at once, and by an open page 20 s after it first saw it (3, 4, E4).
- **R9** A publish never writes the production record, so with no edit there is no further save and
  no further publish (3).
- **R10** No publish step on the page runs longer than 16 ms on the large fixture on a production
  build, and no step starts while a send of the page is in flight (5).
- **R11** A publish never takes a lock a Take waits for; a Take pressed during a publish's write is
  answered without waiting for it (5).
- **R12** A new output parses a published copy off its main thread and hands its preparation the
  same payload as before (5).
- **R13** A new output probes the published stamp on boot, on rejoin, when back online, on a
  prepare request and every 30 s, retrying 2, 4, 8 s, and starts preparing a different version at
  once, the newest winning; a re-check of the version held keeps the 15 s spacing (6).
- **R14** With no page open and no request, a new output reaches the newest publication within 90 s
  (6).
- **R15** No output reloads with something on air; a new output reloads for a new build on its own
  only when nothing is on air and no command reached it for 60 s (6, 7).
- **R16** An expected output without `au` reads amber "Reload <output> when nothing is on air" until
  it reports `au`, and still takes every automatic publish while a page is open (7).
- **R17** Pages publish by themselves only while the state function says installed and on and the
  production's `published_rev` is set or this page's own publish sets it; off, pages show Publish
  changes, still name revisions, and the guard refuses nothing (8).
- **R18** A revision pending 20 s, or a publish failed twice, reads red "Saved, not on the outputs";
  a pending revision is never green (9).
- **R19** In automatic mode there is no "Publish changes"; the first Publish and Check now stay (8,
  O1).
- **R20** An output starts no new frame for a changed or added graphic while it holds a Take waiting
  to run, except the frame that Take waits for (5, Q1).

## 14. Decisions and limits

- **Whole publishes.** Every change still uploads the whole payload (6 to 20 MB) and a changed
  graphic still makes outputs read the whole copy; phase 7 sends only what changed. While somebody
  edits, the page publishes once a sync pass ends synced, which needs a pause in editing at least as
  long as the 2.5 s debounce plus the pass itself (owner decision (a), 2026-11-13). It never publishes
  mid-typing, and at most one publish runs at a time.
- **The save is not the publish.** The personal sync still writes the whole record on the main
  thread (4.4 to 13.9 MB per edit, phase 2); AC-4 judges publishing, and the save becomes a patch in
  phase 7.
- **A design change loads on the output's main thread.** Building a changed graphic's new frame is
  main-thread work on the output that a browser cannot split; a Take arriving while it loads may wait
  for it. AC-4 does not judge it; it is measured and reported (Q1, section 15), and an output never
  starts one while a Take for it waits (section 5, R20).
- **Old pages' publishes are refused in automatic mode** (section 10) rather than allowed with an
  unknown revision: an old page cannot say what it publishes, and S2 already gave pages from before a
  switch these words. Their Takes and saves keep working.
- **Constants.** 20 s grace for another page's save, 30 s page and output periods, 2, 4, 8, 15 s
  retries, 60 s quiet before a periodic build reload, 16 ms per publish step. The build may tune a
  period downward only with the measured reason in the evidence; the 90 s and 50 ms acceptance stay.
- **Several pages.** Up to five pages may publish the same revision at the same moment once each, a
  few whole uploads; the stamp condition lets one land and the rest stop. Phase 8 measures it.
