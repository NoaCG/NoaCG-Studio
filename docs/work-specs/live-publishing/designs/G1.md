# G1: The production's copy is the only truth; old pages only play out

Design gate for phase 4 (W2, O4, O5, S2, E3, AC-2) of `../spec.md`. It covers the four points the
spec lists for G1: how each write identifies its build, a guard on every production-authoring
route only, the order of server guard, adoption and app release, and E3's handling of retained
edits. It also says how the phase 3 owed cue edit meets E3 and the guard. Written against `main`
at 0e65d859. Nothing here is built yet; the build is the next pull request.

## Terms

- **Copy.** A production's own `SavedGraphic` (`src/model/packets.ts:39`): `template`, `savedAt`,
  layer, sounds, adjustments, `graphicId`. Stored inside the production record (personal:
  `documents` row of kind `show`; team: `team_productions.doc`).
- **Library record.** The `GraphicDoc` a copy came from (`graphicId`), edited in the editor.
- **Today.** Readers resolve the library record first and fall back to the copy
  (`templateForSavedGraphic`, `src/model/library.ts:467`; `designEditedAt`, `:474`; and the
  direct reads listed in section 1), and a publish copies newer library designs into the record
  before it writes (`refreshGraphicCopies`, `src/model/shows.ts:1010`, called from
  `src/components/home/useProductionPublish.ts:432`).
- **Old build.** Any page loaded from a bundle before this phase's build. **New build.** This
  phase's bundle and later.
- **Design stamp.** A new optional member of `SavedGraphic`, `designAt` (ISO), which the new build
  sets equal to `savedAt` whenever it sets that copy's design. A copy is **settled** when
  `designAt` is present and equals `savedAt`. An old build never writes `designAt`: its design
  writes (`refreshGraphicCopies`, `addGraphicToShow`, `setGraphicCopyScript`) either change
  `savedAt` and leave `designAt` as it was, or build a fresh object without it, and the team merge
  takes a graphic as a whole item, never field by field. So an unsettled copy is one whose design
  an old build set, or one no new build has settled yet. The stamp is per copy, so a later
  new-build write elsewhere in the record (a cue edit, an owed edit recovered) never makes an old
  build's design look settled. Additive optional: no format version changes.
- **Build mark.** A request header, `x-noacg-production-copies: 1`, that the new build's Supabase
  client sends on every request (`createClient(..., { global: { headers } })`,
  `src/backend/supabase.ts:109`, the app's one client). Old builds send none.
- **The switch.** A row of `system_settings` (migration 0019), key `production_copies`, value
  `{"on": true}`. Absent or anything else means off.

## 1. One source for what plays (O4)

Every read of a pool graphic's design reads its copy. The library is read only for the mark and
Update (section 2) and for entries.

| Read today | Becomes |
|---|---|
| `templateForSavedGraphic(g, library)` (`library.ts:467`): payload and panel (`hostedControl.ts:362,471`), monitors, measuring, clocks and fields on the production page (`ProductionPage.tsx`, 15 sites), publish gate (`productionGate.ts:47`), show export, `packSources.ts:37`, export appearances, `useRundownAuthoring.ts:189` | the copy, `withProductionSounds(g.template, g.soundConfig)`; signature kept, so these move with it |
| `designEditedAt(g, library)` (`library.ts:474`): G3's edit times (`hostedControl.ts:621`), measure keys (`ProductionPage.tsx:2287,2381,4102`) | `g.savedAt` |
| `libraryGraphicDigests` (`hostedControl.ts:566-590`): skips a copy whose record is gone, memo keyed by the record's `updatedAt` | the copy's digests, every graphic, memo keyed by the copy; `usePublishDrift` then no longer reports a library edit as a change to publish |
| `graphicsPack.ts:788`: a graphic with sounds takes the library template | `g.template` (the pack carries the sounds itself, as today) |
| `SourcesLine.tsx:37` `ownSheetReader`: the library script as the "design" | the copy's script; `resolvedJs` and `copyJs` are then the same |
| `shows.ts:2277` `ownSheetGraphics`: copy or library script reads a Sheet | the copy's script only |
| `ProductionPage.tsx:3067,3075` own-reader removal: offered and planned from the library record | planned on the copy (`setGraphicCopyScript`, which also stamps `designAt`); the library record is still cleaned when held, for later adds |
| `ProductionPage.tsx:4556,4562` sound editor | the copy |
| `refreshGraphicCopies` in publish (`useProductionPublish.ts:432`) | removed: a publish never copies a library design |
| `entriesForSavedGraphic` (`library.ts:453`), panel entries (`hostedControl.ts:370`), `activeEntryValues` (`showExport.ts:165`) | unchanged: entries are named value sets, never played by an output, and this phase does not move them |

So a library edit, or a library record that is broken or deleted, changes nothing on the monitors,
in a publish (payload, panel, gate) or on an output. A Node test fails if any design read listed
here reaches the library. The G3 guard (`olderDesigns`, `hostedControl.ts:621-628`) stays: it now
compares copies' `savedAt` with the published edit times.

## 2. Newer design in library, and Update (O4)

- **The mark.** A copy with a `graphicId` whose library record this browser holds, whose record
  `updatedAt` is later than the copy's `savedAt`, and whose template differs from the copy's (the
  digest of section 3) shows "Newer design in library" in the cue editor's graphic section, beside
  the playout layer (`CueEditor.tsx:1723`), with an **Update** button. Copies matched by name only
  never show it.
- **Update** replaces the copy's `template` with the library record's, setting `savedAt` to the
  record's `updatedAt` and `designAt` to the same. It keeps the copy's id, pool name (the
  template's `name` is set to the pool name, since outputs key graphics by it), layer, position in
  the pool, sounds, adjustments and `graphicId`. Cues are not touched: their values, typed data,
  selections, shortcuts and bindings stay as they are.
- **A dropped field is named first.** When the copy has a field the new design lacks and a cue of
  this graphic holds a value for it or a binding names it, Update first says
  "Update drops <field label> from <n> cues." with Update and Cancel. Confirmed, the values stay in
  the cues (harmless, and they come back if a later design restores the field); only the field
  stops showing.
- Update runs the production gate on the new design first (`assertProductionGate`); a design the
  gate refuses is not taken, the note says why and the copy stays.
- Update is an authoring write: on a team production it goes through the team save and its merge;
  it is one undo step. It publishes nothing by itself (automatic updates are phase 6). On air, the
  new design follows the existing rule: at its next Take after the next publish (O3).
- Adding a graphic to a production (`addGraphicToShow`) stamps `designAt`. Adding again a graphic
  the production already holds from the same library record is an Update by another door and
  follows the same rules, dropped-field question included.

## 3. Adoption (O5)

Adoption settles every unsettled copy once, per copy, by the rule below. It is what turns "a
production's copies become what is published now; a production never published takes the
library's current design once" into stored designs.

- **When.** On the production page, once the page has the record and the account may write, and,
  for a published production, once the published stamp (`output->ver`, read as one field as
  `publishControlShow` does) has been read. And, wherever the page is, before any send of a record
  holding an unsettled copy: a publish, a team save, a move to a team (`teamProductions.ts:702`)
  or a personal sync push settles it first (section 5 gives the base it reads). A new-build write
  elsewhere (Home "+ Production") stamps only the copy it writes; the send that carries it settles
  the rest. So every production is settled by the first new-build send of it, opened or not.
- **How it is stored.** One authoring write of the copies it changes, with a new `updatedAt`,
  through the normal paths (personal store and sync, team save with its compare-and-swap). It is
  never an undo step: the history does not record it, so the first Undo after opening undoes the
  operator's own last action. A copy whose design is already the right one still gets its stamp.
  Nothing is written when every copy is settled.
- **The rule, per unsettled copy.** Candidates in order: the copy, the base's copy (section 5),
  the library record.
  - Published, and the graphic is named in the stamp: the first candidate whose digest equals the
    stamp's `g[name]`; if none, the first whose edit time equals `t[name]`; if none, the copy.
    The digest is computed by the same function a publish uses (`graphicSpec` and `graphicDigest`,
    with this copy's name, layer and sounds, and the look's face on the first graphic as
    `buildOutputPayload` adds it), with the candidate's template in place.
  - Unpublished, or a graphic added after the last publish: the library record's current design
    when this browser holds it (by `graphicId`), otherwise the copy.
  - A copy kept because nothing matched may be older than what is on air; a later publish is then
    refused by G3 with its existing note, as today.
- **Two pages adopting at once.** Team: the compare-and-swap refuses one, its merge keeps the
  other's copies (same item changed on both sides: theirs stands), and both end settled. Personal:
  two devices of one account adopting one production at the same moment produce a "(conflicted
  copy)" as any two concurrent edits do today (`src/backend/sync.ts:195-200`); nothing is lost,
  and the copy carries no slugs, so nothing reaches air from it.
- **Before adoption on a just-opened page,** the monitors show the record's copies; adoption can
  change a monitor's design once, right after opening. Outputs are not affected: they play the
  published payload.

## 4. How each write identifies its build, and the guard (G1 points 1 and 2)

**Identification.** The build mark header. A header cannot be echoed back by an old build from
stored data, unlike a body field (old builds keep unknown record fields: `readShape` in
`src/model/shows.ts:641` spreads them), it rides every route alike (table writes, the
`team_production_save` RPC, deletes), and PostgREST exposes it to the database as
`current_setting('request.headers', true)`. Old builds send none.

**The guard.** One migration adds a `before` row trigger on each table that holds production
authoring, and changes nothing else. All three call one `security definer` function with
`set search_path = ''`, owned like the other definer functions, so it reads `system_settings`
(RLS on, service role only) whatever role the request has; it is granted to no client role.

| Table | Fires on | Production-authoring because |
|---|---|---|
| `documents` | insert, update of `body` or `deleted`, delete; acts only where the row's `kind = 'show'`, and passes a delete of a row that is already a tombstone (`old.deleted`) | personal sync of a production (`supabaseProvider.ts:148`) |
| `team_productions` | insert, update of `doc`, delete | team save RPC (`teamProductions.ts:262`), move to a team, team delete |
| `control_shows` | insert, delete, update of `output`, `panel`, `title`, `profile` | publish (`hostedControl.ts:971-994`), unpublish (`:1088`) |

The trigger refuses the write with `raise exception 'Reload this page to edit'` (SQLSTATE
`P0001`) when all of these hold: the switch is on; the request comes from a signed-in client (the
request's JWT role is `authenticated`); and the request carries no build mark. Otherwise it passes
the row through unchanged. So:

- **Not production authoring, never refused:** documents of every other kind; the tombstone purge
  (`supabaseProvider.ts:166-176`, one statement across kinds, which a refused show row would
  otherwise stop for every kind); every `control_shows` write naming none of those columns (live
  cue, audience state, slugs, heartbeats, the team stamp, and `bindings`, `sources` and
  `collections` written alone by `writePublishedSources`, `hostedControl.ts:785-788`); every
  command, report, heartbeat and data write (`control_events`, `control_heads`, the `control_*`
  RPCs); and every server-side writer (agent deliveries, sweeps, service role).
- **Why sources pass.** S2 refuses an old page's saves and publishes; it says the page still plays
  out. A data source's Pause and Resume are live controls ("the tick honours a Pause with the page
  closed") written through the same route as Connect and Disconnect, and the wire cannot tell
  them apart. Refusing them would stop an operator pausing a feed mid-show, which "Let's avoid any
  risky changes" rules out. So an old page's Connect or Disconnect still changes the published
  row's sources (its record save is refused, so the record does not follow), until the next
  publish writes the record's sources again. That is the only stored effect an old page keeps
  after the switch, and it is a live data control, not a design.
- `P0001` is deliberate: an old personal sync marks `42501` and RLS words as a permanent denial
  (`supabaseProvider.ts:153`), and a refusal must not be read that way. A refused put stays
  pending on its device (`sync.ts:446-449`), so nothing the old page did is lost.
- On `control_shows` the trigger fires only for publish-shaped writes, never for a Take, so the
  Take path is unchanged and no lock a Take waits on is added.
- What an old page shows is its own build's failure text, which carries the server's words:
  personal sync's error detail, the team save note, and "Publish failed: Reload this page to edit".
  Its Takes, Outs, value Updates, data patches, reports and heartbeats keep working: it only plays
  out (S2).

The migration is live-path (a trigger on `control_shows`), so it has the live-path header and the
timeouts, applies only in a quiet window (`supabase/AGENTS.md`), and is additive (new functions
and triggers; no column, signature, grant or policy of an existing object changes). Its self-check
calls each trigger as `authenticated` and as service role, with the switch on and off and the mark
present and absent, inside a block a sentinel rolls back, so the switch is never left on. Earlier
migrations' self-checks that impersonate `authenticated` run with the switch off (no row), so the
guard passes them; the build greps them for writes to guarded columns all the same.

## 5. Retained edits under the new build (E3)

An edit made by an old page and not yet stored on the server is retained on its device: a team
production's pending edit in its outbox (`base` and `local`, `src/model/teamOutbox.ts`, restored
at `teamProductions.ts:486-495`), or a personal record pending push in the local store, including
a "(conflicted copy)" an old sync made of it (a new production id, its graphics keeping their
ids, `sync.ts:485`). When the page reloads under the new build, the edit goes up through the new
build's write paths with the mark, so the guard passes it. Before it does, every unsettled copy in
it is settled against a **base**:

- team: the edit's `base`, or for a save refused by compare-and-swap, the stored document it is
  merged onto;
- personal: the server's copy of the same record, read with `get` before the push; when there is
  none (a conflicted copy's new id), the stored production on this device holding a settled copy
  with the same graphic id (its source).

Per unsettled copy:

1. **The base holds that graphic settled** (same id): the copy takes the base's design, so a
   design the old page pulled from the library is dropped. That includes adding again a graphic
   the production already held (it keeps the id and takes the library design: a pull). One
   explicit design edit is kept: Connect data's own-reader removal, recognised exactly (the
   template equals the base's except its script, and that script is `stripLiveData` of the base's
   script). It is re-stamped, so the reader the operator removed stays removed.
2. **Otherwise** (no base holds it settled: a graphic the old page added, or one never settled)
   the adoption rule of section 3, with the base's copy as a candidate. A graphic the old page
   newly added has no base copy and keeps its design (unpublished rule: the library record it was
   just taken from, or the copy).
3. The copy is stamped.

The settle is a local authoring write with a new `updatedAt`, made before the send and never an
undo step, so this device's store, its monitors and what is sent agree. Then the edit merges as
usual for its kind: a team edit by the three-way merge (`src/model/teamShowMerge.ts`), where a
settled copy equal to the base leaves the teammate's side standing; a personal record by the sync
engine's last-write-wins, or a "(conflicted copy)" when the server's record changed meanwhile.
Cue edits, added or removed cues and graphics, folders and the rest of the record are kept exactly
as that merge keeps them today. A personal record whose base cannot be read yet is not pushed
until it can; meanwhile the page shows the copy as stored, and a publish settles first, which
needs the server too.

**The owed cue edit (phase 3).** A page-hide record (`src/model/owedCueEdit.ts`) holds a cue id
and texts: label, note and values. The new build applies it as before (P2: through the history,
only when the cue still holds one of the recorded texts, so a teammate's newer text stands). It
never writes a design: it cannot set a copy's template, `savedAt` or `designAt`, so an old page's
pulled design in the same record stays unsettled and is settled by the rules above before the
record is published, saved to the team or pushed. Applied under the new build, the write carries
the mark and passes the guard, which is right: E3 keeps an old page's cue edits. A record the new
page cannot apply (the cue changed) is dropped exactly as P2 says today. Its format does not
change.

## 6. Order: server guard, app release, adoption, switch (G1 point 3)

1. **The migration lands and is applied** (quiet window). The switch is off, so every write passes
   as before; the guard is inert. Applied before the app that sends the mark, as the run requires.
2. **The new app is released.** New pages send the mark, read only copies, show the mark and
   Update, and settle each production at its first new-build send. Old pages still write as
   today, and in this window an old page's publish can still pull a library design into a stored
   copy and onto air, exactly as today; a copy it pulled into a record it saves cannot be told
   from an old publish that reached air, so section 5 cannot undo it later. This window is
   today's behaviour, not a regression, and it is kept short.
3. **The switch is turned on** as soon as the release is confirmed live: first one new-build save
   and publish on production pass with the mark (the header reaches the database through the
   gateway), then the row is written (service role). From then on, every old page's production
   save, sync, publish and delete is refused with "Reload this page to edit" and changes nothing
   stored. The owner, or the coordinator with the owner's permission, does it; this run never
   writes production settings itself.

Back out at any step: turn the switch off (instant, no deploy); revert the app (old builds ignore
`designAt`; the stamps they leave are harmless); the inert triggers can stay, or a later migration
drops them.

## 7. Rules

Observable lines; the build PR repeats them under **Rules** and tests them.

- R1. Every read of a pool graphic's design reads its copy (section 1's table); no library edit,
  break or delete changes a monitor, a publish's payload, panel or gate, or an output.
- R2. A copy with a newer, different library design shows "Newer design in library" and Update.
  Update takes that design, keeps the copy's id, pool name, layer, position, sounds, adjustments
  and link, touches no cue, and asks first when it drops a field a cue uses or a binding names.
- R3. Every copy the new build sets the design of has `designAt === savedAt`; every other write
  leaves `designAt` alone; a copy without `designAt` is unsettled.
- R4. Adoption and the send-time settle are written once, with a new `updatedAt`, never as an undo
  step: published and named in the stamp, the candidate whose digest (then edit time) matches;
  otherwise the library record's current design if held; otherwise the copy.
- R5. With the switch on, a signed-in write without the build mark to a production-authoring
  route (section 4's table) is refused with "Reload this page to edit" and stores nothing; with
  the mark, with the switch off, or from the server's own roles, it passes unchanged.
- R6. Writes that are not production authoring (other document kinds, a tombstone purge,
  commands, reports, heartbeats, data, live cue, audience, slugs, published sources alone) are
  never refused by the guard.
- R7. A retained old-page edit, reopened under the new build, keeps its cue edits merged as its
  kind merges today; each copy it holds whose base holds that graphic settled takes the base's
  design, except an exact own-reader removal, which is kept.
- R8. A recovered owed cue edit writes cue text only, as P2 says, and never settles or changes a
  copy.
- R9. The guard is applied before the app; the switch is turned on only after the app is live and
  a marked save has passed on production; turning it off restores today's behaviour at once.

## 8. How AC-2 is tested

- **Node tests** (`scripts/`, importing `src`): the payload and panel built from a production
  whose library record was edited, broken or deleted are unchanged, and no design read in section
  1 reaches the library (R1); Update's keeps and its dropped-field question (R2); stamps on every
  design write and none elsewhere (R3); adoption candidates against a stamp, digest then edit time
  then copy, published and unpublished (R4); the E3 settle against a team base, a personal server
  copy and a conflicted copy's source, the own-reader removal, team merge with a teammate's edit,
  and an owed edit beside an unsettled copy (R7, R8). The settle is checked against a small
  reference model written from these rules, not a copy of the production code.
- **Database test on the local stack** and the migration's self-check: R5 and R6 per table and per
  route, with the switch on and off, the mark present and absent, signed-in and service role.
- **Configured spec with an old-build page.** An old build is the new page with its mark removed
  on the wire (Playwright `route` drops the header); the switch is turned on in the isolated stack
  through the service role. It saves, syncs (personal), saves (team) and publishes: each is
  refused with "Reload this page to edit" and the stored rows are unchanged; its Take, report,
  heartbeat and a source Pause still work. Reopened with the mark, its retained cue edit merges and
  a design seeded as pulled from the library (an unsettled copy in its retained edit) is dropped.
  Editing and breaking the library graphic changes nothing on the monitors, in the published row
  or on an output page, and the graphic shows "Newer design in library"; Update keeps cues,
  values, adjustments, link and position and names a dropped field first. The same spec proves the
  header reaches the database through the local gateway from the browser.
- **Save paths under reload** (lesson from phase 3): for adoption, Update and a retained edit, the
  save is delayed on purpose and the page reloaded at once, with a mouse press and with a touch
  press; nothing is lost and no copy is left half settled.
- **Not checked by the run**, for the owner's final check: none in this phase (no hardware path
  changes). The production header check before switch-on is section 6's step 3.

## 9. Limits

- An old page in another tab of the same browser writes the shared local store directly. With no
  account, no server can refuse it; signed in, the new tab's sync pushes the old tab's local
  edits with the mark. Either way those edits meet section 5 before they are sent, as a retained
  edit does, so its pulled designs are dropped and its cue edits kept.
- In section 6's window, an old page's publish can still put a library design on air and into a
  stored copy (today's behaviour), which section 5 then treats as published.
- A published design that no candidate on the adopting device matches is not recoverable from the
  payload (it holds built code, not the template); the copy is kept and G3 refuses a publish that
  would put an older design on air, as today.
- An old page's Connect or Disconnect of a data source still reaches the published row (section
  4, why sources pass) until the next publish.
- An old page whose save is refused retries its push as its build does (the whole record each
  pass) until it is reloaded.

No behaviour choice the owner has not made was needed. "Reload this page to edit" and "Newer
design in library" are the spec's words; the dropped-field question follows AC-2; letting a data
source's Pause through follows S2 (an old page still plays out) and O12; dropping a re-added
design and keeping an exact own-reader removal follow E3 (only designs pulled from the library
are dropped).
