# G1: The production's copy is the only truth; old pages only play out

Design gate for phase 4 (W2, O4, O5, S2, E3, AC-2) of `../spec.md`. It covers the four points the
spec lists for G1: how each write identifies its build, a guard on every production-authoring
route only, the order of server guard, adoption and app release, and E3's handling of retained
edits. It also says how the phase 3 owed cue edit meets E3 and the guard. Written against `main`
at 0e65d859. Nothing here is built yet; the build is the next pull request.

## Terms

- **Copy.** A production's own `SavedGraphic` (`src/model/packets.ts:39`): `template`, `savedAt`,
  layer, sounds, adjustments, `graphicId`. Stored inside the production record (personal:
  `documents` row of kind `show`; team: `team_productions.doc`).
- **Library record.** The `GraphicDoc` a copy came from (`graphicId`), edited in the editor.
- **Today.** Readers resolve the library record first and fall back to the copy
  (`templateForSavedGraphic`, `src/model/library.ts:467`; `designEditedAt`, `:474`; and the
  direct reads listed in section 1), and a publish copies newer library designs into the record
  before it writes (`refreshGraphicCopies`, `src/model/shows.ts:1010`, called from
  `src/components/home/useProductionPublish.ts:432`).
- **Old build.** Any page loaded from a bundle before this phase's build. **New build.** This
  phase's bundle and later.
- **Design members** of a copy: `template`, `savedAt`, `designAt` and `graphicId`. The rest of the
  item (id, name, layer, sounds, adjustments) is its **placement**.
- **Design stamp.** A new optional member of `SavedGraphic`, `designAt` (ISO), which the new build
  sets equal to `savedAt` whenever it sets that copy's design (Update, add, own-reader removal,
  settle, adoption). A copy is **stamped** when `designAt` is present and equals `savedAt`: its
  design was set by a new build. An old build never writes `designAt`: its design writes
  (`refreshGraphicCopies`, `addGraphicToShow`, `setGraphicCopyScript`) either change `savedAt` and
  leave `designAt` as it was, or build a fresh object without it, and its team merge takes a
  graphic as a whole item. So an old build's design write always leaves the copy unstamped. A
  copy no new build has written is unstamped too (every copy before release). The stamp is per
  copy, so a new-build write elsewhere in the record (a cue edit, an owed edit recovered) never
  stamps an old build's design. Additive optional: no format version changes.
- **Build mark.** A request header, `x-noacg-production-copies: 1`, that the new build's Supabase
  client adds to its REST API requests (section 4). Old builds send none.
- **The switch.** A row of `system_settings` (migration 0019), key `production_copies`, value
  `{"on": true}`. Absent or anything else means off.

## 1. One source for what plays (O4)

So a library edit, or a library record that is broken or deleted, changes nothing on the monitors,
in a publish (payload, panel, gate) or on an output.

The record digest that says a production changed since its publish (`publishedRecordDigest`,
`publishedRecord.ts:61`, read by `usePublishDrift`) leaves out `savedAt` today and digests a
template only for a linked copy. Copies are now what publishes, so it digests every copy's
template, linked or not, and leaves out `designAt` beside `savedAt`: stamping or adopting a copy
whose design is unchanged never makes a production read as changed since its publish. A Node test fails if any design read listed
here reaches the library. The G3 guard (`olderDesigns`, `hostedControl.ts:621-628`) stays: it now
compares copies' `savedAt` with the published edit times. Its note says "Reload this page to get
it" today, which a reload cannot fix once copies are the truth; it says instead "<graphic> on air
is newer than this production's copy." and, when the library holds a newer design, "Update it
from the library first."

## 2. Newer design in library, and Update (O4)

- **The mark.** A copy with a `graphicId` whose library record this browser holds, whose record
  `updatedAt` is later than the copy's `savedAt`, and whose template differs from the copy's (by
  the record digest's per-template digest, `templateDigest`, `src/model/publishedRecord.ts:49`) shows "Newer design in library" in the cue editor's graphic section, beside
  the playout layer (`CueEditor.tsx:1723`), with an **Update** button. Copies matched by name only
  never show it.
- **Update** replaces the copy's `template` with the library record's, setting `savedAt` to the
  record's `updatedAt` and `designAt` to the same. It keeps the copy's id, pool name (the
  template's `name` is set to the pool name, since outputs key graphics by it), layer, position in
  the pool, sounds, adjustments and `graphicId`. Cues are not touched: their values, typed data,
  selections, shortcuts and bindings stay as they are.
- **A dropped field is named first.** When the copy has a field the new design lacks and a cue of
  this graphic holds a value for it or a binding names it, Update first says
  "Update drops <field label> from <n> cues." with Update and Cancel. Confirmed, the values stay in
  the cues (harmless, and they come back if a later design restores the field); only the field
  stops showing.
- Update runs the production gate on the new design first (`assertProductionGate`); a design the
  gate refuses is not taken, the note says why and the copy stays.
- Update is an authoring write: on a team production it goes through the team save and its merge;
  it is one undo step. It publishes nothing by itself (automatic updates are phase 6). On air, the
  new design follows the existing rule: at its next Take after the next publish (O3).
- Adding a graphic to a production (`addGraphicToShow`) stamps `designAt`. Adding again a graphic
  the production already holds from the same library record is an Update by another door and
  follows the same rules, dropped-field question included.

## 3. The send-time settle (E3, and the safety rule)

Every send of a production record by the new build goes through one settle first: a team save
(`pushSave`, including a save re-merged after a compare-and-swap refusal and a restored pending
edit), a move to a team (`teamProductions.ts:702`), a personal sync push, a publish, and an
export (show export, graphics pack, community pack). The settle compares the record with a
**base**, the server's copy of the same production:

- team: the pending edit's `base`, or for a save refused by compare-and-swap, the stored document
  it is merged onto (both already in hand);
- personal: the server's record, read with `get` before the push, only for a record holding an
  unstamped copy (after adoption, almost none). The sync engine lives in `backend/`, which may
  import only the kernel (`docs/ARCHITECTURE.md` section 3), so the sync controller gains one
  registration point (a pre-push step for kind `show`), and the app registers the settle there at
  start; with no step registered, a record holding an unstamped copy is not pushed.
- publish and export: the same base as the record's kind.

**The rule, per copy of the record whose id the base also holds:** if the copy is unstamped and
its design members differ from the base's, it takes the base's design members, all four
together. Nothing else changes. This is what drops a design an old page pulled from the library,
whether it pulled it with a publish (`refreshGraphicCopies`) or by adding a held graphic again
(which keeps the id). It does not depend on whether the base copy is stamped. One old-page design
edit is kept: Connect data's own-reader removal, recognised exactly (the template equals the
base's except its script, and that script is `stripLiveData` of the base's script); it is stamped,
so the reader the operator removed stays removed. A stamped copy is a new build's own design
change (Update, add, removal) and is kept. A copy the base does not hold (a graphic the old or new
page added) is kept as it is.

The settle is a local authoring write with a new `updatedAt`, before the send and never an undo
step, so this device's store, its monitors and what is sent agree. It writes only when a copy
changes. When the base cannot be read, the record waits and is not sent; the page shows the copy
as stored meanwhile, and an export offline exports the copies as stored, which is what this
browser's monitors show.

**A personal conflict.** When the sync engine finds the server's record changed meanwhile, the
new build settles the losing local record against that server record before it makes the
"(conflicted copy)" (`sync.ts:195-200`, `makeConflictCopy` at `:485`), so the copy never carries a
pulled design. A conflicted copy an old build made before reload has a new production id and no
source pointer, and duplicated productions share graphic ids (`shows.ts:756-776`), so no base is
looked up for it: it is a never-published production holding what that old device held, and
adoption (section 5) gives it the library's current designs when this browser holds them.

**Then the edit merges as usual for its kind.** Team: the three-way merge
(`src/model/teamShowMerge.ts`) with one change: the rule runs twice per graphic item, once over
its design members and once over its placement ("whichever side left it as in base takes the
other's; both changed differently, theirs stands"). Today it takes the item whole
(`teamShowMerge.ts:100-106`), so a stamp or an Update on one side would beat a layer or
adjustment edit on the other; split, both survive. Cues, folders, lists and the rest of the record
merge exactly as today. Personal: last-write-wins, or a "(conflicted copy)" when the server's
record changed meanwhile, as today; a retained edit to a production another device has since
adopted therefore usually comes back as a conflicted copy, the existing personal rule.

**Retained edits (E3).** An edit an old page made and could not store is retained on its device:
a team pending edit in its outbox (`base` and `local`, `src/model/teamOutbox.ts`, restored at
`teamProductions.ts:486-495`), or a personal record pending push. Reloaded under the new build, it
is sent through the paths above, so it is settled first and merged as usual: its cue edits and
placement edits stay, its pulled designs are dropped, and it passes the guard with the mark.

**The owed cue edit (phase 3).** A page-hide record (`src/model/owedCueEdit.ts`) holds a cue id and
texts: label, note and values. The new build applies it as before (P2: through the history, only
when the cue still holds one of the recorded texts, so a teammate's newer text stands). It never
writes a design and never stamps: an old page's pulled design in the same record stays unstamped
and is settled before the record is sent. Applied under the new build, the write carries the mark
and passes the guard, which is right: E3 keeps an old page's cue edits. A record the new page
cannot apply is dropped exactly as P2 says today. Its format does not change. If adoption (a write
outside the history) lands right after a recovered edit, that edit's Undo is refused with the
history's existing "Undo history was cleared" note; no edit is lost.

## 4. How each write identifies its build, and the guard (G1 points 1 and 2)

**Identification.** The build mark header. A header cannot be echoed back by an old build from
stored data, unlike a body field (old builds keep unknown record fields: `readShape` in
`src/model/shows.ts:641` spreads them), it rides every route alike (table writes, the
`team_production_save` RPC, deletes), and PostgREST exposes it to the database as
`current_setting('request.headers', true)`. It is added only to requests for the REST API
(`/rest/v1/`), in the client's existing `answeredFetch` wrapper (`src/backend/supabase.ts:50`), so
auth, storage uploads and Realtime are sent exactly as today. supabase-js already sends its own
non-standard headers to that API (`apikey`, `x-client-info`), so those requests are already
preflighted; the new name only joins the list a preflight asks for. Section 6 checks the gateway
allows it before the release.

A read-only function, `production_copies_state()`, answers two booleans and nothing else: whether
the calling request carries the mark, and whether the switch is on. The rollout uses the first;
new pages use the second to know when adoption may run.

**The guard.** One migration adds a `before` row trigger on each table that holds production
authoring, and changes nothing else. All three call one `security definer` function with
`set search_path = ''`, so it reads `system_settings` (RLS on, service role only) whatever role the
request has; it is granted to no client role.

| Table | Fires on | Production-authoring because |
|---|---|---|
| `documents` | insert, update of `body` or `deleted`, delete; acts only where the row's `kind = 'show'`, and passes a delete of a row that is already a tombstone (`old.deleted`) | personal sync of a production (`supabaseProvider.ts:148`) |
| `team_productions` | insert, update of `doc`, delete (including the cascade when a whole team is deleted, `0054:84`) | team save RPC (`teamProductions.ts:262`), move to a team, team production delete, team delete |
| `control_shows` | insert, delete, update of `output`, `panel`, `title`, `profile`; update of `bindings`, `sources` or `collections` unless the only change is sources' `paused` members | publish (`hostedControl.ts:971-994`), unpublish (`:1088`), Connect and Disconnect of a data source (`writePublishedSources`, `:785-788`) |

The trigger refuses the write with `raise exception 'Reload this page to edit'` (SQLSTATE `P0001`)
when all of these hold: the switch is on; the statement comes from an API request
(`request.headers` is set, so a migration's own self-check, which sets claims but no headers, is
never refused); the request's JWT role is `authenticated`; and the request carries no build mark.
Otherwise it passes the row through unchanged. So:

- **Not production authoring, never refused:** documents of every other kind; the tombstone purge
  (`supabaseProvider.ts:166-176`, one statement across kinds, which a refused show row would
  otherwise stop for every kind); every `control_shows` write naming none of those columns (live
  cue, audience state, slugs, heartbeats, the team stamp); a data source's Pause or Resume; every
  command, report, heartbeat and data write (`control_events`, `control_heads`, the `control_*`
  RPCs); and every server-side writer (agent deliveries, sweeps, service role).
- **Pause passes, Connect does not.** A source's Pause and Resume are live controls ("the tick
  honours a Pause with the page closed"), so an old page still plays out with them (S2), and
  refusing them mid-show is the risk O12 rules out. They write the same columns as Connect and
  Disconnect, but only a source's `paused` member changes (`Show` sources, `shows.ts:293,309,323,
  344,376`). The trigger compares old and new `sources` with every `paused` member removed, and
  `bindings` and `collections` as they are: equal, the write passes; different, it is authoring
  and is refused like a save. So an old page changes nothing stored after the switch but a
  source's paused state.
- `P0001` is deliberate: an old personal sync marks `42501` and RLS words as a permanent denial
  (`supabaseProvider.ts:153`), and a refusal must not be read that way. A refused put stays
  pending on its device (`sync.ts:446-449`), so nothing the old page did is lost.
- On `control_shows` the trigger fires only for publish-shaped and source writes, never for a
  Take, so the Take path is unchanged and no lock a Take waits on is added.
- What an old page shows is its own build's failure text, which carries the server's words:
  personal sync's error detail, the team save note, "Publish failed: Reload this page to edit",
  and Connect data's "has not reached the server" note. Section 8 checks these on the real old
  bundle. Its Takes, Outs, value Updates, data patches, reports and heartbeats keep working: it
  only plays out (S2). Its own "unpublished changes" reading may show for a production a new
  page changed; pressing Publish there is refused like any old publish.

The migration is live-path (a trigger on `control_shows`), so it has the live-path header and the
timeouts, applies only in a quiet window (`supabase/AGENTS.md`), and is additive (new functions
and triggers; no column, signature, grant or policy of an existing object changes). Its
self-check calls each route as `authenticated` and as service role, with the switch on and off,
the mark present and absent, and `request.headers` set and unset, inside a block a sentinel rolls
back, so the switch is never left on. A database test on the local stack proves `request.headers`
and the role are visible to the trigger inside `team_production_save`.

## 5. Adoption (O5), after the switch

Adoption stamps every unstamped copy once and settles its design to "what is published now", or
for a never-published production "the library's current design". It runs only once the switch is
on, as `production_copies_state()` reports it, so no old page can save beside it: an old page's
whole-item team merge and its record digest, which would read a stamp as a change, never meet an
adopted record while that page can still write. Until then new pages read copies only and stamp
only their own design writes; when the switch state cannot be read, adoption waits. Safety does
not depend on adoption: the settle of section 3 protects every send without it. Adoption is
what makes O5 true and lets later sends skip the base read.

- **When.** On the production page, once the page has the record, the account may write, the
  switch is on, and, for a published production, the published stamp (`output->ver`, read as one
  field as `publishControlShow` does) has been read or found unreadable.
- **Published or not** is the record's `hostedSlug`, never whether this account can read the
  published row (a teammate cannot when the row lacks the team's id,
  `teamProductions.ts:727-730`).
- **The rule, per unstamped copy.** Candidates in order: the copy, the base's copy, the library
  record (by `graphicId`), each taken whole (design members together).
  - Published, stamp readable, graphic named in it: the first candidate whose digest equals the
    stamp's `g[name]` (the digest `libraryGraphicDigests` computes, with the candidate's template
    in place), else whose edit time equals `t[name]`, settled with `savedAt = designAt =` the later
    of its own time and `t[name]`, so G3 never reads a design on air as older than air. Where the
    digest cannot equal the stamp (a graphic with sounds, whose assets a publish rewrites,
    `hostedControl.ts:589`) the edit time decides; a Node test against `stampPayload` output
    covers both.
  - Published, and nothing matches, the graphic is not named (renamed or added since), or the
    stamp is unreadable: the copy, stamped with its own time. A published production never takes
    a library design at adoption.
  - Never published: the library record's current design when this browser holds it, otherwise
    the copy.
- **How it is stored.** One authoring write of design members only, with a new `updatedAt`,
  through the normal paths (so it is settled and merged like any send), never an undo step.
  Nothing is written when every copy is stamped.
- **Who adopts decides.** The first page to adopt settles from what its browser holds; a member
  without a graphic's library record settles it to the copy, and the record's owner later sees
  "Newer design in library" and can Update. Nothing reaches air from that.
- **Two pages adopting at once.** Team: compare-and-swap refuses one, the split merge keeps the
  other's design members, both end stamped. Personal: two devices adopting one production at the
  same moment produce a "(conflicted copy)" as any two concurrent edits do; nothing is lost and
  the copy carries no slugs.
- **On a just-opened page,** adoption can change a monitor's design once. Outputs are not
  affected: they play the published payload.

## 6. Order: server guard, app release, switch, adoption (G1 point 3)

1. **The migration lands and is applied** (quiet window). The switch is off: every write passes as
   before; the guard is inert. Before the app's pull request lands, the gateway is shown to allow
   the header: a CORS preflight (an `OPTIONS` request naming `x-noacg-production-copies` among
   the headers asked for, no data, no key) to the production REST address answers with it
   allowed, and the configured spec shows a browser's marked request reaching the local stack's
   database. If either fails, the app does not land.
2. **The new app is released.** New pages send the mark, read only copies, show the mark and
   Update, stamp their own design writes and settle every send. They adopt nothing yet. Old pages
   still write as today, so in this window an old page's publish can still pull a library design
   into a stored copy and onto air, and an old page's whole-item team merge can still lose a
   placement edit to a teammate's Update of the same graphic: today's behaviour, not a
   regression, and the window is kept short.
3. **The switch is turned on** as soon as the release is confirmed live: a new-build page on
   production, signed in, calls `production_copies_state()` and it reports the mark (the header
   reaches the database through the gateway); then the row is written (service role). If the mark
   is not reported, the switch stays off and nothing else changes. From then on every old page's
   production save, sync, publish, Connect and delete is refused with "Reload this page to edit"
   and changes nothing stored. The owner, or the coordinator with the owner's permission, does
   it; this run never writes production settings itself.
4. **Adoption runs** as new pages open productions, now that no old page can save.

Back out at any step: turn the switch off (instant, no deploy; adoption then pauses for pages that
read it again); revert the app (old builds ignore `designAt`; their record digest reads a stamped
production as changed, which a publish clears); the inert triggers can stay, or a later migration
drops them.

## 7. Rules

Observable lines; the build PR repeats them under **Rules** and tests them.

- R1. Every read of a pool graphic's design reads its copy (section 1's table); no library edit,
  break or delete changes a monitor, a publish's payload, panel or gate, or an output.
- R2. A copy with a newer, different library design shows "Newer design in library" and Update.
  Update takes that design, keeps the copy's id, pool name, layer, position, sounds, adjustments
  and link, touches no cue, and asks first when it drops a field a cue uses or a binding names.
- R3. Every copy the new build sets the design of has `designAt === savedAt`; every other write
  leaves `designAt` alone.
- R4. Every send of a production record (team save, move to a team, personal push, publish,
  export) first gives each unstamped copy whose design members differ from the base's same copy
  the base's design members, except an exact own-reader removal; stamped copies and copies the
  base lacks are kept; with no readable base the record waits.
- R5. With the switch on, an API request from a signed-in client without the build mark to a
  production-authoring route (section 4's table) is refused with "Reload this page to edit" and
  stores nothing; with the mark, with the switch off, outside an API request, or from the
  server's own roles, it passes unchanged.
- R6. Writes that are not production authoring (other document kinds, a tombstone purge,
  commands, reports, heartbeats, data, live cue, audience, slugs, a source's Pause or Resume) are
  never refused by the guard.
- R7. The team merge runs its three-way rule separately over a graphic's design members and its
  placement; a retained old-page edit, reopened under the new build, keeps its cue and placement
  edits merged as its kind merges, and loses only the designs R4 drops.
- R8. A recovered owed cue edit writes cue text only, as P2 says, and never stamps or changes a
  copy.
- R9. The guard is applied before the app; the switch is turned on only after the app is live and
  `production_copies_state()` has reported the mark on production; turning it off restores
  today's behaviour for old pages at once.
- R10. Adoption runs only while the switch reads on, writes design members only, once per copy:
  published (by `hostedSlug`) and matched in a readable stamp, the matching candidate timed at the
  later of its own time and the stamp's; published otherwise, the copy; never published, the
  library record's current design if held, otherwise the copy.
- R11. Stamping or adopting a copy whose design is unchanged never makes a production read as
  changed since its publish; the record digest covers every copy's template and leaves out
  `savedAt` and `designAt`.
- R12. A publish still records stopped Sheet readers in `ownReaderStops` in the write before it,
  and the own-reader removal always edits the copy.
- R13. The header is sent on REST API requests only, and the gateway's preflight is shown to allow
  it before the app lands.

## 8. How AC-2 is tested

- **Node tests** (`scripts/`, importing `src`): the payload and panel built from a production
  whose library record was edited, broken or deleted are unchanged, and no design read in section
  1 reaches the library (R1); Update's keeps and its dropped-field question (R2); stamps on every
  design write and none elsewhere (R3); the settle against a team base, a personal server record
  and a conflict, an unstamped base copy, a re-added held graphic, the own-reader removal, and an
  owed edit beside a pulled design (R4, R8); the split team merge with a retained layer and
  adjustment edit against an adopted record, and a live layer edit racing an adoption (R7);
  adoption against `stampPayload` output including a graphic with sounds and the look's face, a
  renamed graphic, an unreadable stamp, never published, and the settle time (R10); the record
  digest unchanged by stamping and adoption (R11); a publish recording a stopped reader, and the
  removal on a published graphic with no library record (R12). The settle and merge are checked
  against a small reference model written from these rules, not a copy of the production code.
- **Database test on the local stack** and the migration's self-check: R5 and R6 per table and
  route, the Pause comparison, with the switch on and off, the mark present and absent, inside and
  outside an API request, signed-in and service role, and inside `team_production_save`.
- **Configured spec with an old-build page.** An old build is the new page with its mark removed
  on the wire (Playwright `route` drops the header); the switch is turned on in the isolated stack
  through the service role. It saves, syncs (personal), saves (team), publishes and connects a
  source: each is refused with "Reload this page to edit" and the stored rows are unchanged; its
  Take, report, heartbeat and a source Pause still work. Reopened with the mark, its retained cue
  and layer edits merge and a design seeded as pulled from the library is dropped. Editing and
  breaking the library graphic changes nothing on the monitors, in the published row or on an
  output page, and the graphic shows "Newer design in library"; Update keeps cues, values,
  adjustments, link and position and names a dropped field first; the production does not read

## 9. Limits

- An old page in another tab of the same browser writes the shared local store directly. With no
  account no server can refuse it; signed in, the new tab's sync pushes its local edits with the
  mark. Either way they are settled before any send, as a retained edit is.
- In section 6's window an old page behaves as today (step 2).
- A published design that no candidate on the adopting device matches is not recoverable from the
  payload (it holds built code, not the template); the copy is kept, and G3 refuses a publish that
  would put an older design on air, with section 1's note.
- A "(conflicted copy)" an old build made keeps what that device held, as a never-published
  production (section 3).
- An old page whose save is refused retries its push as its build does (the whole record each
  pass) until it is reloaded.

No behaviour choice the owner has not made was needed. "Reload this page to edit" and "Newer
design in library" are the spec's words; the dropped-field question follows AC-2; letting a data
source's Pause through while refusing its Connect follows S2 (an old page still plays out, its
saves are refused) and O12; dropping a re-added design and keeping an exact own-reader removal
follow E3 (only designs pulled from the library are dropped). The owner should know one existing
rule will show more often: a retained personal edit to a production another device has since
adopted comes back as a "(conflicted copy)".
