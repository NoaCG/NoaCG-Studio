# G1: The production's copy is the only truth; old pages only play out

Design gate for phase 4 (W2, O4, O5, S2, E3, AC-2) of `../spec.md`. It covers the four points the
spec lists for G1: how each write identifies its build, a guard on every production-authoring
route only, the order of server guard, adoption and app release, and E3's handling of retained
edits. It also says how the phase 3 owed cue edit meets E3 and the guard. Written against `main`
at 0e65d859. Nothing here is built yet; the build is the next pull request.

## Terms

- **Copy.** A production's own `SavedGraphic` (`src/model/packets.ts:39`): `template`, `savedAt`,
  layer, sounds, adjustments, `graphicId`. Stored inside the production record (personal:
  `documents` row of kind `show`; team: `team_productions.doc`).
- **Library record.** The `GraphicDoc` a copy came from (`graphicId`), edited in the editor.
- **Today.** Every reader resolves the library record first and falls back to the copy
  (`templateForSavedGraphic`, `src/model/library.ts:467`; `designEditedAt`, `:474`), and a
  publish copies newer library designs into the record before it writes
  (`refreshGraphicCopies`, `src/model/shows.ts:1010`, called from
  `src/components/home/useProductionPublish.ts:432`).
- **Old build.** Any page loaded from a bundle before this phase's build. **New build.** This
  phase's bundle and later.
- **Design stamp.** A new optional member of `SavedGraphic`, `designAt` (ISO), which the new build
  sets equal to `savedAt` whenever it sets that copy's design. A copy is **settled** when
  `designAt === savedAt`. An old build never writes `designAt`: its design writes
  (`refreshGraphicCopies`, `addGraphicToShow`, `setGraphicCopyScript`) either change `savedAt` and
  leave `designAt` as it was, or build a fresh object without it. So an unsettled copy is one whose
  design an old build set, or one no new build has looked at yet. The stamp is per copy, so a later
  new-build write elsewhere in the record (a cue edit, an owed edit recovered) never makes an old
  build's design look settled.
- **Build mark.** A request header, `x-noacg-production-copies: 1`, that the new build's Supabase
  client sends on every request (`createClient(..., { global: { headers } })`,
  `src/backend/supabase.ts:109`). Old builds send none.
- **The switch.** A row of `system_settings` (migration 0019), key `production_copies`, value
  `{"on": true}`. Absent or anything else means off.

## 1. One source for what plays (O4)

- `templateForSavedGraphic(g, library)` returns the copy, `withProductionSounds(g.template,
  g.soundConfig)`, and no longer reads the library. `designEditedAt(g, library)` returns
  `g.savedAt`. Both keep their signatures, so every reader moves at once: the payload and panel
  (`src/control/hostedControl.ts:362,471,574,583`), the monitors, measuring, clocks and fields on
  the production page (`ProductionPage.tsx`, 24 sites), the publish gate
  (`src/validation/productionGate.ts:47`), show export, packs, `SourcesLine`, export appearances
  and `useRundownAuthoring`. The two sites that read `resolveSavedGraphicDoc(...)?.template`
  directly (`ProductionPage.tsx:4556,4562`, the sound editor) read the copy too.
- Therefore a library edit, or a library record that is broken or deleted, changes nothing on the
  monitors, in a publish (payload, panel, gate) or on an output. `libraryGraphicDigests` becomes
  the copy's digests, so `usePublishDrift` no longer reports a library edit as a change to
  publish.
- Not design, unchanged: a graphic's saved **entries** stay read from its library record
  (`entriesForSavedGraphic`). They are named value sets for the control panel, never played by an
  output, and this phase does not move them.
- Connect data's own-reader removal (`ProductionPage.tsx:3065`) already writes the copy through
  `setGraphicCopyScript`; it keeps doing so, and also stamps `designAt`. Its library edit stays as
  it is (it fixes the library record for other productions).
- The G3 guard of the publish guard (`olderDesigns`, `hostedControl.ts:621-628`) stays: it now
  compares copies' `savedAt` with the published edit times, which is what it should guard.

## 2. Newer design in library, and Update (O4)

- **The mark.** A copy with a `graphicId` whose library record this browser holds, whose record
  `updatedAt` is later than the copy's `savedAt`, and whose template differs from the copy's (by
  the same digest a publish would compute) shows "Newer design in library" in the cue editor's
  graphic section, beside the playout layer (`CueEditor.tsx:1723`), with an **Update** button.
  Copies matched by name only never show it.
- **Update** replaces the copy's `template` with the library record's, setting `savedAt` to the
  record's `updatedAt` and `designAt` to the same. It keeps the copy's id, pool name (the
  template's `name` is set to the pool name, since outputs key graphics by it), layer, position in
  the pool, sounds, adjustments and `graphicId`. Cues are not touched: their values, typed data,
  selections, shortcuts and bindings stay as they are.
- **A dropped field is named first.** When the copy has a field the new design lacks and a cue of
  this graphic holds a value for it or a binding names it, Update first says
  "Update drops <field label> from <n> cues." with Update and Cancel. Confirmed, the values stay in
  the cues (harmless, and they come back if a later design restores the field); only the field
  stops showing.
- Update runs the production gate on the new design first (`assertProductionGate`), and a design
  the gate refuses is not taken: the note says why and the copy stays.
- Update is an authoring write like any other: on a team production it goes through the team save
  and its merge; it is one undo step. It publishes nothing by itself (automatic updates are phase
  6). On air, the new design follows the existing rule: at its next Take after the next publish
  (O3).
- Adding a graphic to a production (`addGraphicToShow`) stamps `designAt`. Adding again a graphic
  the production already holds from the same library record is an Update by another door and
  follows the same rules, dropped-field question included.

## 3. Adoption (O5)

Adoption settles every unsettled copy once, per copy, by the rule in section 5. It is what turns
"a production's copies become what is published now; a production never published takes the
library's current design once" into stored designs.

- **When.** On the production page, once the page has the production record and the account may
  write, and, for a published production, once the published stamp (`output->ver`, read as one
  field as `publishControlShow` does) has been read. Also, wherever the page is, before a publish,
  a team save or a personal sync push sends a record holding an unsettled copy: that send settles
  it first (section 5, which reads the server's copy and the stamp). A new-build write elsewhere
  (Home "+ Production") stamps only the copy it writes; the save that carries it settles the rest.
  So every production is settled by the first new-build send of it, opened or not.
- **How it is stored.** One authoring write of the copies it changes, through the normal paths
  (personal store and sync, team save with its compare-and-swap). A copy whose design is already
  the right one still gets its stamp. Nothing is written when every copy is settled.
- **Published production.** For each graphic named in the published stamp, the design whose
  digest equals the stamp's `g[name]` is taken, from the candidates in order: the record's copy,
  the base copy (section 5), the library record. If none matches, the one whose edit time equals
  the stamp's `t[name]`; if none, the copy is kept. The copy kept in that last case may be older
  than what is on air; then a later publish is refused by G3 with its existing note, as today.
  A graphic added after the last publish is not in the stamp and is treated as unpublished.
- **Unpublished production, or a graphic not in the stamp.** The library record's current design
  when this browser holds the record (by `graphicId`), otherwise the copy.
- **Two pages adopting at once.** Team: the compare-and-swap refuses one, its merge keeps the
  other's copies (same item changed on both sides: theirs stands), and both end settled. Personal:
  two devices of one account adopting one production at the same moment produce a "(conflicted
  copy)" as any two concurrent edits do today (`src/backend/sync.ts:195-200`); the conflicted copy
  is unpublished and settles by the unpublished rule. Nothing reaches air from it (conflict copies
  carry no slugs).
- **Before adoption on a just-opened page,** the monitors show the record's copies; adoption can
  change a monitor's design once, right after opening. Outputs are not affected: they play the
  published payload.

## 4. How each write identifies its build, and the guard (G1 points 1 and 2)

**Identification.** The build mark header. A header cannot be echoed back by an old build from
stored data, unlike a body field (old builds keep unknown record fields, `readShape` in
`src/model/shows.ts:641` spreads them), it rides every route alike (table writes, the
`team_production_save` RPC, deletes), and PostgREST exposes it to the database as
`current_setting('request.headers', true)`. Old builds send none.

**The guard.** One migration adds a `before` row trigger on each table that holds production
authoring, and changes nothing else:

| Table | Fires on | Production-authoring because |
|---|---|---|
| `documents` | insert, update of `body`, delete, only where the row's `kind = 'show'` | personal sync of a production (`supabaseProvider.ts:148`) |
| `team_productions` | insert, update of `doc`, delete | team save RPC (`teamProductions.ts:262`), move to a team, team delete |
| `control_shows` | insert, delete, update of `output`, `panel`, `title`, `bindings`, `sources`, `collections`, `profile` | publish (`hostedControl.ts:971-994`), published sources (`:788`), unpublish |

The trigger refuses the write with `raise exception 'Reload this page to edit'` (SQLSTATE
`P0001`) when all of these hold: the switch is on; the request comes from a signed-in client
(the request's JWT role is `authenticated`); and the request carries no build mark. Otherwise it passes the
row through unchanged. So:

- Untouched: documents of every other kind; every `control_shows` write naming none of those
  columns (live cue, audience state, slugs, heartbeats, the team stamp); every command, report,
  heartbeat and data write (`control_events`, `control_heads`, the `control_*` RPCs, which write
  other tables or columns); and every server-side writer (agent deliveries, sweeps, service role).
- `P0001` is deliberate: an old personal sync marks `42501` and RLS words as a permanent denial
  (`supabaseProvider.ts:153`), and a refusal must not be read that way. A refused put stays
  pending on its device (`sync.ts:446-449`), so nothing the old page did is lost.
- The trigger reads one `system_settings` row and one setting. On `control_shows` it fires only
  for publish-shaped writes, never for a Take, so the Take path is unchanged. A publish still
  takes no lock a Take waits on beyond what it takes today.
- What an old page then shows is its own build's failure text, which carries the server's words:
  personal sync's error detail, the team save note, and "Publish failed: Reload this page to edit".
  Its Takes, Outs, Updates of on-air values, data patches, reports and heartbeats are other routes
  and keep working: it only plays out (S2).

The migration is live-path (a trigger on `control_shows`), so it has the live-path header, the
timeouts, applies only in a quiet window (`supabase/AGENTS.md`), is additive (new functions and
triggers, no column, signature or policy change), and its self-check calls each trigger with the
switch on and off, with and without the mark, as a signed-in role and as service role.

## 5. Retained edits under the new build (E3)

An edit made by an old page and not yet stored on the server is retained on its device: a team
production's pending edit in its outbox (`base` and `local`, `src/model/teamOutbox.ts`,
restored at `teamProductions.ts:486-495`), and a personal production's record pending push in
the local store. When the page reloads under the new build, the edit goes up through the new
build's write paths, with the mark, so the guard passes it. Before it does, every unsettled copy
in it is settled:

1. **The base holds that graphic settled** (same id, `designAt === savedAt`): the copy takes the
   base's design. This is what drops a design the old page pulled from the library. The base is
   the team edit's `base`, or, for a team save refused by compare-and-swap, the stored document it
   is merged onto; for a personal record, the server's copy, read with `get` before the push.
2. **Otherwise** the adoption rule of section 3, with the base's copy as a candidate.
3. The copy is stamped.

Then the edit merges as usual for its kind: a team edit by the three-way merge
(`src/model/teamShowMerge.ts`), where a settled copy equal to the base leaves the teammate's side
standing; a personal record by the sync engine's last-write-wins, or a "(conflicted copy)" when
the server's record changed meanwhile. Cue edits, added or removed cues and graphics, folders and
the rest of the record are kept exactly as that merge keeps them today. A graphic the old page
added has no settled base and keeps its own design (it was an explicit add). A personal record
whose server copy cannot be read yet is not pushed until it can; meanwhile the page shows the
copy as stored, and publishing settles it first, which needs the server too.

**The owed cue edit (phase 3).** A page-hide record (`src/model/owedCueEdit.ts`) holds a cue id
and texts: label, note and values. The new build applies it as before (P2: through the history,
only when the cue still holds one of the recorded texts, so a teammate's newer text stands). It
never writes a design: it cannot set a copy's template, `savedAt` or `designAt`, so an old page's
pulled design in the same record stays unsettled and is settled by the rules above, before the
record is published, saved to the team or pushed. Applied under the new build, the write carries
the mark and is admitted by the guard, which is right: E3 keeps an old page's cue edits. A record
written by an old page that a new page cannot apply (the cue changed) is dropped exactly as P2
says today. Nothing in the record's format changes.

## 6. Order: server guard, app release, adoption, switch (G1 point 3)

1. **The migration lands and is applied** (quiet window). The switch is off, so every write
   passes as before; the guard is inert. Applied before the app that sends the mark, as the run
   requires, although the new app does not depend on it.
2. **The new app is released.** New pages send the mark, resolve only copies, show the mark and
   Update, and adopt each production the first time a new page opens it or writes its copies.
   Old pages still write as today. A design an old page pulls into a record in this window is
   unsettled (its stamp no longer matches) and is settled by section 5 the next time a new page
   meets it, so the window's length is not a safety question.
3. **The switch is turned on**, a separate step after the release is live (one row in
   `system_settings`, service role). From then on, every old page's production save, sync,
   publish and delete is refused with "Reload this page to edit", and changes nothing stored.
   The owner or the coordinator does it with the owner's permission; this run never writes
   production settings itself.

Back out at any step: turn the switch off (instant, no deploy); revert the app (old builds ignore
`designAt`; the stamps they leave are harmless); the inert triggers can stay or a later migration
drops them.

## 7. Rules

Observable lines; the build PR repeats them under **Rules** and tests them.

- R1. Every reader of a pool graphic's design reads its copy; no library edit, break or delete
  changes a monitor, a publish's payload, panel or gate, or an output.
- R2. A copy with a newer, different library design shows "Newer design in library" and Update.
  Update takes that design, keeps the copy's id, pool name, layer, position, sounds, adjustments
  and link, touches no cue, and asks first when it drops a field a cue uses or a binding names.
- R3. Every copy the new build sets the design of has `designAt === savedAt`; every other write
  leaves `designAt` alone.
- R4. Adoption settles each unsettled copy once: published and named in the stamp, the candidate
  whose digest (then edit time) matches what is published; otherwise the library record's current
  design if held; otherwise the copy.
- R5. With the switch on, a signed-in write without the build mark to a production-authoring
  route (section 4's table) is refused with "Reload this page to edit" and stores nothing; with
  the mark, or with the switch off, or from the server's own roles, it passes unchanged.
- R6. Writes that are not production authoring (other document kinds, commands, reports,
  heartbeats, data, live cue, audience, slugs) are never refused by the guard.
- R7. A retained old-page edit, reopened under the new build, keeps its cue edits merged as its
  kind merges today, and every copy it holds whose base holds that graphic settled takes the
  base's design.
- R8. A recovered owed cue edit writes cue text only, as P2 says, and never settles or changes a
  copy.
- R9. The guard is installed and applied before the app; the switch is turned on only after the
  app is live; turning it off restores today's behaviour for old pages at once.

## 8. How AC-2 is tested

- **Node tests** (`scripts/`, importing `src`): the payload and panel built from a production
  whose library record was edited, broken or deleted are unchanged (R1); Update's keeps and its
  dropped-field question (R2); stamps on every design write and none elsewhere (R3); adoption
  candidates against a stamp, digest then edit time then copy, published and unpublished (R4); the
  E3 settle against a base, team merge with a teammate's edit, and an owed edit beside an
  unsettled copy (R7, R8). The settle is checked against a small reference model written from
  these rules, not a copy of the production code.
- **Migration self-check**, and a database test on the local stack: R5 and R6 per table, with the
  switch on and off, the mark present and absent, signed-in and service role.
- **Configured spec with an old-build page**: an old build is the new page with its mark removed
  on the wire (Playwright `route` drops the header), the switch turned on in the isolated stack
  through the service role. It saves, syncs (personal), saves (team) and publishes: each is
  refused with "Reload this page to edit" and the stored rows are unchanged; its Take, report and
  heartbeat still work. Reopened with the mark, its retained cue edit merges and a design seeded
  as pulled from the library (an unsettled copy in its retained edit) is dropped. Editing and
  breaking the library graphic changes nothing on the monitors, in the published row or on an
  output page, and the graphic shows "Newer design in library"; Update keeps cues, values,
  adjustments, link and position and names a dropped field first.
- **Save paths under reload** (lesson from phase 3): for adoption, Update and a retained edit,
  the save is delayed on purpose and the page reloaded at once, with a mouse press and with a
  touch press; nothing is lost and no copy is left half settled.
- **Not checked by the run**, for the owner's final check: none in this phase (no hardware path
  changes).

## 9. Limits

- An old page in another tab of the same browser with no account writes the shared local store
  directly; no server can refuse it. Its only design writes are explicit (adding a graphic again,
  Connect data), which the new build settles as section 5 says, keeping an explicit add.
- A published design that no candidate on the adopting device matches is not recoverable from the
  payload (it holds built code, not the template); the copy is kept and G3 refuses a publish that
  would put an older design on air, as today.
- An old page whose save is refused retries its push as its build does (the whole record each
  pass) until it is reloaded.

No behaviour choice the owner has not made was needed: the words "Reload this page to edit" and
"Newer design in library" are the spec's; the dropped-field question follows AC-2.
