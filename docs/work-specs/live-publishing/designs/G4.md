# G4: Only what changed, each image once

Design gate for phase 7 (W5, O9, AC-5) of `../spec.md`. It covers every point the spec lists for
G4: revision-checked patches and partial reads; what happens when a requested revision has been
replaced; content-named image storage with older outputs still reading inline images; and old and
new clients writing at once. Written against `main` at b1e06209, on top of phase 4 (G1, the
production's copy is the only truth), phase 5 (G2, run reports) and phase 6 (G3, the saved revision
`rev`, the publication guard, automatic updates, outputs that check the stamp themselves). Nothing
here is built yet; the build is the next pull request.

## Today (phase 2 and phase 6 evidence)

- **A save sends the whole record.** Personal: `supabaseProvider.put` upserts the whole body and
  asks for the whole body back to confirm it (`select('body')`), 6.94 MB up and 6.94 MB down per
  cue edit on the large fixture. Team: `team_production_save` takes the whole document. Images and
  fonts already leave the record body for Storage under content-hash keys (`externalizeAssets`,
  `externalizeSharedAssets`), but each page load uploads every image it externalizes again once
  (`upsert: true`, deduplicated per session only).
- **A publish sends the whole payload.** `publishRevision` writes `output` (every graphic with its
  images inline as data URLs) and `panel` in one `PATCH`: 20 MB up on the large fixture, about
  32.8 MB with the panel and the request around it.
- **An output reads the whole copy.** `control_output_resolve` answers the whole `output`, 20.2 MB on
  the large fixture, for every new version, even when only a cue's text changed. Phase 6 measured
  the result: on the large fixture, publishing each cue edit adds about 334 ms p95 to press to ran,
  the output re-reading each whole copy; and D1's Take of a brand-new graphic takes 30 to 33 s
  throttled (20 Mbit/s), most of it moving 20 MB twice.

## Terms

- **Document.** One of the stored JSON values this phase sends in parts: a personal production
  record (`documents.body`, kind `show`), a team production record (`team_productions.doc`), a
  publication's **head** (section 4) and its `panel`.
- **Unit.** The piece of a document that is sent or skipped whole. Every top-level member of a
  document is one unit, except a **keyed list**: a top-level array with at least one element, whose
  elements are all objects carrying the same unique string identity, `id`, else `key`, else `name`
  (the first of those every element has, distinct across the array). Each element of a keyed list
  is its own unit, and the list's order is one more small unit (its identities in order). An empty
  array, or one that is not keyed, is a single unit. So a production record's `graphics` and `cues`
  are keyed by `id`, a head's graphic references by `key`, the panel by `name`; `name`, `look` or
  `outputSetup` are single units.
- **Unit digest.** The first 128 bits of SHA-256 over the unit's canonical JSON (keys sorted, values
  as `JSON.stringify` writes them), hex. Two equal digests mean equal content. A digest is only ever
  compared with another made by the same function, so the order in which the database keeps object
  keys cannot matter.
- **Unit map.** For one stored document: its format (`f: 1`), every unit's digest, each keyed list's
  order, and the stored `rev` (records) or `n` (head and panel) it describes. Kept on the server
  beside the document, written only by the server from the operations it applied (section 1). A
  map of another format is no base: a later build that names units differently never trusts an
  older map.
- **Patch.** A list of operations on units, sent with the revision it was built against (its
  **base**). Operations: set a member, drop a member; for a keyed list: put elements (each with its
  digest), delete identities, the new order when it changed, and the list's final length.
- **Part.** One graphic of a publication, its images replaced by references, stored once under the
  digest of its own whole body (section 4).
- **Content name.** The SHA-256 of an image's data URL text (its UTF-8 bytes), written as 64
  lowercase hex characters: the name an image is stored and read under for outputs (section 3). The
  page computes it with Web Crypto and the server with pgcrypto's `digest`, over the same bytes.
- **New and old.** A page or output built with this phase, or before it. Old pages are the phase 6
  build and earlier; old outputs read `control_output_resolve` only.

## 1. Patches: only the changed units, checked against a revision

One small module, `src/backend/unitPatch.ts`, used by saves and publishes alike:

- `unitMap(doc)`: the unit map of a document.
- `diff(base, doc)`: the patch from a base unit map to `doc`. A unit is left out only when its
  digest equals the base's digest for it. Everything else is sent: a changed or new element whole,
  a removed one by identity, a member that changed shape (a keyed list that is no longer one, or
  the reverse) as a whole member, the order when it changed.
- `applyPatch(doc, patch)`: the same operations applied in TypeScript, the reference the tests
  compare the server against.

The server applies a patch with one function, `public.unit_patch_apply(doc jsonb, patch jsonb)`
(plpgsql, immutable): set and drop by member; for a keyed list, replace elements in place by
identity, append new ones, remove deleted ones, then reorder when an order is given. It **refuses**
(raises, so the write changes nothing) when the stored member is not a keyed list by the patch's
identity, when an order is not exactly the resulting identities, or when the resulting length is
not the patch's length. A refusal is answered as **replaced** (below), never as a partial write.

The same call updates the unit map (`unit_map_apply`): the digests the patch carries for put
elements and set members, deleted identities removed, the order read from the patched document,
and the new revision. The map is never sent whole after the first time; a patch carries only the
digests of what it sends.

**Revision-checked.** A patch is applied only when the stored document is exactly its base:

| Document | Base | Checked by |
|---|---|---|
| Personal record | the record's `rev` (0117) | `documents_show_patch`: `where id = p_id and kind = 'show' and rev = p_base` |
| Team record | the compare-and-swap token `updated_at`, as `team_production_save` | `team_production_patch(p_id, p_expected, p_patch)` |
| Publication head and panel | the stamp `n`, and only while `published_units->>n = published_ver->>n = p_named_n` | `control_publish_parts` (section 4) |

A unit left out of a patch is, by its digest, already on the server at that base; the base check
makes sure the server still holds that base when the patch lands. That is the whole correctness
argument, and it holds whatever the client's local copy looks like.

**How a writer knows its base.** It holds the unit map of the stored document and the revision the
map describes:

- after its own write: the map it computed for what it sent, with the revision the server answered;
- on first use after the page opens: the server's map (`body_units`, `doc_units`,
  `published_units`, a few kB, read by id), trusted only when the map's format is `1` and its own
  revision equals the row's current revision. A map that does not match (an old client wrote the
  document since, section 6) is no base.

With no base, the writer sends the whole document, as today, then the map it computed for it (one
small call, `documents_show_units_set` or `team_production_units_set`, which stores the map only if
the row is still at the revision the whole write answered). A whole map is sent only then.

**When the base has been replaced.** The stored revision is not the base, or the server refused the
patch's shape: the server answers `replaced` with the current revision and changes nothing. The
writer does exactly what it does today when another save came first:

- personal: the record goes up whole, the sync engine's own rule (last writer wins, as today), and
  that whole write gives the next patch its base;
- team: the answer is today's `saved: false` with the stored document, and the team merge runs as
  today; the next save reads the map again for the merged result's token, as on first use, and
  patches when it describes that revision (else it saves whole);
- head: section 4.

A patch is never applied to a revision it was not built for, and nothing is half applied.

## 2. Saves send only what changed

### Personal

`supabaseProvider.put` for a live (not deleted) record of kind `show`, when the patch switch is on
(section 7):

1. **Base.** The provider holds, per record id, the unit map and `rev` of the last body it wrote
   (memory). On a page's first put of that record it reads `rev, body_units` by id.
2. **Units of the new body.** Computed on the record as stored locally (images inline), one unit per
   step: each step waits while a send of this page is in flight and yields to the event loop
   (`publishRevision`'s `step()`), so a Take is never queued behind the digests. **The cost, and why
   it is not cached here:** the sync engine hands `put` a record it has just read back from the
   browser's own storage, so every object is new and a cache by object identity would not hit. Every
   save therefore digests the whole record: canonical JSON of each unit (the text is built from the
   strings the record already holds) and SHA-256 through Web Crypto, which hashes off the main
   thread. That replaces work today's whole save already does on the main thread for the same
   record (`externalizeAssets` copies the whole body through `JSON.stringify` and `JSON.parse`, the
   upsert stringifies it again, and the answer's body is parsed back), so a save costs no more main
   thread than today and is split into steps where today's is one task. The publisher works on the
   page's own in-memory production, where unchanged objects keep their identity, so its digests are
   cached by object identity (a `WeakMap`). The build reports, on the large fixture, the save's
   long tasks (the browser's Long Tasks API) against today's, and the carried AC-4 timing (section 11)
   measures what it does to Takes.
3. **Externalize only what goes up.** The changed units only go through `externalizeAssets`, so an
   unchanged graphic's images are not touched.
4. **Send.** `rpc('documents_show_patch', { p_id, p_base, p_ops })`: the answer is
   `{ rev, updated_at }`, a few bytes, where `updated_at` is the stored body's own `updatedAt` (what
   0107 copies into `body_updated_at`), replacing today's whole body sent back. `updatedAt` is a
   member like any other, so `body_updated_at` (0107) and the sync engine's identity work
   unchanged. The function also sets the row's `name` column from the body's `name`, as today's
   upsert does.
5. **Answer.** The same confirmation the sync engine reads today (the stored `updatedAt` equals the
   record's), so `sync.ts` is unchanged. `replaced`: one whole upsert in the same call, as today,
   and its answer confirms only `rev, body_updated_at` (not the body).

A whole write, when one is needed, also no longer reads the whole body back: it selects
`rev, body_updated_at`. A deletion (a tombstone) always goes whole, as today.

`documents_show_patch` runs with the caller's rights (`security invoker`): the row policy decides
whose record it is, and the 0115 production-copies guard and the 0117 revision trigger act on its
`update` of `body` as on any save.

The unit digests are of the local form (images inline). The server's map was made by the same
function from what its writer had locally, so equal digests mean equal local content, and equal
local content externalizes to the same stored content (keys are content hashes in the account's
own folder). A unit whose images could not be externalized on one device stays inline there and
differs in stored form only, never in content.

### Team

`saveTeamProduction` sends `team_production_patch(p_id, p_expected, p_patch)` when it holds a base
for that token, and the whole document otherwise. Clients have no right to update
`team_productions` directly (0054), so the function runs with the owner's rights (`security
definer`) and repeats `team_production_save`'s checks exactly: signed in, not suspended, a member of
the production's team, compare-and-swap on `updated_at`, and it sets `updated_by` and `updated_at`
as that function does. The answer is the save's (`saved`, `updated_at`, `updated_by`, `rev`; and on
a conflict or a refused patch the stored document, as today). The team merge,
`teamProductions.ts`, is unchanged.

### What a patch save never does

- It never changes a field the edit did not change, and never sends a unit whose digest the server
  already holds.
- It never bypasses a guard: the 0115 production-copies guard, the 0117 revision trigger and the
  row policy (personal) or the save function's own checks (team) act on it as on a whole save.
- It never writes a record whose kind is not `show`; other kinds keep today's whole upsert.

## 3. Each image once

Two stores, each content-named:

- **For records (pages):** Storage, as today. New: before uploading a key it has not uploaded in
  this page load, the provider asks whether the object exists (one small request); an object that
  exists is not sent. With step 3 of section 2, a save uploads only images that appear in a changed
  unit and that Storage does not already hold. Using the same image again uploads nothing. Skipping
  an upload makes the key's uniqueness carry the content, and today's keys are a 32-bit hash
  (`contentHash`, personal; plus the length, `sharedAssetKey`, team), so with parts on a new upload
  is keyed by the content name instead: `<uid>/s256-<content name>` and `team/<team>/s256-<content
  name>`. Keys already stored keep reading as before (`rehydrateAssets` reads whatever key a
  reference names); an image first saved under an old key goes up once more under its strong key the
  first time a changed unit carries it.
- **For outputs:** a table, `control_assets (hash text primary key, data text, bytes int,
  created_at)`, one row per distinct image or font, keyed by its content name.

Why a table and not Storage for outputs: an old output reads images inline in the payload
(`composeDocument` inlines data URLs). The server must be able to put an image back inline for it
(section 4), and the database cannot read Storage objects. A record's Storage objects are also
private to their account, and an output reads anonymously.

**Access.** Clients have no privilege on `control_assets` or `control_parts` (section 4) and neither
table has a policy: every read and write goes through functions that run with the owner's rights
and check the caller themselves. The self-check asserts the absence of every client privilege.

- `control_asset_put(p_show, p_data)`: a signed-in caller who may publish `p_show` (the check below)
  stores an image; the server computes its content name, so a row can never hold content under
  another content's name, and a second put of the same content writes nothing.
- `control_assets_missing(p_show, p_hashes)`: for a caller who may publish `p_show`, the subset of
  `p_hashes` that no part of a production the caller may publish names. An image used before in any
  of the caller's productions is not sent again; nobody learns what other accounts stored.
- **May publish** (`control_may_publish(p_show)`, owner's rights, not callable by clients): the
  row's own policy expression (`control_shows_owner_all`, 0063: the owner of a personal row, a
  current member of a team row's team) and its restrictive ones (not suspended, `control.hosted`
  not denied). The self-check compares it with the policy's answer on a throwaway row for the owner,
  a stranger and a teammate.

**Reading.** An output reads an image through `control_output_assets(p_output_slug, p_hashes)`,
which answers only hashes that a part of that output's production names (the same slug check as
`control_output_resolve`), so a content name alone never opens an image. An answer holds images up
to about 8 MB and lists the hashes it left out (`more`); the first image is always answered, whatever
its size, so an image over 8 MB comes alone. The output asks again for what was left out until
nothing is.

**Pruning.**

- `control_parts.left_at`: a part is inserted with `left_at` set to the time it was stored, cleared
  when a head that landed names it, and set again when a landed head stops naming it. So a part a
  publish stored and never named (its publish answered `moved` or `replaced`) is pruned like one
  that left. A part is removed an hour after `left_at`, by the next landed publish of that
  production.
- Images no part names are removed after a day, by a daily job (0039's `pg_cron` pattern), in two
  statements. The first locks the candidates (older than a day, no part naming them) with `for
  update skip locked`; the second, which reads a fresh snapshot, deletes those of them that still no
  part names. A publish takes `for key share` on every image row its parts name before storing them:
  a row the job has locked makes the publish wait until the job ends, and a row the publish holds is
  skipped by the job. So a part committed after the first statement's snapshot is seen by the second,
  and its images stay. A publish that finds an image gone is answered `missing_assets` and sends it.
- Neither ever removes what the current publication uses.

## 4. Publications in parts

### What is stored

On `control_shows`, two nullable columns, added without a default:

- `published_head jsonb`: the publication without graphic bodies: every member of today's `output`
  (cues, playout cues, scenes, output setup, rundown colours, sounds, resolution, `v`, `ver`), with
  `graphics` as references `[{ "key": <name>, "p": <part digest>, "g": <stamp digest>, "t": <design
  edited at, when known> }]` in today's order.
- `published_units jsonb`: the unit maps of the head (without `ver`) and of `panel`, with format and
  the `n` they describe.

A table `control_parts (show_id uuid references control_shows on delete cascade, digest text,
body jsonb, assets text[], created_at, left_at, primary key (show_id, digest))`: each part is one
graphic's `OutputGraphicSpec` with every asset's `data` replaced by `{ "h": <content name> }`,
under the digest of that whole body. Content-named, so a part never changes: a new design is a new
part.

`output` stays what it is today: the whole payload, images inline, written by the server (below).
Every reader of `output` (old outputs through `control_output_resolve`, `control_output_by_slug`,
the OGraf package route in `api/`, the page's scene read, the 0118 guard triggers) keeps working
unchanged.

### The part's name

The publisher names a part by the digest of its whole body (images as content names), never by the
stamp digest `g`: `graphicDigest` covers html, css, js, asset paths and data, resolution, fps and
layer, but not `ograf` or an asset's `audio`, so a change only there keeps `g`. To avoid building
every graphic's part on every publish, the name is memoized by a key that covers the whole body:
`g` (the heavy fields) plus the canonical JSON of the spec with html, css, js and every asset's data
left out (every other field, present or future). An equal key means an equal body.

### The publish

`control_publish_parts(p_id, p_named_n, p_ver, p_head, p_panel, p_parts, p_columns)` runs with the
caller's rights (`security invoker`): its one write to the row is an ordinary `UPDATE`, so the row
policy, the 0115 guard and the 0118 triggers act on it exactly as on today's `PATCH`. Its helpers
that touch `control_parts` and `control_assets` run with the owner's rights and check **may
publish** (section 3) first.

- `p_parts`: only parts whose digest the stored head does not name (the publisher compares its part
  names with the head's references: from its own last publish, else from `published_head->graphics`,
  one small read); each with its asset content names.
- `p_head`, `p_panel`: patches against the stored head (without `ver`) and panel when the publisher
  holds their maps for `p_named_n`; whole values otherwise (a first publish in parts, or after an old
  page's publish, section 6).
- `p_ver`: the stamp as phase 6 writes it (`n`, `at`, `h`, `r`, `c`), without `g` and `t`: the
  server builds those from the head's references, so a cue edit does not send every graphic's
  digest. It is the only source of the head's and `output`'s `ver`.
- `p_columns`: bindings, sources and collections on every publish (they are small, and Connect,
  Disconnect and Pause write them with no publish, `writePublishedSources`, so they must ride every
  publish as phase 6 made them); title and profile too, except on the patch path when this
  publisher's own last publish is the base `p_named_n` and they have not changed since. A whole head
  always carries all five.

Steps, one transaction, no row lock taken before step 5:

1. **Parts.** Lock (`for key share`) the image rows the new parts name; any that is missing is
   answered `missing_assets`, nothing written. Insert the new parts (`on conflict do nothing`) with
   `left_at` set, so a part that no landed head ever names is pruned (step 6).
2. **Head and panel.** Read the row without locking it. A patch is applied only when
   `published_units->>n`, `published_ver->>n` and `published_head->ver->>n` all equal `p_named_n`;
   otherwise a patch is answered `replaced`, and only a whole head and panel are taken. A stamp
   whose `n` is distinct from `p_named_n` (null counts as a value) is answered `moved`. A refused patch is answered `replaced`. Each
   writes nothing.
3. **References.** Every reference in the new head must name a stored part of this production;
   otherwise `missing_parts`, nothing written.
4. **Compose `output`.** The head, with `ver` from `p_ver` and the references, each reference
   replaced by its part and each `{h}` by the image's data URL. Only on the patch path of step 2, and
   only when no graphic reference changed, does the stored `output` keep its graphics and have only
   its other members replaced. A whole head always recomposes `output` in full.
5. **Write.** One `UPDATE` of the row by id with `published_ver->>n` not distinct from `p_named_n`
   (phase 6's condition; a row with no stamp matches a publish naming none), setting `output`, `panel`, `published_head`, `published_units` and the columns sent.
   This is the only statement that locks the row (`FOR NO KEY UPDATE`, as today's publish). The
   0118 triggers run on it as on today's publish: the revision guard, `published_rev`,
   `published_ver`. A row the condition or the guard does not let through answers `moved`.
6. **Prune.** Parts the new head names get `left_at` cleared, others get it set if it is not, and
   this production's parts whose `left_at` is over an hour ago are deleted.

The answer is small: `{ landed, n }` or the reason. The revision-only update of phase 6 (nothing on
the outputs changes) is unchanged.

**The publisher on the page** (`publishRevision`) builds exactly what it builds today, then sends
the difference instead of the whole:

- new parts only, their missing images put first (`control_assets_missing`, then
  `control_asset_put` for each);
- the head and panel as patches while it holds their maps for the stored `n`; otherwise it reads
  `published_units` and `published_head->graphics` (a few kB) and checks their `n`;
- `moved`: it reads the stamp again and follows phase 6's rule (a newer revision is published: done;
  otherwise rebuild the patch against the new base, at most 3 times); `replaced`: whole head and
  panel, once; `missing_parts` or `missing_assets`: send those, once;
- **fallback:** a timeout, a server error, or a second answer of the same kind falls back once to
  today's whole publish (the phase 6 `PATCH`), which needs none of this phase's server functions.

The publish is still off the Take's path as phase 6 made it (steps, `sendsIdle`), and now its body
is kilobytes for a cue edit instead of megabytes.

**The Publish press goes the same way.** Automatic updates stay off in production (owner decision
(b), phase 6), so there every publish after the first is a press (Publish changes, through
`publishControlShow`). When the row exists and the switch is on, the press sends through the same
`publishInParts` with the stamp it builds (with `r` when it knows the revision, as phase 6 made it);
the first Publish of a production (an insert) stays whole, and so does a press when the parts path
falls back. Everything else the press does (the gate, the older-design check for a publish with no
revision, the slugs and the join brand after it) is unchanged.

**Sounds.** A full publish puts the graphics' sounds in Storage (`publishAudio`), keyed by the
sound's own SHA-256 (`audio-<hash>`). With the switch on it asks whether the object exists before
sending it, as images are (R7), so a publish sends no sound bytes Storage already holds.

**Small reads only.** Every new function reads named columns and never `output`, except step 4's
patch path, which keeps the stored graphics; `control_output_head` reads `published_head`, not the
payload.

### What it costs the server

Composing `output` for old readers moves the 20 MB from the network to the database: a design
change or added graphic recomposes it, a cue edit rewrites the stored value once (a `jsonb` value
is stored whole). Today every publish already writes those 20 MB, so the database does no more
than today. Steps 1 to 4 lock no row of `control_shows`; only step 5's `UPDATE` does, for as long
as today's publish holds it, and a Take's `KEY SHARE` passes it (0071). An old page's Take that
writes `live_cue` waits for step 5 only, as it waits for today's publish. The build measures the
whole function on the large fixture: it must stay under 2 s there, well inside the API's statement
timeout; a slower result goes to the coordinator before landing. Writing `output` only while an old
output can still read it is a follow-up for after phase 8, filed as an issue with that number.

## 5. Partial reads

### New outputs

A new output takes a version in three reads, all in its reader worker (`payloadReader.ts`, plain
ES2017 for Chromium 71):

1. `control_output_head(p_output_slug)`: today's `control_output_resolve` answer with
   `published_head` in place of `output`. `head: null` when the row has no current head (its
   `published_head->ver->>n` is not `published_ver->>n`, section 6) or while the `partial_writes`
   switch is off (section 7). Tens of kB.
2. `control_output_parts(p_output_slug, p_digests)`: only the parts it does not hold.
3. `control_output_assets(p_output_slug, p_hashes)`: only the images it does not hold, in as many
   answers as it takes (section 3).

The worker composes each new part as today's inline spec and posts to the main thread the head and
only the specs the main thread does not hold; the main thread puts them together with the specs it
holds for unchanged references, so the swapper, the stage and the cues take exactly the payload
they took before (phase 6 R12 kept). A cue edit therefore costs an output one head read and no
graphic; a design update one head and one part and only its new images.

**What it keeps.** The worker and the main thread keep the parts and images named by the version
the output holds and by the one it is taking, and nothing else: once a version is handed over,
everything only an older version named is dropped. An output that runs for days holds no more than
two versions' worth, as today.

**When a requested revision has been replaced.** Parts and images never change under their names,
so a read of them is either answered or missing:

- the head moved while the output read parts (another publish landed): the output finishes the
  version it read the head of, from parts that stay stored for an hour after they leave the head,
  and then takes the newer one as phase 6's newest-wins rule says (the stamp probe sees it);
- a part or image is missing (pruned, or never stored by an old page's publish): the answer lists
  it; the output drops that version and reads the head again once. A second missing answer for the
  same head, a `null` head, or two failed answers to the same request (the head, one batch of parts,
  or one batch of images) make it read `control_output_resolve` whole, as today, for that version.

An output never shows a version made of parts of two heads: it hands a payload to its preparer only
when it holds every part and image that one head names.

### Writers

A page reads a document's map (a few kB) instead of its body when it needs a base (section 1), and
a publisher reads the head's references instead of the payload. A page that pulls a production
another page saved still reads the whole record in this phase (section 9).

## 6. Old and new clients writing at once

Each row says what happens and why nothing is lost or wrong.

| Writer, then | What happens |
|---|---|
| Old page saves a personal record whole | `rev` moves (0117 trigger); `body_units` keeps its old revision, so no new page uses it as a base. A new page's next patch is `replaced` and goes up whole, as today's last-writer-wins sync; the whole write stores a fresh map. |
| Old page saves a team record whole | The token moves; a new page's patch gets today's conflict answer and merges as today. The team map is checked by revision like the personal one. |
| Old page publishes (allowed while `auto_publish` is off, or before automatic mode, G3 section 10) | It writes `output` whole with images inline; the 0118 triggers run as today. `published_head` and `published_units` keep the old `n`, so they no longer describe the row. New outputs: the head function answers `head: null` (its `n` is not `published_ver->>n`), so they read `control_output_resolve` whole. A new publisher: step 2 refuses a patch (the maps' `n` is not the stamp's), so it sends a whole head and panel, and step 4 recomposes `output` in full from them. Nothing reads or keeps a stale head. |
| New page presses Publish (an existing row, switch on) | The same path as an automatic publish, in parts (section 4); the first Publish of a production is an insert and stays whole, which leaves no head: the next publish sends a whole head. |
| New page publishes in parts, old output open | The server wrote `output` whole, images inline: the old output reads it as today. Its whole downloads are reported, not judged (AC-5). |
| New page publishes in parts, new output open | Section 5. |
| Two new pages publish the same revision | Phase 6's rule: the stamp condition lets one land; the other's answer is `moved`, it reads the stamp, finds the revision published and stops. |
| Two new pages save one personal record | The second's patch is `replaced` (the first moved `rev`); it goes up whole, as two whole saves do today. Phase 8 measures it with five people. |
| A new page's patch and an old page's save race | The base check is one statement under the row lock: exactly one lands first; the other sees the moved revision. |

## 7. Switching on

1. **Migrations land** (section 10): installed, they change nothing visible. Nobody calls the new
   functions yet; the new columns are null.
2. **The app is released.** New pages read `partial_writes_state()` (signed-in pages only, as
   `auto_publish_state`): installed, and the `system_settings` switch `partial_writes`. Off or
   unreadable means today's whole saves and whole publishes. New outputs ask for the head; the head
   function answers `null` while the switch is off, so they read whole.
3. **The switch.** Turned on by the owner, or by the coordinator with his permission, after the app
   is live and `partial_writes_state()` reports `installed: true` on production. Separate from
   `auto_publish`, which stays off until the owner turns it on.

**Back out.** Switch off: pages save and publish whole from their next state read (on open and
every 30 s, as `auto_publish_state`), and every output's next head read answers `null`, so it reads
whole at once. No deploy, nothing to repair: a whole publish leaves the head stale, which section
6's rules already handle when the switch comes on again.

## 8. Rules

- **R1** A patch is applied only when the stored document is exactly its base revision (`rev`, the
  team token, and for a head or panel the `n` that the stamp, the head and the maps all carry);
  otherwise nothing is written and the answer is `replaced` or `moved` (1, 4).
- **R2** A unit is left out of a patch only when its digest equals the digest the base's map holds
  for it (1).
- **R3** Applying a patch to its base gives exactly the document the writer had: the TypeScript and
  the database apply agree, and a malformed patch (wrong identity, incomplete order, wrong length)
  changes nothing (1).
- **R4** A map is used as a base only when its format is `1` and its revision equals the row's
  current revision (1, 6).
- **R5** A patch save keeps every guard, trigger and check a whole save has (0115, 0117, the row
  policy, the team save's checks) (2).
- **R6** A personal patch's answer and a whole save's answer carry no record body (2).
- **R7** A save uploads an image only when it is in a changed unit and its Storage object does not
  exist (3).
- **R8** A publish stores each image once by its content name, computed by the server; it sends
  only images no part of the caller's productions names (3).
- **R9** Clients have no privilege on `control_parts` or `control_assets`; an output reads an image
  only through its production's parts (3).
- **R10** A publish sends only parts the stored head does not name, named by their whole body, and
  the head and panel as patches only on a valid base (4).
- **R11** After any publish, new-style or old, `output` is the whole inline payload of
  `published_ver`, so every old reader works unchanged; a whole head always recomposes it (4, 6).
- **R12** A new output reads the head, then only the parts and images it lacks, off its main thread,
  and hands its preparer the same payload a whole read would have given (5).
- **R13** An output never hands its preparer a payload mixing two heads; a missing part makes it
  read the head again once, then whole; it keeps only what the version it holds and the one it is
  taking name (5).
- **R14** A head whose `n` differs from `published_ver->>n` is never read or patched as current (5,
  6).
- **R15** No part or image the current publication uses is ever pruned, and a publish locks the
  images it names before naming them (3, R22).
- **R16** With the `partial_writes` switch off, pages save and publish whole and outputs read whole,
  as before this phase (7).
- **R17** A publish locks the `control_shows` row only in its final `UPDATE`, as today (4).
- **R18** Unit digests on a page are computed one unit per step, never while a send is in flight
  (2).
- **R19** A publish always carries bindings, sources and collections, and carries title and profile
  whenever its base is not its own last publish (4).
- **R20** With parts on, an upload whose existence is checked is keyed by the image's content name
  (3).
- **R21** A Publish press over an existing row sends in parts when the switch is on, as an automatic
  publish does; only the first Publish (an insert) and a fallback write whole (4).
- **R22** The image prune deletes only rows it locked and that no part names in a snapshot taken
  after the lock (3).

## 9. Decisions and limits

- **Whole writes stay as the fallback** for a missing base, every `replaced` answer and a failed
  publish in parts. They are today's paths, already tested.
- **Pulls of another page's save stay whole in this phase.** A page that pulls a production changed
  elsewhere reads the record whole, as today. AC-5 judges the editing page and the outputs; the
  server's map makes a partial pull possible later (read the map, then only differing units) and
  phase 8, which runs five people on one production, measures whether it is needed. Filed as an
  issue when the build lands.
- **The server keeps writing `output` whole** for old outputs and other readers (section 4).
  Reported with its time; stopping it is a follow-up.
- **Digests are SHA-256 truncated to 128 bits** on pages (Web Crypto). Outputs compute none.
- **Constants.** Parts kept an hour after leaving a head; images a day after no part names them;
  output image answers at most 8 MB; at most 3 rebuilds of a publish patch, as phase 6; the publish
  function under 2 s on the large fixture.
- **Automatic updates stay off in production** (owner decision (b), phase 6). This phase changes
  only what is sent.
- **The published panel of a production whose graphics' records are in another account's library**
  (a team production, issue #779, `heldPanelIfNeeded`) is still read whole by the publisher, as
  phase 6 does. AC-5's fixture is personal; reading it by units is a follow-up filed when the build
  lands, with its size measured.

## 11. How AC-5 is tested and measured

The judging rule for the 20 kB, fixed now: every request and response of the production page, bodies
and headers both ways, from the edit until the publication names the save (`published_rev` is the
save's revision), excluding Takes and their reports, on the large fixture, on a production build,
after the page has saved and published once since it opened (its first save and publish may be
whole, section 1). The budget it should come to, per request, for the build to check:

| Request | Expected |

| Save: `documents_show_patch` with one cue (at most 2 kB) and `updatedAt`, and its answer | about 4 kB with headers |

| Publish: the stamp read | about 1 kB |
| Publish: `control_publish_parts` with one cue in the head patch, `p_ver` without `g` and `t`, no columns, and its answer | about 5 kB |
