# Fix #2617 evidence: a bound press is a relative operation, resent until it lands

Scoped fix inside the live-publishing run (#2361). The phase 9 load diagnosis
(`phase-9-load-diagnosis.md`, section 4, cause 4) found that a Goal press on a bound score is lost
when the backend is slow: 199 presses on staging, final score 55. Review class: Risky (a migration
on the live path; attempted, accepted and unknown outcomes; retries). Pull request: #2630.

## Cause

A press on a bound field (the ± stepper, an event's `adjust`) waits for the press before it on the
same graphic for up to 7 s (`afterPress`, `src/control/graphicVerbs.ts`), then writes the bound
value through `operatorWrite` (`src/control/productionDataSession.ts`) as an ABSOLUTE figure
computed from this page's tree. It makes one attempt. On failure it says "not moved" and calls
`refresh()`, which replaces the page's tree with the server's and so drops every press counted on
top of it. With requests of several seconds and a press every 2.25 s, the queue never drains.

## Rules (observable; stated before the code)

Revised after the Rules-first `/so` (grade B, amendments A to H); the first draft is in this file's
history at a77c27a.

- **R1. What is queued.** On a published production, two kinds of press on a BOUND field go into
  the page's press queue, each with a press id (a uuid) minted at the press: an `adjust` (the ±
  stepper, an event's `adjust`) as "add N to path P", and a `set` (an event's `set`, such as a
  Reset to 0) as "make path P this text", retyped by the server when it lands to the type the
  stored leaf has then (R2). A list `add` or `remove`, whose value is
  computed from the list's current content, keeps today's road (one optimistic, absolute write),
  with one change: while a press of this page is queued on a path inside that list, the list
  press is refused with a note saying presses on that list are still sending, and nothing is
  written over them (its value was computed before they land). See "Left for later". The Data workspace, the Sheet reader, a feed and an
  unpublished production keep their absolute writes unchanged.
- **R2. What the server does.** One function, `control_data_adjust_by_slug(slug, presses)`, takes
  at most 50 presses `{id, path, by}` or `{id, path, text}`; a longer list is refused whole. In
  order:
  1. It takes the production row's lock (waiting at most 4 s, R4), then refuses the whole call if
     hosted control is switched off for the production, before anything else.
  2. A press whose id is not a uuid, or whose path is empty or not dotted text, is refused on its
     own. A press whose id it already holds for this production is answered as landed and not
     applied again.
  3. It folds the rest in order onto the stored tree: an `adjust` adds N to the leading integer of
     the leaf's text, or to 0 (`adjustedValue`); a number leaf stays a number, a text leaf stays a
     text, a missing or null leaf becomes a number; a boolean, list or object leaf refuses that
     press. A `set` writes its text retyped like `retypeLeaf` against the stored leaf: a number
     leaf takes the number if the text is one, a boolean takes `text = 'true'`, a list splits the
     text into lines, anything else takes the text.
  4. Each path is checked alone, inside a savepoint that is always rolled back, by sending its
     folded value through today's operator door (`control_data_patch_by_slug`). Only that door's
     own "not a bound path" or "not a field value" refuses a path, and then every press on it. Any
     other error (the command budget, a statement or lock timeout) ends the whole call with
     nothing recorded, so the page resends it. A rolled-back check leaves no row, so it costs the
     budget nothing; the checks grow with the number of distinct paths in the call, not presses.
  5. It writes ONE absolute merge patch through that door: each changed path once, and a path
     that runs through a list index (`teams.0.score`) as the whole list taken from the folded
     tree, so two presses under one list in one call are both kept.
  6. It records the applied ids, deletes this production's ids older than 24 hours, and answers
     `{data, writes, landed: [ids], refused: [{id, reason}]}`.
- **R3. Once per press id.** Ids are recorded in the same transaction as the write, in a table
  whose primary key is (production, id), kept 24 hours (each call deletes its production's older
  rows). The table has row level security on, no policy, and `revoke all` from public, anon and
  authenticated: only the function reads or writes it. A failed call (a statement or lock timeout, the
  command budget, a lost connection before commit) records nothing, so its resend applies each
  press once. The page never resends a press older than one hour: it drops it and the note line
  says how many, so a resend can never outlive its id. The server refuses a call that would record
  more than 100 ids for one production in 5 s, as it refuses an over-budget command (the page
  waits and resends).
- **R4. Resend until it lands.** The queue keeps press order. One call is out at a time per page,
  carrying the oldest unsent presses (at most 50). A call with no answer (no connection, a 5xx, a
  statement or lock timeout, the budget, or nothing back in 15 s, when the page gives up on it)
  goes again after 0.5 s, doubling to 8 s. The function waits at most 4 s for the row's lock, so an
  attempt the page gave up on does not hold a place in the lock queue for long. A press refused by
  the answer is dropped and the note line says how many presses that was; the others go on.
- **R5. The tree and air.** Unsent presses are never in the tree the page holds: Take, Update,
  PREVIEW and the bound fields on screen read the server's newest tree, as today, and move when the
  server's answer or its rows arrive. An event never carries a bound field in its payload (today's
  `pressSend` leaves bound keys out), so air takes the figure from the server's update rows only.
  While a press is queued, its button reads "Sending" and the status tag counts it (R7), so the
  operator sees the press was taken even though the figure has not moved yet.
- **R5a. A Take's or Update's bound figures are the stored tree's at its row.** The page still
  sends them (`withBoundValues`), but `control_send_seq`, while it holds the production's head
  (0071 step 2), checks every bound field already present in an item's `data` against the stored
  tree's value (since revised: it follows the item with a correcting row rather than rewriting it,
  see "Rules found after coding") (`production_data_resolve`, the resolution `control_data_apply`'s update rows use)
  before it numbers the rows and sends the fast frame. It adds no field the item did not carry,
  and a path the tree lacks keeps the page's figure, as today. A data write changes `data` before
  its update rows take the head (0071's `control_events_seq`), so whichever of the two rows lands
  last carries the server's newest figure: air ends on the tree whatever the order, for this
  page, other pages on today's road and feeds alike. An old page's own Takes go through
  `control_send_many`, which is unchanged, so they keep today's race. The page's own PROGRAM monitor may show its own
  figure until the rows arrive, as today. Same signature, grants and answers; a database without
  this migration keeps today's race (R10). How: the read is its own statement after the head lock,
  made only when an item left after the skip filter is an `update` with a non-empty `data`, and it
  resolves only the touched graphics' bindings; it runs before step 8, so the head summary and
  the rows take the corrections. Every item stays exactly as sent. A correction is the row a data
  write makes: `{t:'update', data, src:'operator'}` with only the differing bound fields, no
  command id, never fast. The text is the server's (`production_data_format`), as its data update
  rows already write it.
- **R5b. R5a's limits** (coordinator, 2026-11-20, on #2361; each has a test):
  1. Only a field the production binds to its tree (`bindings[graphic][field]`, a non-empty path)
     is replaced. Every other field, and typed data (an item's `typed`, which is not in `data`),
     is left exactly as sent.
  2. A tree write still in flight when a Take's row is numbered writes its own update row after
     it, so air always ends on the last tree write that landed.
  3. The head is held at 60 graphics within a few milliseconds of today's time; measured before
     and after and reported. If it grows materially, the builder stops and reports.
  4. Old pages, feeds, cue arms (a timed cue's Take goes through `control_send_seq` from the page,
     `cueArmEngine.ts`) and every other caller keep working unchanged: same signature, same
     grants, same answer shape. A production with no bindings, and every Out, Next, event or snap,
     runs exactly today's code path.
- **R6. Other writers.** Presses from several pages, tabs or people on one path all count: each is
  applied to whatever the stored value is when it lands. An absolute write by anyone else (the
  Data owner, the Sheet reader, a feed, an old page) sets the value, and presses that land after
  it count on top of it. Within one page, its queued presses land in press order. R10's fallback
  write is absolute too, so like today's it overwrites a write by someone else that landed after
  its figure was computed.
- **R7. Unsent count.** While any press is queued, PROGRAM's status tag reads "1 press unsent" or
  "N presses unsent", ahead of "sending…" and "not confirmed", and the page counts as holding air
  (no automatic reload). At 0 the tag says what it would have said without it.
- **R8. Order and outcome.** A press on a graphic still waits for the press before it on that
  graphic (the kept ordering wait for an event's send), but not for the one before it to land: it
  is queued as soon as its turn comes. The press's outcome stays "Sending" until it settles:
  accepted when its id is answered as landed, refused when refused, failed with the note when it
  is dropped (R3's hour, R9).
- **R8a. An event's bound moves follow its send's outcome** (coordinator, 2026-11-20, on #2361).
  The event is sent first, as today. Accepted: its bound presses are queued. Unknown (no answer, so
  it may still commit): its bound presses are queued all the same, since each can land only once.
  Refused, or failed with an answer: nothing is queued and no shared value moves, as today.
  The press reports the event's outcome: unknown with today's note while the event's send is
  unknown, as `failedSends.ts` already says ("No answer; it may still land") and settles when its
  row is heard. The score's presses are shown by the unsent count, and the note line says if they
  are refused or dropped. If the event never commits, the score moves with no Goal animation; the
  coordinator chose that over a lost goal.
- **R9. Mode.** Unpublishing, or a new control slug, drops the old slug's queued presses and the
  note line says how many. A republish that keeps the slug keeps them. Closing or reloading the
  page drops them; R7 is what tells the operator first.
- **R10. Old pages, old database.** An old page keeps calling `control_data_patch_by_slug` as today
  and sees no change. A new page on a database without the new function (it answers `PGRST202`)
  sends each queued path's figure as today's absolute write instead: the server tree's value with
  that path's queued presses folded on, computed once and resent unchanged until it lands, so a
  resend writes the same figure and cannot count twice; it takes every press it covered off the
  queue.
- **R11. The live path and the invariant.** The migration also replaces `control_send_seq` (R5a), so it is a
  live-path migration. `productionData.ts` is unchanged and still expresses no increment, and
  the tree write stays an absolute merge patch. The increment is turned into that patch by the
  server, under the row lock, and the press id is what keeps a retry from counting twice. This
  reading is recorded in `contracts/rules` in the same PR.

## Rules found after coding

Listed apart from the Rules above, as the review checkpoints ask. Each has a test.

- **R2.4, how a refused path is found.** Not a rolled-back probe per path: the call writes the whole
  patch through the door, and when the door refuses a path it drops the presses under that path
  and writes the rest again, inside the same call. The answer is the same as R2.4 states; in the
  common case, nothing refused, the row is written once rather than once per path plus once.
- **R2.3, a list element that does not exist yet** (`grid.0.gap` on `grid: []`) is made, as the
  page's `setPath` makes it, so the door's rule for elements past the stored end applies.
- **R2.6, landed means held.** A press whose value the door's answer does not hold (a leaf inside
  a list that nothing binds, which the door leaves alone) is refused and never recorded.
- **R5a, an `update` with no `data`, or a graphic nothing binds,** is sent exactly as it came.
- **R4, a refusal is a refusal whatever its status.** PostgREST answers 42501 with 401 to a
  signed-out caller; the page resends a 401 only for a lapsed sign-in.
- **R4, no progress waits.** An answer that settles none of its presses is treated as no answer:
  the next call waits for the backoff.
- **R8, one press per bound field.** An event moving two fields bound to one path queues each
  field's own delta.
- **R10, only from a tree read from the server,** and never while a read is out; its attempt is
  given up after 15 s like the relative call's.
- **R7, the tag** counts unsent presses ahead of every other published state, "connection lost"
  included: the count is what the operator needs then.
- **A press after the session ended** answers not landed at once.
- **R4, a gateway's 408 or 429** recorded nothing, so the call goes again (final `/so`).
- **R2.4, narrower than a unit** (Codex on #2630): a refused path refuses only the presses on it,
  above it or below it; its siblings in the same list are folded again from the stored tree and
  written. Only when the door names a path no press is on are the presses under that list refused.
- **R2.3, no list padded past index 1000** (final `/so`): a press whose path would make a list
  longer than that is refused on its own, so a press cannot hold the row while a list is padded.
  An object key that happens to be a number (`results.2024.score`) is not a list index and stays
  allowed. Old press ids are pruned when that production is next pressed; an idle production's
  rows go with it when it is deleted.
- **R5a, a correcting row, not a rewritten one** (Codex on #2630): rewriting the item left its
  command id in place, so the sending page took the corrected row for its own echo and kept its
  PROGRAM on the figure it had sent. Now the item stays exactly as sent, and when one of its bound
  figures differs from the stored one the server puts a correcting `update` right after it, with
  only those fields and the stored text. Every follower, the sending page included, applies it
  last. R5b.1 holds: nothing of the item changes.
- **R5a, the correction is a data row** (fresh review of 458aaf1): a first version copied the item's
  `fast` flag and carried no `src`. On the fast road a row with no command id is applied twice, and
  a late copy could take air back to an older figure; without `src` it also counted as a press
  (rev, owed) and released a graphic held for typed data. It is now exactly a data write's row,
  `src:'operator'` and never fast, so it follows the rules a feed's row already follows. A
  correction counts against the 50-row burst cap like any row; at the cap the send is refused and
  resent, as today.
- **R10, the hold is bounded** (same review): an abandoned figure holds new figures back until it
  settles, or for at most a minute; the API roles' statement timeouts end its write long before.
- **R10, no new figure behind one given up on** (Codex on #2630): an absolute attempt given up
  after 15 s can still commit, so until it has settled only the same figure is resent; a new
  figure waits, or it could be overwritten by the late one.
- **R1, a list press is refused, not delayed** (Codex on #2630): waiting did not help, because its
  value was computed before the queued presses landed; written after them, it undid them.

### Timing, local stack (the instrument: `fix-2617-goals.measure.ts.txt`, runs in `fix-2617-data/`)

One signed-in page, a personal production of 6 or 60 graphics (a House Score bound to the tree,
the rest Hairlines), Goal pressed every 2.25 s for 45 s (21 presses), then 40 s to settle, then
the database at full speed and 40 s more; then 10 Takes of the score. "Staging-like" holds every
data write 3 s in the browser and cuts every fourth before it reaches the server (the diagnosis's
request times and lost attempts). A CPU limit on the database (`docker update --cpus 0.1`) alone
did not slow these small writes enough to lose a press here (21 of 21 before, 0.1 to 0.24 s).
Before ran on the base commit with 0071's `control_send_seq`; after on this branch with 0123.

| | before 6 | after 6 | before 60 | after 60 |
|---|---|---|---|---|
| final score of 21 presses, full speed | 21 | 21 | 21 | 21 |
| final score of 21 presses, staging-like | 15 | 21 | 14 | 21 |
| data write calls, staging-like (ok / cut) | 21 (16 / 5) | 15 (12 / 3) | 21 (16 / 5) | 15 (12 / 3) |
| data write request p50 / p95, full speed | 12 / 50 ms | 44 / 91 ms | 145 / 220 ms | 111 / 213 ms |
| data write function mean, full speed | 4.6 ms | 7.0 ms | 4.6 ms | 6.4 ms |
| `control_send_seq` mean per Take (head held), full speed | 2.83 ms | 3.52 ms | 3.13 ms | 3.18 ms |
| `control_send_seq` mean per Take, staging-like | | 2.92 ms | 3.27 ms | 3.50 ms |

Before, the staging-like page said "The shared value did not move: the server did not answer" and
the presses were gone; after, the tag read "N presses unsent" while they waited, and every one
landed once within the settle. Step 7b keeps the head-hold within a fraction of a millisecond of
0071's at 6 and 60 graphics (R5b.3). One call carries every waiting press, so a slow write costs
fewer calls than presses.

## Left for later

- A bound list `add` or `remove` is still one attempt (R1), though it is refused rather than
  written over this page's queued presses. Making it safe to resend needs the list operation on the server too; its
  own issue, linked from the PR.

## Same family, decided

- **A Take attempt is cut at 1.5 s and abandoned at 4 s** (`failedSends.ts`). Its own PR. It is the
  road every verb's send takes, including the Goal's event, and its window exists so a Take never
  airs late or twice; widening it needs its own Rules and the server's late-commit check, not a
  data write's. A Goal whose event send is abandoned with no answer still moves the score (R8a).
- **`audience_operator_add` is sent once** (`audienceData.ts`). Its own PR: another seam and
  another RPC, and making it safe to resend needs an id on the audience row, its own migration.
