# Fix #2617 evidence: a bound press is a relative operation, resent until it lands

Scoped fix inside the live-publishing run (#2361). The phase 9 load diagnosis
(`phase-9-load-diagnosis.md`, section 4, cause 4) found that a Goal press on a bound score is lost
when the backend is slow: 199 presses on staging, final score 55. Review class: Risky (a migration
on the live path; attempted, accepted and unknown outcomes; retries).

## Cause

A press on a bound field (the ± stepper, an event's `adjust`) waits for the press before it on the
same graphic for up to 7 s (`afterPress`, `src/control/graphicVerbs.ts`), then writes the bound
value through `operatorWrite` (`src/control/productionDataSession.ts`) as an ABSOLUTE figure
computed from this page's tree. It makes one attempt. On failure it says "not moved" and calls
`refresh()`, which replaces the page's tree with the server's and so drops every press counted on
top of it. With requests of several seconds and a press every 2.25 s, the queue never drains.

## Rules (observable; stated before the code)

- **R1. What is relative.** A press that ADJUSTS a bound field (the ± stepper on a bound field, an
  event's `adjust` on a bound field) on a published production is sent as "add N to path P" with a
  press id minted at the press, never as a figure. The server reads the stored value under the
  row's lock and writes the sum through today's operator door (`control_data_patch_by_slug`), so
  every guard it has stays: the path must be bound, the value must be a field value, the command
  budget, hosted control switched off. The arithmetic is today's (`adjustedValue`: the leading
  integer of the value's text, or 0, plus N), and the leaf keeps its type (a number stays a
  number, a text stays a text, a missing leaf starts as a number). A `set`, an `add` or `remove`
  on a list, the Data workspace, the Sheet reader and an unpublished production keep their
  absolute writes, unchanged.
- **R2. Once per press id.** The server records each press id it applies, in the same transaction
  as the tree write, and keeps it for 24 hours. A press id it already holds is not applied again,
  and the answer names it as landed all the same. A write that fails (a statement timeout, the
  command budget, a lost connection before commit) records nothing, so its resend applies it once.
- **R3. Resend until it lands.** A page's unsent presses wait in press order. One request is out
  at a time per page, carrying every unsent press (at most 50, oldest first). When it has no
  answer (no connection, a 5xx, a statement timeout, the command budget, or nothing back in 15 s,
  when the page gives up on it) it goes again after 0.5 s, doubling to 8 s, for as long as the
  page holds this production's control slug. A press the server REFUSES by its answer (the path
  is not bound, the value is not a field value, hosted control is off, the slug is unknown) is
  dropped, the note line says how many presses that was, and the other presses go on.
- **R4. The page's figure.** The tree the page holds is the server's newest tree with every unsent
  press added on top. A failed request, a read, or another press's answer never drops a stacked
  press from the figure. A press answered as landed leaves the overlay in the same step as the
  answer's tree is held. A press whose earlier attempt committed while its answer was lost can
  show one too many on this page only, until its resend is answered; what airs follows the
  server's rows and is never affected.
- **R5. Unsent count.** While any press is unsent, PROGRAM's status tag reads "1 press unsent" or
  "N presses unsent", ahead of "sending…" and "not confirmed", and the page counts as holding air
  (no automatic reload). At 0 the tag says what it would have said without it.
- **R6. Order and outcome.** A press on a graphic still waits for the press before it on that
  graphic (the kept ordering wait for the event's send), but not for the one before it to LAND: it
  is queued as soon as its turn comes, so presses never wait behind a slow write. A press reports
  accepted once its id is answered as landed, and failed with the note once refused. An event
  whose send did not go moves no shared value, as today (see "Same family" below).
- **R7. Mode.** Unpublishing, or a new control slug, drops the old slug's unsent presses and the
  note line says how many. A republish that keeps the slug keeps them. Closing or reloading the
  page drops them; R5 is what tells the operator first.
- **R8. Old pages, old database.** An old page keeps calling `control_data_patch_by_slug` as today
  and sees no change. A new page on a database without the new function (it answers `PGRST202`)
  falls back to today's absolute write for that path: it sends the figure the page shows (the
  server's tree plus the path's unsent presses), one request at a time, resent until it lands like
  R3; a resend writes the same figure, so it cannot count twice. The landed write takes every
  unsent press on that path with it.

## Same family, decided

- **A Take attempt is cut at 1.5 s and abandoned at 4 s** (`failedSends.ts`). Its own PR. It is the
  road every verb's send takes, including the Goal's event, and its window exists so a Take never
  airs late or twice; widening it needs its own Rules and the server's late-commit check, not a
  data write's. Until then a Goal whose EVENT send is abandoned still moves no score (R6), and the
  note says the event failed.
- **`audience_operator_add` is sent once** (`audienceData.ts`). Its own PR: another seam and
  another RPC, and making it safe to resend needs an id on the audience row, its own migration.
