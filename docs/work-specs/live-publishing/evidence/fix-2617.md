# Fix #2617 evidence: a bound press is a relative operation, resent until it lands

Scoped fix inside the live-publishing run (#2361). The phase 9 load diagnosis
(`phase-9-load-diagnosis.md`, section 4, cause 4) found that a Goal press on a bound score is lost
when the backend is slow: 199 presses on staging, final score 55. Review class: Risky (a migration
on the live path; attempted, accepted and unknown outcomes; retries).

## Cause

A press on a bound field (the ± stepper, an event's `adjust`) waits for the press before it on the
same graphic for up to 7 s (`afterPress`, `src/control/graphicVerbs.ts`), then writes the bound
value through `operatorWrite` (`src/control/productionDataSession.ts`) as an ABSOLUTE figure
computed from this page's tree. It makes one attempt. On failure it says "not moved" and calls
`refresh()`, which replaces the page's tree with the server's and so drops every press counted on
top of it. With requests of several seconds and a press every 2.25 s, the queue never drains.

## Rules (observable; stated before the code)

Revised after the Rules-first `/so` (grade B, amendments A to H); the first draft is in this file's
history at a77c27a.

- **R1. What is queued.** On a published production, two kinds of press on a BOUND field go into
  the page's press queue, each with a press id (a uuid) minted at the press: an `adjust` (the ±
  stepper, an event's `adjust`) as "add N to path P", and a `set` (an event's `set`, such as a
  Reset to 0) as "make path P this text", retyped by the server when it lands to the type the
  stored leaf has then (R2). A list `add` or `remove`, whose value is
  computed from the list's current content, keeps today's road (one optimistic, absolute write),
  with one change: it waits until no queued press of this page is on a path inside that list, so
  it cannot overwrite a press that landed while its answer was still out. It waits at most the
  press wait's window (7 s, `afterPress`); past it the list press is refused with a note saying
  presses on that list are still sending, and nothing is written over them. See "Left for later". The Data workspace, the Sheet reader, a feed and an
  unpublished production keep their absolute writes unchanged.
- **R2. What the server does.** One function, `control_data_adjust_by_slug(slug, presses)`, takes
  at most 50 presses `{id, path, by}` or `{id, path, text}`; a longer list is refused whole. In
  order:
  1. It takes the production row's lock (waiting at most 4 s, R4), then refuses the whole call if
     hosted control is switched off for the production, before anything else.
  2. A press whose id is not a uuid, or whose path is empty or not dotted text, is refused on its
     own. A press whose id it already holds for this production is answered as landed and not
     applied again.
  3. It folds the rest in order onto the stored tree: an `adjust` adds N to the leading integer of
     the leaf's text, or to 0 (`adjustedValue`); a number leaf stays a number, a text leaf stays a
     text, a missing or null leaf becomes a number; a boolean, list or object leaf refuses that
     press. A `set` writes its text retyped like `retypeLeaf` against the stored leaf: a number
     leaf takes the number if the text is one, a boolean takes `text = 'true'`, a list splits the
     text into lines, anything else takes the text.
  4. Each path is checked alone, inside a savepoint that is always rolled back, by sending its
     folded value through today's operator door (`control_data_patch_by_slug`). Only that door's
     own "not a bound path" or "not a field value" refuses a path, and then every press on it. Any
     other error (the command budget, a statement or lock timeout) ends the whole call with
     nothing recorded, so the page resends it. A rolled-back check leaves no row, so it costs the
     budget nothing; the checks grow with the number of distinct paths in the call, not presses.
  5. It writes ONE absolute merge patch through that door: each changed path once, and a path
     that runs through a list index (`teams.0.score`) as the whole list taken from the folded
     tree, so two presses under one list in one call are both kept.
  6. It records the applied ids, deletes this production's ids older than 24 hours, and answers
     `{data, writes, landed: [ids], refused: [{id, reason}]}`.
- **R3. Once per press id.** Ids are recorded in the same transaction as the write, in a table
  whose primary key is (production, id), kept 24 hours (each call deletes its production's older
  rows). The table has row level security on, no policy, and `revoke all` from public, anon and
  authenticated: only the function reads or writes it. A failed call (a statement or lock timeout, the
  command budget, a lost connection before commit) records nothing, so its resend applies each
  press once. The page never resends a press older than one hour: it drops it and the note line
  says how many, so a resend can never outlive its id. The server refuses a call that would record
  more than 100 ids for one production in 5 s, as it refuses an over-budget command (the page
  waits and resends).
- **R4. Resend until it lands.** The queue keeps press order. One call is out at a time per page,
  carrying the oldest unsent presses (at most 50). A call with no answer (no connection, a 5xx, a
  statement or lock timeout, the budget, or nothing back in 15 s, when the page gives up on it)
  goes again after 0.5 s, doubling to 8 s. The function waits at most 4 s for the row's lock, so an
  attempt the page gave up on does not hold a place in the lock queue for long. A press refused by
  the answer is dropped and the note line says how many presses that was; the others go on.
- **R5. The tree and air.** Unsent presses are never in the tree the page holds: Take, Update,
  PREVIEW and the bound fields on screen read the server's newest tree, as today, and move when the
  server's answer or its rows arrive. An event never carries a bound field in its payload (today's
  `pressSend` leaves bound keys out), so air takes the figure from the server's update rows only.
  While a press is queued, its button reads "Sending" and the status tag counts it (R7), so the
  operator sees the press was taken even though the figure has not moved yet.
- **R5a. Air converges on the tree.** A Take, an Update or a folder's Take carries the bound
  figures of the server tree the page holds (`withBoundValues`), so one sent while a call of this
  page is out can carry a figure that call is about to move, and its row can land after the call's
  update row. So when a call is answered, for every graphic this page sent a Take or an Update to
  whose send was out at any moment the call was out (started before it or during it), which is
  still on air from this page's view, and one of whose bound
  fields reads a path in that call, the page sends one Update carrying only those bound fields,
  from the answer's tree, through the one sender. Air then ends on the server's figure whichever
  row landed last. The same holds when a refused press was in the call: the Update carries the
  server's figure, which never had the refused press in it. Takes from other pages are as today:
  the server's rows and their own trees decide them (a race that exists today, not widened here). A failed call, a read or another answer never drops a queued
  press, because the queue is not the tree. An answer the `asked/held` numbering passes over still
  takes its landed and refused ids off the queue. Air follows the server's rows only.
- **R6. Other writers.** Presses from several pages, tabs or people on one path all count: each is
  applied to whatever the stored value is when it lands. An absolute write by anyone else (the
  Data owner, the Sheet reader, a feed, an old page) sets the value, and presses that land after
  it count on top of it. Within one page, its queued presses land in press order. R10's fallback
  write is absolute too, so like today's it overwrites a write by someone else that landed after
  its figure was computed.
- **R7. Unsent count.** While any press is queued, PROGRAM's status tag reads "1 press unsent" or
  "N presses unsent", ahead of "sending…" and "not confirmed", and the page counts as holding air
  (no automatic reload). At 0 the tag says what it would have said without it.
- **R8. Order and outcome.** A press on a graphic still waits for the press before it on that
  graphic (the kept ordering wait for an event's send), but not for the one before it to land: it
  is queued as soon as its turn comes. The press's outcome stays "Sending" until it settles:
  accepted when its id is answered as landed, refused when refused, failed with the note when it
  is dropped (R3's hour, R9).
- **R8a. An event's bound moves follow its send's outcome** (coordinator, 2026-11-20, on #2361).
  The event is sent first, as today. Accepted: its bound presses are queued. Unknown (no answer, so
  it may still commit): its bound presses are queued all the same, since each can land only once.
  Refused, or failed with an answer: nothing is queued and no shared value moves, as today.
  The press reports the event's outcome: unknown with today's note while the event's send is
  unknown, as `failedSends.ts` already says ("No answer; it may still land") and settles when its
  row is heard. The score's presses are shown by the unsent count, and the note line says if they
  are refused or dropped. If the event never commits, the score moves with no Goal animation; the
  coordinator chose that over a lost goal.
- **R9. Mode.** Unpublishing, or a new control slug, drops the old slug's queued presses and the
  note line says how many. A republish that keeps the slug keeps them. Closing or reloading the
  page drops them; R7 is what tells the operator first.
- **R10. Old pages, old database.** An old page keeps calling `control_data_patch_by_slug` as today
  and sees no change. A new page on a database without the new function (it answers `PGRST202`)
  sends each queued path's figure as today's absolute write instead: the server tree's value with
  that path's queued presses folded on, computed once and resent unchanged until it lands, so a
  resend writes the same figure and cannot count twice; it takes every press it covered off the
  queue.
- **R11. The invariant.** `productionData.ts` is unchanged and still expresses no increment, and
  the tree write stays an absolute merge patch. The increment is turned into that patch by the
  server, under the row lock, and the press id is what keeps a retry from counting twice. This
  reading is recorded in `contracts/rules` in the same PR.

## Same family, decided

- **A Take attempt is cut at 1.5 s and abandoned at 4 s** (`failedSends.ts`). Its own PR. It is the
  road every verb's send takes, including the Goal's event, and its window exists so a Take never
  airs late or twice; widening it needs its own Rules and the server's late-commit check, not a
  data write's. A Goal whose event send is abandoned with no answer still moves the score (R8a).
- **`audience_operator_add` is sent once** (`audienceData.ts`). Its own PR: another seam and
  another RPC, and making it safe to resend needs an id on the audience row, its own migration.
