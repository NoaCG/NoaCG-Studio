# Fix #2565 evidence: an edit made while the page reads teammates' changes is kept

Scoped fix inside the live-publishing run (#2361), before phase 8's AC-6 lands: phase 8's
five-person check hits it (an editor typed `#9`, the team's record kept `#7`, on every page).
Review class: Risky (other writers; reload and recovery of a team production's edits).
Previous verified `main`: 1b7e067c537d567e119c5f886b22f521b2a80503. Revert: `git revert -m 1 <this pull
request's merge commit>`; nothing persisted changed, so no data step goes with it.

## Cause

`refreshOnce` in `src/backend/teamProductions.ts` reads the teams, then decides which productions
hold an edit on its way up (`keep`, from `dirty` and `inflight`), then awaits the documents of every
other production whose token moved. An edit made during that await (typing into a cue, preparing a
message) marks its production dirty, but the code after the await still uses the `keep` taken
before it:

- it sets the fetched document and token as that production's base, so the edit's save goes up
  with the newer token and is accepted without a merge;
- it applies the fetched record over the page's record (`applyServerTeamShows(records, keep)`), so
  the edit is gone from the page, and the save sends the server's text. This rewrites every listed
  production outside `keep`, not only the fetched ones: an edit to a production whose token did not
  move is put back to its own base's text.

The save timer is 600 ms and the read can take longer (each row's files are read back), so an edit
made during the read can also be saved, accepted or refused, before the read answers. The
production is then neither dirty nor in flight, and the read moves its base back to the older row
and puts the teammate's text back on the page.

The team read runs on a 15 s poll, on window focus and when the page comes back online, so the
window opens whenever someone clicks into a window and types while a teammate has just saved.

## Rules (observable; stated before the code)

- **F1.** An edit made to a team production while a team read is out stays on the page: the read
  never replaces the record of a production it still lists and that was edited during it, whether
  or not that production's token moved.
- **F2.** That production's save is judged against the base and token the edit started from, so a
  teammate's save the read saw is merged with the edit (the existing refusal and merge), never
  written over and never dropped. The outbox entry keeps that same base, so a reload restores it.
- **F3.** A production with no edit and no save of this tab during the read takes the read's
  document, base and token, exactly as today.
- **F4.** A production that already held an edit when the read began is handled as today: not read,
  kept as the page has it.
- **F5.** The edit reaches the server: a production left dirty after the read is saved, as today.
- **F6.** Nothing else of the read changes: teams, members, heads, and the removal of productions
  the read no longer lists (an edit to one of those during the read leaves the page and stays in the
  outbox, exactly as an edit to it made before the read does today).
- **F7.** A production whose base this tab moved during the read (its save accepted or refused
  there) keeps that base, its page record and the head its save recorded: the read never moves a
  base or a head to an older token.

## Durable check

`scripts/team-save.test.mjs`, the production module's own `refreshOnce` and `pushSave` with the
backend stubbed, asserting the page record, the base and token, and the set the read hands to
`applyServerTeamShows` as the records it must keep:

- an edit made inside the read's await and saved there, first refused and merged, then accepted,
  before the read answers with the teammate's older row (F7).

Each fails without the fix.

## The fix

`refreshOnce` takes the set of productions it must leave alone after the documents' await, not
before: everything dirty or in flight then, plus every production whose base entry or token is no
longer the one it held as the read left (each save, accepted or refused, writes a new entry). It
neither sets a fetched base for those nor replaces their records, and keeps the head this tab's own
save recorded. Nothing else in the read moves. No migration, no persisted identifier, no change to
the save or its merge.

Known and accepted: when a teammate saves again after this tab's save inside the read, the read's
newer row is not taken for that production; the next read (at most 15 s) or this tab's next save,
refused and merged, brings it in. Taking it would mean judging which of two tokens is newer, which
the tokens do not say.

Pre-existing, not changed: an edit to a production the read no longer lists stays dirty, so the
outbox's "no longer accessible" note does not appear for it (the same for an edit made before the
read).
