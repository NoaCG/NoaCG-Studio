# Fix #2565 evidence: an edit made while the page reads teammates' changes is kept

Scoped fix landed inside the live-publishing run (run #2361), after phase 8 found it. Row class:
**Risky** (it changes a state rule of the team save in `src/backend/teamProductions.ts`).

## Cause

`refreshOnce` took `keep` (productions with an edit waiting or on its way up) before
`await fetchTeamProductionDocs(stale)`. An edit made during that await marked the production
dirty, but the fetched document and token still became its base, and `applyServerTeamShows`
replaced its local record with the fetched one, because `keep` was the set from before the await.
The typed text left the page's record, and the save that followed sent the server's text with the
new token.

## Rules (observable; stated for a Risky row before coding)

- **R1, an edit made during the read is kept.** When the document fetch answers, a production that
  has an edit waiting or on its way up at that moment (dirty or in flight), or had one when the
  pass began, keeps both its base and token and its local record exactly as they are. Its save
  goes up with the old token; a teammate's newer save refuses it, and that refusal merges the two.
- **R2, a confirmation during the read is not undone.** A production whose known server copy was
  replaced while the fetch was out (a save of this tab confirmed meanwhile) keeps that newer copy
  and its local record; the fetched row, read before or around that save, is not adopted.
- **R3, nothing else changes.** Every other fetched row is adopted as before: its document and
  token become the base and its local record is replaced.
- **R4, a skipped production is never stuck.** A production skipped under R1 or R2 is fetched
  again on the next pass in which it has no edit owed and its head token differs from the known
  one, so a teammate's change still reaches the page.
