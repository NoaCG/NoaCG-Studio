# Fix #2494 evidence: continuous edits no longer keep the sync running back to back

Scoped fix landed inside the live-publishing run (owner decision 2026-11-13, run #2361), before
phase 8. Row class: **Risky** (it changes sync pacing state rules in `src/backend/`).

Issue (verbatim done-when):
- A pass that ends with newer edits waiting does not start the next pass at once while edits keep
  arriving. It waits for the debounce, or a short minimum gap, so continuous typing costs one pass
  per pause, not one pass per pass.
- Edits are still never lost, and a pass still runs when the edits stop.
- A measurement on the large fixture with edits once a second shows press to ran within the no-edit
  baseline, with the switch off.

## Cause

`src/backend/syncController.ts`, the `finally` block of `syncNow`. When a local edit bumped
`revision` while a pass ran, the success path set `queued = true`, and the `finally` re-dispatched
`void syncNow()` at once. On a large production one pass outlasts the gap between edits, so every
pass ends with a newer edit waiting and the next starts immediately: the sync runs back to back for
as long as the typing continues, each pass re-uploading the whole record, and Takes pressed meanwhile
run 1 to 2 s late instead of under 100 ms.

## Rules (observable; stated for a Risky row)

- **R1, one pass per pause, not per pass.** A pass that ends with only a newer *local-edit*
  revision waiting (no caller is waiting on a receipt) does not start the next pass at once. The
  next pass fires when the edit debounce elapses, `DEBOUNCE_MS` (2.5 s) after the last edit, so
  continuous typing costs one pass per pause.
- **R2, no local edit is lost.** A local edit always arms the 2.5 s debounce in `scheduleSync`,
  and the only things that clear an armed debounce are a pass starting (which then owns pushing up
  to its `startedRevision`) or the debounce firing (which becomes a waiter if a pass is running,
  else starts a fresh pass). So whenever a local edit has advanced `revision` past the last
  confirmed one, a debounce or a waiter is always pending at the `finally`: the latest revision is
  covered, and a pass still runs once typing stops.
- **R3, explicit callers are still answered promptly.** A caller that awaited `syncNow` while this
  pass ran (a deep-link or record lookup, the online handler) is a waiter and still gets its queued
  pass run at once, never deferred. This preserves the deep-link / cross-device contract (`waiting`,
  R2.4, #2153): the signal is `waiting.length > 0`.
- **R4, the chip still settles, and an adopted change runs no local pass.** Once edits stop, the
  debounced pass confirms the latest revision and the status reaches `synced`. An adopted cross-tab
  change bumps `revision` but arms no debounce and is not a waiter: the `finally` runs no pass for
  it, the tab that made the change owns pushing it and broadcasts its confirmation
  (`followOtherTabsConfirmations` settles this tab's chip), which keeps ONE-PASS-PER-CHANGE.
- **R5, a confirmation that lands during this tab's pass is kept, not dropped** (Codex P2 on
  3428c9c3). The handler used to ignore a confirmation while `running`; the old immediate re-run
  hid that. Now it records the revision it arrived at (`confirmedElsewhereAt`), and the pass, when
  it ends with only adopted changes behind it (`!ownChangePending`) and the revision unchanged since,
  settles `synced` without a pass. An adoption after the confirmation still leaves the tab pending
  for that change's own confirmation.
- **R6, a pass that pushed this tab's own edits clears them, even when adopted changes remain**
  (`/so` B on 720e1755). `ownChangePending` used to clear only on a fully confirmed pass, so an own
  edit plus an adoption during its pass ended `pending` with no pass, no debounce and a handler that
  ignored the writer's confirmation (it skips tabs with something unsent). The tab now records the
  revision of its latest own edit (`ownRevision`); a pass that started at or after it clears
  `ownChangePending`. What is left is adopted only, so the
  writer's confirmation settles it, whether it arrives during the pass (held, R5) or after. An own
  edit made during the pass keeps the flag and its debounce. A confirmation is held during any pass
  and judged when the pass ends.
- **R7, only a pass that ends `synced` broadcasts a confirmation** (Codex P2 on 9caec2c6). A
  confirmation names no write (#2499), so a pass that pushed its own edits but ends `pending` on
  adopted ones stays silent: otherwise a third tab that adopted the same unpushed change would
  settle on it. Main never sent one there either (its immediate re-run confirmed the whole library
  first). Test: `a pass that ends pending tells no other tab it confirmed anything` (red on 9caec2c6).
- **R8, adopted changes nobody confirms are settled by one slow pass of this tab's own** (Codex P2
  on 7e929d6c: two tabs that each adopted the other's edit during their own passes both end
  `pending` and wait on each other for ever). A pass that ends `pending` with only adopted changes
  left arms one settle pass, 30 s later (the focus-pass spacing), cancelled by any pass that starts
  and by a confirmation that settles the tab first. Its pass confirms the whole library and
  announces it. At most one per 30 s, so a tab beside another that keeps typing never chains, and
  well inside the 60 s before the chip warns. Tests: `two tabs that each adopted the other's edit
  during their passes do not wait on each other for ever` and `a confirmation that arrives first
  cancels the settle pass` (both red on 7e929d6c, and under each mutation: never arming it, or the
  handler not cancelling it). 25 tests pass.

  **Reassessment** (fourth confirmed finding in one family, Review checkpoints): every finding since
  3428c9c3 has one root cause. A cross-tab confirmation names no write (#2499), and the immediate
  re-run this fix removes used to paper over that. R5 to R7 closed instances. R8 is the class-level
  backstop: whatever the confirmations miss, a tab left `pending` on adopted changes alone is settled
  by its own bounded pass. #2499 remains the precise fix.

## The fix

`syncNow`'s `finally`: when `queued` is set, run the next pass at once only if a caller is waiting
(`waiting.length > 0`). Otherwise do nothing, a local-edit revision bump already armed the debounce
(let it fire: one pass per pause), and an adopted-only bump needs no pass here. Nothing else changed
,  the success path still sets `queued`/`pending`, and the retry, focus, online and auth triggers are
untouched.

## Durable check (cheapest layer)

`scripts/sync-pass-receipt.test.mjs` (Node, transpiles and drives the controller with stubbed
timers and passes, the cheapest layer that proves this pure pacing logic):

- New test `continuous edits during a pass cost one pass per pause, not one pass per pass (#2494)`:
  a page-load pass overlaps three edits; the pass ends with the revision bumped; asserts **no**
  immediate re-run (`passes.length` stays 1, phase `pending`), the 2.5 s debounce armed; firing it
  runs exactly one pass that confirms the revision (`synced`), and the chain ends.
- New test `an adopted cross-tab change during a pass triggers no local pass or debounce (#2494)`:
  asserts the adopted-only bump runs no per-tab pass and arms no debounce.
- Updated `coalesced callers receive the next pass receipt even when newer work starts another
  pass`: the receipt-routing contract is unchanged; the follow-up pass now comes from the debounce
  rather than an immediate re-run.

- New tests for R5: `a confirmation from the writing tab that lands during this tab's pass settles
  it when the pass ends` and `a held confirmation does not cover an adoption that came after it`.
  Dropping the held confirmation reddens the first alone; ignoring the revision guard reddens the
  second alone. 19 tests pass with the fix.

- New tests for R6: `own edit pushed, adopted change behind it: the writer's later confirmation
  settles the tab`, `own edit pushed, adopted change confirmed during the pass: the pass ends
  synced` (both red on 720e1755), and `an own edit made during the pass is not covered by a held
  confirmation`. 22 tests pass; against main's controller 8 fail (it runs the extra pass these
  rule out). With R7: 23 pass.

Mutation proof (before R5): replacing the `finally` deferral with the original unconditional `void syncNow()`
reddens 3 tests (`continuous edits …`, `coalesced callers … newer work`, the adopted-change test);
re-adding a `!debounce` fallback that arms a pass for an adopted-only bump reddens the adopted-change
test alone. With the fix all 17 pass. `tsc` and `eslint --max-warnings 0` clean.

The existing configured spec `e2e/configured/sync-one-pass-per-edit.spec.ts` is unaffected: each of
its scenarios drives `syncNow()` explicitly (a waiter → R3) or a single debounced pass, so none
relied on the pass-to-pass chain.

## Measurement (acceptance criterion 3), handed to the coordinator

Criterion 3 asks for a before/after measurement on a production build with the large fixture, edits
once a second and Takes pressed (press-to-ran within the no-edit baseline, switch off, p50/p95 and
saves per minute). That exact harness is the continuous-edit case `MEASURE_EDIT=cues` on the
`autopublish` test, it lands with **phase 6 (PR #2488)** and is **not on main**. On-main
`e2e/configured/measure/baseline.measure.ts` only performs a single owed edit (`owedEdit`), which
cannot reproduce the once-per-second storm that is the bug's precondition, so the before/after
cannot be produced from main without pulling #2488's unmerged harness, which this fix must stay out
of. The causal link the measurement would confirm is already established by the issue's own phase-6
probe (28 chained passes → press-to-ran 84–1740 ms; no chain → under 100 ms), and this fix removes
the chain, proven deterministically above. Recommendation: the phase-6 measurement (its harness,
which found the bug) re-runs on this fix to record the confirming numbers. Flagged to the coordinator
in the receipt.
