# Fix #2616 evidence: a 60-graphic publish writes the output once, without reading it back

Scoped fix inside the live-publishing run (#2361). The phase 9 load diagnosis
(`phase-9-load-diagnosis.md`, section 2) found that the whole publish write, `writeControlShow` in
`src/control/hostedControl.ts`, took 1,081 ms locally and 3.4 to 5.6 s on idle staging at 60
graphics, and passed the 8 s statement limit once anything else ran. Review class: Risky (a
live-path migration on `control_shows`, and the publish's compare-and-set).

## Cause

One `UPDATE control_shows SET output = <5 MB> WHERE id = ... AND output->ver->>n = <n>`:

- the filter `output->'ver'->>'n'` decompresses the whole stored output to read one number, though
  0118 keeps that stamp in `published_ver`;
- the BEFORE triggers compare or copy the 5 MB value: `control_stamp_audio_owner` compares the new
  output with the stored one (decompressing it), `production_authoring_guard` copies the row into a
  record variable and returns the copy, and an unmarked request compares the whole output;
- compressing and writing the new value with pglz, the column's default method.

## Measured before the fix (local stack, 4 CPUs)

Instrument (Method, below): the publish write through PostgREST as the configured suite's local
account (`e2e-s1@noacg.local`), the same statement and filter as `writeControlShow`. The payload is
the phase 9 step 7 production, built by the app's own builders as `_five.ts` builds it: Hairline
lower thirds and one House Score, 0.56 MB at 6 graphics and 5.09 MB at 60 (the diagnosis: 0.58 and
5.12 MB), stored at 2,128,501 bytes with pglz (the diagnosis: 2,155,401). Each write moves the stamp
and adds one cue, as a publish does. Nine writes per run, two runs.

| graphics | REST end to end, median | in the database (pg_stat_statements mean) |
|---|---|---|
| 6 | 44 / 80 ms | 28.0 / 28.2 ms |
| 60 | 324 / 338 ms | 235.1 / 239.5 ms |

EXPLAIN (ANALYZE, BUFFERS) of the same 60-graphic UPDATE as the signed-in role: 178 ms in all; the
filter on `output->'ver'->>'n'` 15.4 ms (1.3 ms on `published_ver`); triggers
`control_stamp_audio_owner` 14.5 ms, `control_publication_guard_b_output` 7.0 ms,
`control_shows_set_updated_at` 3.9 ms, `control_shows_production_authoring_guard` 3.4 ms (a plain
call; more through REST unmarked). The rest, about 135 ms, is compressing and writing the new
value; PostgREST's parse of the 5 MB body adds about 60 ms to the statement.

**Scale.** This machine writes the same 60-graphic payload in 331 ms where the diagnosis's local
machine took 1,081 ms, and idle staging 3,381 to 5,602 ms: staging is 10.2 to 16.9 times this
machine for this write. The diagnosis's per-part figures (293 ms filter, 90 to 108 ms per trigger)
are about 7 to 25 times these, so the same parts are what move.

## Rules (observable; stated before the code)

Guarantees kept exactly, except the one case R2 names (a stamp an owner wrote by hand):

- **G1 (0118, a publication never replaces a newer one).** For any write naming `output`, insert or
  update: `published_ver` becomes `output->'ver'`; a `ver.r` above the record's saved revision is
  refused ("This publication names a save that does not exist"); a `ver.r` below the stored
  `published_rev` writes nothing (no row); no `ver.r` with `auto_publish` on and a stored
  `published_rev` is refused ("Reload this page to edit"); no `ver.r` otherwise lands and clears
  `published_rev`. A write naming `published_rev` alone moves it only up and never past the
  record's revision. A write naming neither column runs neither check. No change to 0118's
  functions or triggers: `control_publication_guard_b_output` still copies the row (it must set
  two columns), as `control_shows_set_updated_at` does (a function every table shares).
- **G2 (0120, publications in parts).** `control_publish_parts` keeps its compare-and-set on
  `published_ver->>'n'`, still writes `output` whole with every image inline, and every reader of
  `output`, `published_head` and the parts sees the same values as today. No change to 0120.
- **G3 (0076 and 0108, the audio owner).** On insert the audio owner is the caller, else the
  production's owner. On an update naming `output` or `audio_owner_id`, the audio owner becomes the
  caller (else the stored audio owner, else the owner) when the output or the audio owner changed;
  a write naming neither never moves it.
- **G4 (0115, edits from a page opened before production copies).** An authenticated API request
  without the mark, with `production_copies` on, is refused when it changes a production's output,
  panel, title, profile, bindings, collections or sources other than a Pause or Resume; every other
  write passes, on documents, team productions and control shows alike. Only the control_shows
  branch changes (R2); the documents and team_productions branches stay as they are, and nothing
  outside that branch names `published_ver` (those tables have no such column).

What changes:

- **R1. The press reads and filters the stamp from the same small column.** The whole-publish press
  (`publishControlShow` with `partial_writes` off) reads the stored stamp from `published_ver`
  instead of `output->'ver'`, and its write lands only where `published_ver->>'n'` is that stamp's
  `n` (`published_ver is null` where it read none), as an automatic publish (`publishRevision.ts`)
  and a publish in parts (0120) already do. Read and filter use one column, so a row on which the
  two disagree still publishes. The scenes and the panel are read as today (scenes from `output`).
  An instance without `published_ver` (behind 0118) answers SQLSTATE 42703 naming that column; then,
  and only then, the read and the write use `output->'ver'` as before, from then on for that page.
  The fallback sits inside the read and inside `writeControlShow`, so it runs before, and
  separately from, the existing retries for `collections`, `profile` and `sources`. Any other error, a refusal
  (P0001) among them, is reported as today and never retried by this fallback. The first publish
  (an insert) is unchanged.
- **R2. A moved stamp counts as a changed output.** In `control_stamp_audio_owner` and in the
  control_shows branch of `production_authoring_guard`, a write whose new `published_ver` differs
  from the stored one (compared whole, `is distinct from`) is treated as changing the output without
  opening the stored value; equal stamps compare the whole output as today. This rests on the
  trigger order: triggers fire by name, so `control_publication_guard_b_output` sets the new
  `published_ver` before `control_shows_production_authoring_guard` and `control_stamp_audio_owner`
  read it. The stamps can differ while the outputs are equal only on a row whose `published_ver` an
  owner wrote by hand (the row policy allows it, no page does), and then the result is an extra
  stamp naming the caller or an extra "Reload this page to edit" for an unmarked page on that
  owner's own row: never a missed stamp, never a change let through. 0120 and
  `control_output_version` trust the same column already. A write naming panel, title or sources
  without output (an unmarked page's Pause) still compares the whole output, as today.
- **R3. No trigger copies the row it passes unchanged.** The authoring guard returns the row it
  was given rather than a copy held in a record variable; the audio stamp assigns only when the
  value moves.
- **R4. The output is stored with lz4, in its own migration.** New writes of `control_shows.output`
  compress with lz4. An instance is a Supabase stack, hosted or local, and both have it; on a
  Postgres without lz4 the migration stops whole with "compression method lz4 not supported". (A
  guard in a `do` block would hide the statement from `db:push`'s live-path classifier, which reads
  top-level statements only, so the change would not wait for the quiet window.) Values
  already stored stay readable and change method on their next write. Every reader of `output`
  (outputs, `control_output_audio_manifest`, the OGraf route, the 0118 and 0120 functions) sees the
  same JSON. `ALTER ... SET COMPRESSION` takes an AccessExclusiveLock for an instant (measured with
  `pg_locks`), behind `lock_timeout` 2 s and the quiet window. Cost: lz4 stores a little more
  (stored sizes before and after go in this file). Revert: `set compression pglz` in its own file;
  lz4 values already written stay readable on any server built with lz4. A self-hoster restoring a
  dump onto a server without lz4 uses `pg_dump --no-toast-compression` (supabase/README.md).
- **R5. Old pages keep working.** No signature, column, grant, policy or trigger condition changes;
  a page that still filters on `output->ver->>n` lands as today, only faster.
- **R6. Tests.**
  - Red without the fix in the build (CI): `scripts/publish-write.test.mjs` drives
    `writeControlShow` and the press's stamp read with a recording client. Neither names
    `output->ver` in a select or a filter; on 42703 naming `published_ver` both fall back once; on
    P0001 or any other error nothing is retried. Mutation: put back `output->ver->>n` in the
    filter (two of four tests fail).
  - Red without the fix in the database: 0121's self-check counts TOAST index scans of the stored
    output (`pg_stat_get_xact_numscans`) for two writes of the same size, one moving the stamp and
    one keeping it. A plain call: keeping it scans exactly once more than moving it (the audio
    stamp's comparison). An unmarked signed-in request: moving it scans as many times as the plain
    call (the guard adds none) and keeping it once more than the plain call (the guard's
    comparison). Each trigger is isolated: on 0076's stamp alone, on 0115's guard alone, and on
    both, the check fails (measured: plain 3/3 and unmarked 3/4; plain 2/3 and unmarked 3/4; plain
    3/3 and unmarked 4/4). It also calls every G3 and G4 branch (these pass on the old functions
    too) and asserts the trigger order R2 relies on. **No CI gate runs it**: in CI the migrations
    apply before the accounts exist, so it skips. It runs at every hosted apply (staging, then
    production) and on a local stack with accounts, and was run here against the old functions.
  - In CI, the configured `publish-guard.spec.ts` (the whole configured set is selected by
    `supabase/`) drives the press's compare-and-set end to end: a publish landing between a page's
    read and its write is published over once, and 0115's guard on every route.
- **Target, measured before and after on this machine with the same instrument.**
  - The 60-graphic write, REST end to end, times 16.9 (the worst staging ratio above) is under 4 s,
    half the 8 s limit. Before: 331 ms, 5.6 s, which fails it.
  - The in-database statement and the end-to-end write are both lower at 6 and at 60 graphics.
  - Expected saving per part at 60 graphics, from the EXPLAIN above: the filter about 14 ms, the
    audio stamp about 14 ms, the authoring guard about 3 ms plain (more unmarked), and lz4 most of
    the 135 ms of compressing and writing. guard_b and `set_updated_at` keep their copies (G1).
  - Staging is measured again after landing; that is a check of the scale, not the acceptance.

Not in scope: parsing the 5 MB body (PostgREST, about half the statement here), the press's read of
`output->'scenes'` (its own statement), and publishing in parts by default (`partial_writes`, not
this fix's switch).
