# Fix #2616 evidence: a 60-graphic publish writes the output once, without reading it back

Scoped fix inside the live-publishing run (#2361). The phase 9 load diagnosis
(`phase-9-load-diagnosis.md`, section 2) found that the whole publish write, `writeControlShow` in
`src/control/hostedControl.ts`, took 1,081 ms locally and 3.4 to 5.6 s on idle staging at 60
graphics, and passed the 8 s statement limit once anything else ran. Review class: Risky (a
live-path migration on `control_shows`, and the publish's compare-and-set).

## Cause

One `UPDATE control_shows SET output = <5 MB> WHERE id = ... AND output->ver->>n = <n>`:

- the filter `output->'ver'->>'n'` decompresses the whole stored output to read one number, though
  0118 keeps that stamp in `published_ver`;
- the BEFORE triggers compare or copy the 5 MB value: `control_stamp_audio_owner` compares the new
  output with the stored one (decompressing it), `production_authoring_guard` copies the row into a
  record variable and returns the copy, and an unmarked request compares the whole output;
- compressing and writing the new value with pglz, the column's default method.

## Measured before the fix (local stack, 4 CPUs)

Instrument: `scratchpad/publish-bench.mjs` style, kept in this file's Method section below. The
publish write through PostgREST as the configured suite's local account (`e2e-s1@noacg.local`),
same statement and filter as `writeControlShow`, payload a tree of small values per graphic (layers,
keyframes, fields) of about 89 KB, 5.32 MB at 60 graphics, stored at 1.35 MB.

| graphics | REST end to end, median of 9 | in the database (pg_stat_statements mean) |
|---|---|---|
| 60 | 600 to 613 ms | 333 ms |

EXPLAIN (ANALYZE, BUFFERS) of the same UPDATE as the signed-in role, 60 graphics: 145 ms in all;
the filter 9.6 ms (1.1 ms on `published_ver`); triggers `control_stamp_audio_owner` 10.2 ms,
`control_publication_guard_b_output` 9.3 ms, `control_shows_set_updated_at` 5.0 ms,
`control_shows_production_authoring_guard` 4.6 ms (11.9 ms through REST, unmarked). The rest of
the statement is parsing the 5 MB body (PostgREST's `json_to_record`, about 190 ms) and
compressing the new value. This machine is faster than the diagnosis's per operation: the
diagnosis's 293 ms filter and 90 to 108 ms triggers did not reproduce here at that size, but the
shares that can move are the same ones.

## Rules (observable; stated before the code)

Guarantees kept exactly:

- **G1 (0118, a publication never replaces a newer one).** For any write naming `output`, insert or
  update: `published_ver` becomes `output->'ver'`; a `ver.r` above the record's saved revision is
  refused ("This publication names a save that does not exist"); a `ver.r` below the stored
  `published_rev` writes nothing (no row); no `ver.r` with `auto_publish` on and a stored
  `published_rev` is refused ("Reload this page to edit"); no `ver.r` otherwise lands and clears
  `published_rev`. A write naming `published_rev` alone moves it only up and never past the
  record's revision. A write naming neither column runs neither check. Unchanged: no change to
  0118's functions or triggers.
- **G2 (0120, publications in parts).** `control_publish_parts` keeps its compare-and-set on
  `published_ver->>'n'`, still writes `output` whole with every image inline, and every reader of
  `output`, `published_head` and the parts sees the same values as today. Unchanged: no change to
  0120's functions, tables or grants.
- **G3 (0076 and 0108, the audio owner).** On insert the audio owner is the caller, else the
  production's owner. On an update naming `output` or `audio_owner_id`, the audio owner becomes the
  caller (else the stored audio owner, else the owner) exactly when the output or the audio owner
  changed; a write naming neither never moves it.
- **G4 (0115, edits from a page opened before production copies).** An authenticated API request
  without the mark, with `production_copies` on, is refused exactly when it changes a production's
  output, panel, title, profile, bindings, collections or sources other than a Pause or Resume;
  every other write passes as today, on documents, team productions and control shows.

What changes:

- **R1. The press's compare-and-set reads the small column.** A whole publish over an existing row
  lands only where `published_ver->>'n'` is the stamp the press read (`published_ver is null` where
  it read none), as an automatic publish (`publishRevision.ts`) and a publish in parts (0120)
  already do. Same rows as `output->ver->>n`, because G1 sets `published_ver` from `output` on every
  write that names it. On an instance without `published_ver` (behind 0118) the press retries once
  with the old filter, so publishing does not start failing there.
- **R2. No trigger reads the stored output to learn whether a publish changed it.** When the new
  stamp differs from the stored one, the output changed (G1 keeps each stamp equal to its output's
  `ver`): G3 and G4 decide on that and never open the stored value. Only when the stamps are equal
  (a page from before stamps, a resend of the same stamp) do they compare the whole output, as
  today. This can only stamp the caller or refuse where today's comparison would also, given G1.
- **R3. No trigger copies the row it passes unchanged.** The authoring guard returns the row it
  was given; the audio stamp assigns only when the value moves.
- **R4. The output is stored with lz4.** New writes of `control_shows.output` compress with lz4
  where the server supports it (hosted and local Supabase do), faster to write and to read; values
  already stored stay readable as they are and change method on their next write. Where lz4 is not
  available, nothing changes. Every reader sees the same JSON.
- **R5. Old pages keep working.** No signature, column, grant, policy or trigger condition changes;
  a page that still filters on `output->ver->>n` lands exactly as today, only faster.

Target: a 60-graphic whole publish well under the 8 s hosted limit with staging 4.5 to 8 times
slower than local, measured before and after at 6 and 60 graphics on the local stack.

Not in scope: parsing the 5 MB body (PostgREST, about half the statement here) and publishing in
parts by default (`partial_writes`, not this fix's switch).
