the 10-page run lost the last text of up to 6 of 7 editors.
Review class: Risky (other tabs and writers; the cue draft's save; the undo history).

## Cause

`src/components/home/useRundownHistory.ts` keeps the production page's undo history. When the
rundown changes elsewhere (another tab's save, a teammate's save the page adopts), the history can
no longer be trusted, so it is cleared with the note "changed elsewhere". Two places do that, and
both also throw away the cue being typed:

- `reconcile`, run on every team state change and every `spx-data-changed`, finds the rundown no
  longer equal to the open typing group's slice (or to an unconfirmed team edit) and calls
  `invalidate()`, which calls `cancelDraft()`: the typed text leaves the screen, nothing is unsent,
  and the next save sends the old text.
- `perform`, the draft's own queued write, finds the same mismatch, calls `invalidate()` and returns
  without writing. A draft write queued before another invalidation is dropped by the queue itself
  (its epoch moved), so the text is never written.

A teammate editing any other cue is enough. The more people edit, the more often it happens.

Reproduced on `main` by the new test in `e2e/rundown-history.spec.ts` (below): "Typed here" reverts
to "Alpha" when another cue is renamed elsewhere.

## Rules (observable; stated before the code)

"The cue being typed" is the cue of the open typing group. Its text is its label, note and values,
the three things the draft writes (`fieldsOf` in `control/cueDraft.ts`). "Left as it was" means
those three are what the history expected and the cue still exists; a move or a folder change of
that cue, and any change to another cue, a graphic or a server item, count as a change elsewhere.

- **D1.** A change made elsewhere (another tab, a teammate) that leaves the cue being typed as it
  was never discards the typed text: it stays on screen and is saved over the new rundown, changing
  only that cue's text; every other change made elsewhere stays. This holds for every later change
  too: after each one, "as it was" is judged against the rundown accepted then.
- **D2.** Such a change still clears the undo history, with the same note ("changed elsewhere") at
  each change, as today.
- **D3.** A change made elsewhere to the text of the cue being typed (its label, its note or any of
  its values, including a value the typist did not touch, since the draft writes the whole values
  map) or its removal is handled as today: the typed text is discarded and the note says the
  rundown changed. Which of two texts typed into one cue should win is the owner's to decide (O10);
  this keeps today's answer.
- **D4.** Undo and redo behave as today: the typed text is first saved, then the step is undone or
  redone, and the draft is discarded.
- **D5.** Text kept by D1 reaches the record with no further typing, whether the change elsewhere
  arrived before its save, while the save waited in the page's write queue, or while the save
  (a team production's included) was out; and the page then shows nothing unsent.
- **D6.** Nothing else changes: every other write (Delete, Duplicate, a move, a restore) still
  refuses and clears the history when the rundown changed under it. The draft's save still needs
  the same production identity and an account allowed to write; account pausing and leaving the
  production behave as today.
- **D7.** After a change elsewhere, Undo never reverts it: the typing that goes on is a step whose
  start already holds the change.

## The fix

All in `src/components/home/useRundownHistory.ts`, with one pure key in `src/model/rundownHistory.ts`
and the cue id passed to the draft's save from `ProductionPage.tsx`:

- `cueTextKey(slice, cueId)`: the typed cue's label, note and values as one key, null once the cue
  is gone; `typedCueUnchanged` compares two slices by it (D1, D3).
- The hook keeps **the typing**: the typed cue and its text as this page last knew it. It is taken
  when typing starts on a cue, moved by every write of this page that storage accepted (a Delete
  of that cue ends it), kept through each change elsewhere that leaves that text alone (D1,
  repeated changes), and cleared when the typing is discarded. Every decision compares against it,
  never against a typing group's slice. The typed cue's own text is checked on its own only between
  a kept change and the next accepted write, when the history expects nothing (D3).
- `invalidate` clears the history as before and discards the typing only when asked: every path
  that clears it because of a change made elsewhere (`reconcile`'s two branches, `perform` at its
  start and after its awaits, a team confirmation that found this save merged with a teammate's,
  `closeGroup`) keeps the typing when its text is as the page last knew it (D1, D2). A change to
  that text since then, even after an earlier kept change, discards as today (D3).
- A cleared history drops the typing group; later typing starts a group whose start holds the
  change (D7), and a queued draft save whose group was cleared is judged against no stale slice.
- The draft's save in the page's write queue is no longer dropped because the history was cleared
  meanwhile; it is dropped only if the typing was discarded since it was queued (D3, D5). Its
  failure is reported even then.
- A stored typed text counts as sent (nothing unsent) when the rundown changed elsewhere while its
  save was out and the save itself did not fail, or when the team confirmed a revision that holds
  it merged with a teammate's change. A storage or network failure, or a refusal, is as today (D6).
- The same save no longer clears the "changed elsewhere" note it has just set (D2).

No migration, no persisted identifier, no change to what is saved or sent to air.

## Fresh drafts after a live edit

On the exact failing PR merge, the quiz's own live action edited the stored cue between
drafts. The next question draft was compared against the preceding draft's text, and Update
discarded it as a change from elsewhere. The same quiz assertion passed on the first parent.

Use the cue text that seeds a fresh draft for its conflict check, including when it reuses
an open undo group. A continuing draft keeps that baseline across field changes or a
rundown change elsewhere. Leave live-action persistence outside preparation undo. The
existing quiz must air the new question, a change elsewhere must keep the draft, and a
change to the typed cue must still win. Accepted and refused writes retain their behavior.

## Queued drafts and storage conflicts

A save keeps the cue and baseline of the draft that queued it. An accepted write can
advance that draft's baseline. A refused write keeps its last accepted baseline. A
same-cue conflict clears undo and only cancels the active draft if its own text conflicts.
A queued write loses its authority when its production or account session ends. The notice
of a remote change stays through the automatic save that preserves the draft.

For a personal draft, compare the cue text again in the existing rebased storage write.
For a team draft, preserve its text through the existing save retry when the teammate
left its cue text alone. The pending edit records which text came from a checked draft.
If the cue is gone, either text changed outside the draft, or the resulting text would
write a connected field, the draft cannot overwrite the teammate's record. The original
quiz assertion and the existing rundown and refusal journeys still have to pass. A held
save, cue switch, page exit and same-cue metadata change exercise these rules.

### Writes that overlap

Closing or pausing uses the exact locally staged text of the same draft as a predecessor
when the local record still holds it. Storage receipts confirm the local write separately
from the team server. Browser exit keeps the existing recovery record until local storage
accepts the text.

Keep an exact checked draft transition across a preceding ordinary team save. Apply the
team merge exception only after the server document holds its starting text. For the
personal storage transaction, a later whole-record write cannot commit from an optimistic
predecessor that was refused or rebased to different text. A later cue edit can be applied
to the stored document when that cue still holds the text it read.

### Who may carry a draft through a team retry

A team controller may use its own checked draft history, including pending work restored
after adopting its exact local record. An ordinary text write ends that cue's draft
history. Returning to the same text does not revive it. The controller cannot borrow a
draft from another tab's pending record. A browser exit keeps the owed edit when a local
storage receipt is missing.
