# Fix 2667: the 60-graphic publish write sent every script twice

Issue #2667: on hosted staging a 60-graphic team publish (team_designs and production_copies on,
auto_publish and partial_writes off) took 64 s once and failed twice with "canceling statement due
to statement timeout" another day. Run issue #2361. Measured 2026-11-21 on the local stack.

## Answer in short

The press makes two kinds of large request: the team record's first split save (all 60 designs,
six `team_designs_put` calls of up to 1 MB) and the publish write to `control_shows`. Locally the
publish write is the statement nearest the 8 s limit. It sent 9.7 MB, and 4.6 MB of that was the
`panel` column repeating each graphic's script (about 76 KB per lower third) beside the payload's
own copy. PostgREST parses the whole request body inside the statement, so the statement grows with
the bytes sent: 3.0 to 3.4 s at staging-like slowness, before any other load. Nothing reads the
panel's script since the hosted control page was retired (docs/work-specs/retire-hosted-control). A
publish now leaves it out: 5.1 MB, 1.0 to 1.7 s.

Which statement timed out on staging is inferred, not observed: the failing run kept no trace, and
the error text does not name the request. The design puts are the other candidate. On staging a
1 MB put took up to 6.4 s, while a 5.1 MB document sync from the same page was still running. So
puts now go in batches of at most 500 KB as well (G5 R15 allows up to 1 MB): 0.1 to 0.3 s each at
0.1 CPU instead of 0.6 to 0.75 s, and 2.4 s for all 60 designs instead of 3.7 s.

## How it was measured

- Local stack: Supabase CLI 2.111.0 through `scripts/configured-stack.mjs`, all migrations, the
  configured suite's local account. Role limits as hosted: `authenticated` statement_timeout 8 s.
- Staging-like slowness: the database container limited to 0.1 CPU (`docker update --cpus 0.1`).
  At that limit a 5.1 MB team record insert takes 2.8 s in the database, about 9 times the 4-CPU
  time, a little slower than staging's 4.5 to 8 times (phase-9-load-diagnosis.md section 5).
- Requests: the step-7 bodies taken from the trace of staging run 44892116622 (`hosted-results-1`),
  replayed as the signed-in account; and the real page, a 60-graphic team production built as the
  phase 8 scene builds it, one Publish press, every backend request timed. Statement times from
  pg_stat_statements; the update broken down with EXPLAIN (ANALYZE, BUFFERS).
- Staging was not run: no staging switch was touched.

## Where the press's time goes (0.1 CPU, first publish, 60 graphics)

| From the press | team_designs on | team_designs off |
|---|---|---|
| team record save | 6 `team_designs_put` (0.4 to 1.2 s each, 5.1 MB in all), then `team_production_store` (26 KB, 0.1 s) | one `team_production_save_v2` (5.1 MB, 2.3 to 2.6 s) |
| browser work before the publish read | about 8.5 s (production gate and payload build for 60 graphics; no request) | about 8.5 s |
| publish write before | 9.7 MB, 3.6 s request, landed 18.9 s after the press | 9.7 MB, 3.2 s request, landed 17.4 s after the press |
| publish write after | 5.1 MB, 1.0 s request, landed 14.4 s after the press | 5.1 MB, 1.1 s request, landed 14.5 s after the press |

The save comes with the press because a first publish settles the production's outputs, which
changes the record.

## The statement

pg_stat_statements, 0.1 CPU, the trace's 60-graphic body:

| | before (9.7 MB) | after (5.1 MB) |
|---|---|---|
| INSERT (first publish) | 3.0 s | 1.0 s |
| UPDATE (republish, whole) | 2.9 to 3.4 s | 0.8 to 1.7 s |

The same UPDATE with the values already parsed in the database costs 0.1 to 0.4 s (EXPLAIN
ANALYZE: `control_publication_guard_b_output` 0.2 s, `control_shows_set_updated_at` 0.09 s, the
rest compression). Parsing the 9.7 MB body to jsonb alone takes 1.0 to 1.4 s. So most of the
statement is the body, and halving the body roughly halves it.

The design puts are not near the limit: 0.4 to 1.2 s each at 0.1 CPU for 1 MB. On staging the
trace showed 1.0 to 6.4 s per put, and 15.8 s for the 9.7 MB publish request.

## Why it failed on one day and not another

Staging was slower that day: the failing run's set-up took 634 s against 279 s, and its first
minute had a p95 of 10.5 s per request. With the publish statement at 3 s or more on an idle
staging-like database, a slower moment takes it past 8 s. After the fix the statement has about
five times headroom at this slowness instead of about two and a half.

## Who reads `control_shows.panel`, and whether it needs the script

On `main` at 5634c2f:

| Reader | File | What it reads |
|---|---|---|
| a whole publish, before writing | `src/control/hostedControl.ts` `readPublishedWhole`, `buildPanelSpec` | `entries` of graphics this library lacks |
| a publish in parts | `src/control/hostedControl.ts` `smallPublishedRead`, `publishedPanelEntries`; SQL `control_panel_entries` (0120) | `name`, `entries` |
| automatic publish | `src/control/publishRevision.ts` (`heldPanelIfNeeded`, its digest strips `js`) | `entries` |
| the parts write | SQL `control_publish_parts` (0120) | stores and patches the panel as given |
| the publication guard | SQL 0121 trigger | `panel` unchanged or not, as a whole |
| slug resolve for the production page and outputs | SQL `control_show_by_slug` (0059), `control_show_resolve` (0071); `src/control/hostedControl.ts` `readResolvedShow` | passes `panel` through `readPanel`; no caller reads it (`src/control/sessionWire.ts`, `src/components/home/ProductionPage.tsx` use `output`, `live`, `staged`, `profile`) |
| the data route | `api/_lib/dataIngest.ts` (`PanelGraphicLike`) | `name`, `fields` |

No reader in `src/`, `api/`, `cli/`, `companion-module/`, `player-host/`, `render-worker/` or
`supabase/` reads the panel's `js`. Companion and Stream Deck keys go through the panel relay
(`panel_rows`, fed by the production page), not this column. Edge functions: none in the repository.

**Pages opened before a deploy.** The only reader of the panel's `js` ever was the hosted control
page (`src/components/HostedControlPage.tsx`, lines 480, 598, 951 to 969 and 1942 at bb02ec343^),
removed on 2026-11-10 by bb02ec343. A copy of that page still open from before 2026-11-10, never
reloaded since, would show no event buttons for a graphic after its next publish. Takes, Out and
data do not read the script there. Outputs and renderers read `output`, which still carries every
script. Production pages from 2026-11-10 on read no panel script.

## Not changed here

- The browser's 8.5 s before the publish read is client work, not a statement; on a slower runner
  it adds to the press time but cannot time out.
- The staging press times are not fully explained by these numbers: 64 s on staging against 14 to
  19 s locally, and 213 s before the first failure. Request round trips from the runner, uploading
  about 15 MB, the runner's slower browser and staging's own slow minutes all add to it, and the
  failing run kept no trace to split them. A first-press check on hosted staging, team_designs on
  and off, is still owed.
- With team_designs off, the press still saves the whole 5.1 MB record (2.3 to 2.6 s at 0.1 CPU);
  that is what team_designs exists to remove (#2614).
- Rows published before this change keep the scripts in `panel` until a publish rewrites the
  panel: every whole publish does; an automatic publish of unchanged content writes only the
  revision and leaves the panel as it is.
- An imported OGraf graphic's script is in its package assets, not the payload's `js`; nothing
  read it from the panel either.
