# Fix #2615 evidence: a refused team save answers with its token, and the page reads only what changed

Scoped fix inside the live-publishing run (#2361). The phase 9 load diagnosis (PR #2619,
`phase-9-load-diagnosis.md`, finding 2) found that a team save that loses the compare-and-swap is
answered with the whole stored record (`team_production_save`, `team_production_patch`). With seven
writers on a 60-graphic record, 123 of 144 saves were refused locally and about 630 MB came back in
20 s; on staging, 6 graphics, 91 refusals returned 51.7 MB in 30 s. Each refusal also reads and
builds the whole record inside the database while the landing save holds the row.
Review class: Risky (a migration, and the refused save is a state rule).

## Cause

Both save functions build their refusal from `select *` of the row, document included, and the
page takes the teammate's document from that answer (`saveTeamProduction` and `pushSave` in
`src/backend/teamProductions.ts`). The page usually already holds most of that document: what a
teammate changed since the page last read is a few cues.

## Rules (observable; stated before the code)

- **R1. The refusal.** `team_production_save_v2(p_id, p_expected, p_doc)` and
  `team_production_patch_v2(p_id, p_expected, p_ops)` check, store and answer a landed save exactly
  as `team_production_save` and `team_production_patch` do (signed in, not suspended, a member of
  the team, the same compare-and-swap on `updated_at`, the same `saved: true` answer). A refusal
  answers `saved: false` with `updated_at`, `updated_by` and `rev` of the stored row (and
  `replaced: true` where the patch could not apply, as today), and never the document. Deciding the
  refusal selects only `team_id`, `updated_at`, `updated_by` and `rev`, never the whole row; only a
  patch that is going to be applied reads the document.
- **R2. Old pages, old databases.** `team_production_save` and `team_production_patch` do not
  change: a page built before this keeps getting the document with its refusal. A page built after
  this calls the v2 functions; on an instance without them (PostgREST `PGRST202`) it calls the old
  ones for the rest of the page's session and takes the document from the refusal, as today. A
  refusal that does carry a document is used as today. A `replaced: true` answer means a whole save
  next, as today, never a read.
- **R3. The read.** After a refusal with no document, the page reads the stored record once with
  `team_production_changes(p_id, p_map)`, with `p_map` = `{"f": "s1", "m": {member: entry}}`. A
  map without `f: "s1"`, or one that is not that shape, is read as an empty map (every member set),
  never as an error. An entry is a hex hash string or `{by, order, d}` as G4's `KeyedEntry`
  (`src/backend/unitPatch.ts`); any other entry is malformed and read as missing. One `select` of the row gives the document and its
  `updated_at`, `updated_by` and `rev`, so the answer is one stored version. Its `ops` are G4's
  `PatchOp`s (`src/backend/unitPatch.ts`) from `p_map` to that document, the way `diff` builds them:
  - Units are G4's: a top-level member, or one element of a keyed list (a non-empty array of
    objects whose `id`, else `key`, else `name` is a unique string, the first that holds).
  - A unit's hash is SHA-256 (`pg_catalog.sha256(convert_to(<unit>::text, 'UTF8'))`) of its stored
    JSON text, first 128 bits, hex.
  - A plain member whose hash differs from the map's entry is `set`, with `u` its hash.
  - A keyed list whose map entry is a keyed entry with the same `by` is answered as `put` (each
    element whose hash differs or is new, with `d` its hash), `del` (identities in the entry's
    order that the list lacks), `order` (always) and `len` (always).
  - A member whose map entry is missing, of another shape (a hash against a keyed list, a keyed
    entry against a plain value) or keyed by another `by`, is `set` whole, with `u` its full entry.
  - A member the map has and the document lacks is `{m, drop: true}`.
  - A member equal to the map's entry is left out.
  The read runs with the caller's rights: a production the caller's row policy does not show is
  `unknown team production`.
- **R4. What the page sends and keeps.** Per production, the page keeps the stored form (file
  references, not file data) of the last version it read this way, that version's token and the map
  the read answered for it (`applyToMap`). It sends that map; with none, an empty map, and the answer
  is every member set. It applies the answer to the kept stored form with `applyPatch`, which gives
  the stored document of the answer's version, equal as a JSON value (key order not significant).
  Files are then filled in on that result, which `rehydrateSharedAssets` copies, never on the kept
  form. If `applyPatch` refuses (`PatchRefused`), the page reads once more with an empty map. These
  maps are of their own kind (hashes of stored JSON text, `f: "s1"`); they never go into `teamBases`
  or `doc_units`, and G4's maps never go into this read. An answer is applied only to the kept form
  whose map was sent: if that form was replaced, or team sync stopped, while the read was out, the
  answer is dropped and the attempt fails as in R6. The kept forms live in memory only (no persisted format) and are dropped when team sync stops.
- **R5. The merge.** The page merges exactly as it does with a refusal's document today, using the
  document read and the token read. That token may be newer than the refusal's; it is never older,
  and the document and token always belong to the same stored version. A refusal and its read count
  as one of the `MAX_SAVE_ATTEMPTS` (4, unchanged). Undo (`restoreTeamRundown`) reads the same way,
  and its shape check runs on the document read.
- **R6. A failed read.** A read that errors, answers with no token, or whose answer is dropped
  (R4) fails that save attempt as a save with no answer does today: the edit stays dirty and on
  screen, the failure is shown, and the save goes again on its own timer (#2618). Nothing typed is
  dropped. For Undo it answers `failed` with its existing message ("Undo was not saved to the
  team." or the read's error), and the rundown is not changed.
- **R7. Size.** A refusal answer is under 1 kB whatever the record size. A read answers only the
  units that changed since the version the page last read this way, plus the order and length of
  each keyed list that changed. The kept form moves only on a read, never on the page's own landed
  saves, so those saves' units come back too, and the first read of a production in a page's
  session sends an empty map and answers the whole record. The database still reads and hashes the
  whole record per read, but takes no row lock.
- **R8. Rights.** EXECUTE on the three new functions is granted to `authenticated` only, never to
  `anon` or `public`, and the migration's self-check asserts both, then calls each on a throwaway
  row when an account exists (refusal shape, landed save, a read with an empty map and with the
  answered map).
- **R9. Nothing else.** The landed save, the patch building and the unit maps of 0119
  (`doc_units`), the poll's reads, publishing and the switches (`auto_publish`, `partial_writes`,
  `production_copies`) are unchanged. The migration adds functions only; it names no `control_*`
  object and none of the live-path helper functions, so it is not a live-path migration.
  Revert: drop the three functions; pages fall back to the old functions (R2).

## Acceptance

- **The real read against an oracle (configured suite, local stack).** Several writers make random
  edits through the real functions (cue text, a cue added, removed or moved, a graphic changed, a
  plain member changed or dropped, a list that changes keying). After each landed save, a reader
  holding an older kept form reads with its map: `applyPatch` of the answer on the kept form equals
  the stored document as a JSON value, and the members and elements the ops name are exactly those
  `diff` (`src/backend/unitPatch.ts`) finds changed between the two versions (a keyed list's order
  alone may name the member with no `put`). Red when the read ignores `p_map`, and red when it
  leaves a changed element out.
- **The controller (Node test, `scripts/team-save.test.mjs`).** A refusal with no document reads
  with the kept map, merges and saves; the old answer with a document still works; a dropped or
  failed read fails the attempt and keeps the edit; `PGRST202` from a v2 function switches the page
  to the old functions for the rest of its session and takes the document from the refusal. Red
  without the fix.
- **The scene, before and after, on the local stack** (the diagnosis instrument's seven writers
  saving every 600 ms for 20 s, each typing its own cue, at 6 and 60 graphics). Pass bars:
  - every refusal answer under 1 kB;
  - bytes returned to refused writers at most one whole record per writer plus the changed units;
  - landed saves not fewer than before;
  - no reader waits on a row lock (the read takes none): `pg_locks` held by the read's backend,
    sampled during the scene, show no row-level lock on `team_productions`;
  - zero lost edits: each writer's last text is in the final record.
- **The seven-typist page scene** (phase 8's `five.measure.ts` with ten pages, seven editors) on
  the local stack after the change: every editor's last text in the record, the publication and
  every page.
