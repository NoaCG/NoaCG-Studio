# Put a ready SPX rundown in the production export

**Filed:** 2026-09-30. **Source:** the playout target research,
[`PLAYOUT_TARGETS_RESEARCH.md`](../PLAYOUT_TARGETS_RESEARCH.md) §2.5 and §4 (SPX route 2).

## Why

An SPX operator works from a rundown. NoaCG's production export already writes one SPX template
folder per graphic in rundown order (`src/export/showExport.ts`), but the operator still builds the
rundown by hand and types every entry's values again. SPX keeps a project as
`DATAROOT/<Project>/profile.json` and each rundown as `DATAROOT/<Project>/data/<Rundown>.json`, one
item per graphic with its template path, playout settings and field values, and its docs describe
the storage as file-system based and open to rundowns generated by another process. SPX Solo, the
free edition, answers 501 to `rundown/json` and most of its API, so writing files is the route that
works everywhere. This turns "NoaCG exports SPX templates" into "NoaCG hands SPX the show".

## What it would take

- In the SPX flavour of the production export, add a `DATAROOT/<production>/` folder: a
  `profile.json` listing the templates, and one rundown JSON with an item per cue, its `DataFields`
  values taken from the cue's saved entry and its layer from the pool's layer order.
- Match the shape of SPX's own sample
  (<https://raw.githubusercontent.com/TuomoKu/SPX-GC/master/DATAROOT/MyFirstProject/data/MyFirstRundown.json>),
  and say in the README where each folder goes.
- Solo allows five layers; a production with more says so in the README rather than failing.
- Proof: a test that checks the written rundown against the sample's shape, then the SPX round
  (`spx-gc-ograf-round.md`) loads it on a real SPX.

- SPX Solo API limits, <https://raw.githubusercontent.com/TuomoKu/SPX-GC/master/routes/routes-api-v1.js>
