## Verdict: REVISE

1. The owner's outcomes are right and most of the primitives they need already exist. The
   candidate plan builds a shared content workspace, six format adapters, server-owned
   five-second readers, held-write Pause across two API routes and a field-level snapshot
   isolation rule. Several of those are more than the outcomes need, and two contradict each other.
2. The paste-to-graphic result needs no refactor phase. Started from the cue editor, the
   destination is explicit by construction, which also removes the #1313 class of fault. It can
   land first, as a small feature change, and students can use it while the refactor proceeds.
3. Of the fourteen refactor phases, the content work depends on phase 1 (the safety net and the two
   suspected defects), phase 7 (the data session) and a props-only cue editor extraction. Phases
   3 to 6, 8 to 12 and 14 are playout maintenance and can follow in their own window.
4. Snapshot protection should not restrict `/update` or refuse later bindings. A prepared cue is
   already plain values; the one route that can override it is a live binding on the destination's
   fields. Keep bound fields out of message destinations and the problem is gone.
5. Sheets: a browser reader at five seconds while a page is open, a server fallback at about a
   minute when none is, both honest about what they promise. Measure before promising ten seconds.
6. YouTube: keep the browser live-chat reader, add one-shot video comments (1 quota unit), decide
   the history page deliberately, defer server-side intake and all new Twitch work.
7. The acceptance criteria prove implementation contracts well and user outcomes thinly; add
   comprehension checks, list-graphic output checks on a real player and a bindings migration test.

## 2. Independent model, and how it compares

### 2.1 The independent proposal in one paragraph

Two words for the operator: **Fill** and **Follow**. Fill copies content into a cue once (paste,
a Sheet row, a message, a table row); the cue owns it afterwards, which is what `loadRow` and
"Send to rundown" already do. Follow makes a graphic field track a live value (today's binding to
a production-data path), and a source keeps that value current (API push, Sheet poll, RSS poll,
operator press). The place to do both is the cue editor, where a non-technical operator already
fills fields. A production-level Sources list shows status and Pause. The inbox is one source of
candidates whose only exit is Fill into a compatible graphic chosen explicitly. Appendix A is the
full text as written before reading the specs.

### 2.2 Two viable operator models, compared

**A. Shared content workspace** (the candidate). One Data/Content view listing content sets
(News, Tonight, Match, Messages), each with its source, "Used by" and actions; a Messages view
specialises selection; cue fields also offer Connect.

**B. Field-led with an inbox and a sources line** (this review). The cue editor's field offers
"Fill from…" (Paste, Message, Table row) and "Follow…" (Sheet, Feed, Another system). A Messages
inbox (the trimmed Audience workspace) prepares candidates and offers "Prepare cue on…" with an
explicit compatible picker. Playout shows one line per source with status and Pause. The existing
Data tab stays, trimmed, under Advanced.

**C. The Sheet is the editor** (the owner's R3 question). NoaCG has no data page; every list is a
Sheet tab; the cue field only says "connected to Sheet X".

| Criterion | A. Shared workspace | B. Field-led | C. Sheet as editor |
| --- | --- | --- | --- |
| Steps to paste a message onto a card | Open content, Messages, paste, choose destination, prepare, go to Playout, Take | Select or add the card's cue, Fill from Paste, Take | Not covered; needs a Sheet |
| Destination ambiguity | Needs a picker or a remembered choice; #1313 class stays possible | None: the cue's graphic is the destination | None |
| Teaches a new screen | Yes, one | No; adds a menu where fields already are | Yes, Google's |
| New store needed | A content registry for "sets" | None; cue values, `ShowDataset`, inbox, bindings | None in NoaCG |
| Works without Google or an account | Yes | Yes | No |
| Where live status shows | In the workspace | One line on Playout, plus the field's mark | Nowhere in NoaCG |
| Migration of today's bindings | Name-keyed bindings must map to "sets" | Bindings stay; a connection record is additive | Same as B |
| Risk | Two editable copies of a message (workspace and inbox) unless disciplined | The cue editor grows; preview of a Follow before saving needs care | Formulas refresh hourly; no fast scores |

Recommendation: **B**, with A's one good idea kept: a read-only overview on the existing Data
view that lists each content set, its source and the graphics using it (the second opinion's
"Data" sketch), and Advanced holding paths, seed, Raw JSON and per-field bindings. C is a fine
default for lists, not a product model: scores and messages need NoaCG controls.

The candidate's own prototype phase (15) already asks for this comparison ("Compare this with a
simpler field-led design"). This review's answer is to make B the default hypothesis and let the
trial falsify it, not the reverse.

## 3. Design notes behind the recommendation

### 3.1 Where the destination comes from

In the cue editor the operator has already chosen a cue, and the cue names its graphic. "Fill
from Paste" therefore has no picker: the pasted body goes to the body field by title (Message,
Question, Comment, Body, Text), the optional name to the name field (Name, Author, From, Sender,
Handle, Asked by). If the graphic has neither, the menu item says so and offers to add a question
card (A2) instead of filling the first text field. The inbox's "Prepare cue on…" is the second
door and needs the picker, which lists compatible graphics only, excludes vote boards by
`pollFieldMap`, excludes graphics whose body or name field is bound, remembers the choice per
production, and offers a catalog card when the list is empty (`House Q&A`, `Volt Q&A`,
`Frost Q&A`, `Clean Q&A`, `src/templates/audience/qaCard.ts:128-155`).

### 3.2 One candidate model, durable

Keep `AudienceSubmission` as the candidate record: it already has original and broadcast text,
anonymity, status and usedAt (`audienceTypes.ts:35-53`). Add two additive optional fields:
`externalId` (a Sheet row hash, a YouTube message or comment id) and `source` (a free label such
as "WhatsApp" or "Sheet: Messages"). Make the local provider durable for operator-authored and
imported rows (localStorage keyed by show id, the `productionState.ts` pattern), while simulated
rehearsal rows stay in memory. On a published production, paste and Sheet import go through the
Supabase provider so other operators see them; the `audience_submissions` table
(`0035:90-112`) needs an additive `external_id` column for deduplication.

Alternative considered: messages as a `ShowDataset` of kind `messages`. It is persisted and
importable today, but it has no original/broadcast split, the row matcher would not load into a
Question/Asked by card (`cueData.ts:85-87`), and published productions would then hold messages in
two unrelated stores. Not recommended.

### 3.3 Formats: the Sheet mirrors the graphic's own text

Every list graphic already parses one textarea. The starter rows should be that text, one row per
line, so the operator learns one rule: a row in the Sheet is a line in the graphic.

| Graphic | Field it reads | Row rule | Code |
| --- | --- | --- | --- |
| Ticker | items textarea | one cell; "SPORT: United win" is a kicker, "|" is plain text | `src/templates/tickers/shared.ts:118-157` |
| Schedule | textarea | cells joined " \| "; first pipe splits | `src/templates/infographics/dataRuntimes.ts:40-52` |
| Standings | rows (f2) and column headers (f3) | header row after the first cell fills headers; body rows joined " \| " | `src/templates/competition/results/shared.ts:153-165, 185-186` |
| Credits | textarea | "Role \| Name" is read; a role-only row must become "Role:"; a cell starting with "#" is a heading, so trailing empty cells are trimmed before the join; an empty row is a section break and is kept | `src/templates/endCredits/shared.ts:205-233` |
| Guests, messages | row table | one row loaded or prepared at a time | `cueData.ts`, §3.1 |
| Values | name, value | one row per value | `productionData.ts` |

So the adapter registry is four shapes: lines (with the two credits tweaks and a flag for
"single cell" tickers), standings, row table, values. The "six graphic formats" in the candidate
are these four seen from six catalog types. Node fixtures must include: a credits heading row with
a trailing empty Name cell, a role-only row, an internal blank row, a standings header row, a
ticker row containing "|" and a schedule show name containing "|".

### 3.4 Where a live connection is stored

Keep `Show.bindings` (graphic name, field id, path) as the resolution contract that the page, the
publish and `control_data_patch` already share. Add an additive optional `Show.sources` list:
`{ id, kind, config, paused, label, writes: [{ graphic, graphicId, fieldId, path, shape }] }`.
A source's reader writes the tree under source-scoped paths (`sheet.<id>.rows`), and saving a
connection writes the matching binding entries. Renaming a graphic breaks today's name-keyed
bindings already; the `graphicId` on the source lets a later phase migrate bindings on rename, and
nothing else changes. No `Show.version` bump: both fields are additive optional
(`root/version-every-persisted-format-ship-breaking`).

## 4. Operator walkthroughs

Each walkthrough names what the operator sees and does, what they should expect, what happens when
the source changes after staging or while on air, and which existing or proposed contract makes it
so. "Today" describes `7313cd8`.

### 4.1 Paste a WhatsApp or SMS message

1. Playout tab. The production has a `House Q&A` card. The operator presses "+ cue" on it (or
   selects an existing cue) and, in the cue editor, "Fill from… Paste".
2. A small box: Message (required), Name (optional), a "Show name" toggle and "Anonymous". They
   paste the text and the sender's first name, trim a sentence.
3. The preview shows the card with that text. "Save" writes the cue's values; "Take" airs it.
4. Later: the sender writes again, the operator pastes a new message into a new cue. The first cue
   keeps its text (`shows.ts:70-72`). Nothing can change it except the operator editing that cue.
5. On air: the WhatsApp thread moving does nothing. If the operator edits the on-air cue and
   presses ✎ Update, the new text airs (`ProductionPage.tsx:3189`), which is the intended manual route.

Today: not possible without a published production and a phone; the inbox route exists only for
join or chat arrivals. Expectation to verify in the trial: the operator knows, before pressing
Take, that nothing from the phone will reach air by itself.

### 4.2 Select a message from a Sheet

1. The operator creates a Sheet tab from starter rows (Name, Message, Source, Reference), shares
   it "Anyone with the link can view", pastes the tab link into Messages › "Add Sheet messages".
2. Candidates appear with Name and Message only; Source and Reference are shown as small grey
   provenance, never filled into a graphic field.
3. They pick one, edit the broadcast text, "Prepare cue on…", pick the card (remembered), Take.
4. Source changes: a row edited in the Sheet becomes a new candidate on the next read (its hash
   changed); the old candidate disappears from the list, marked "changed in the Sheet" for one
   read; the prepared cue is untouched. A reordered sheet changes nothing: identity is the row's
   content hash, never its position. A deleted row removes the candidate, not the cue. Two rows
   with identical text from different names are two candidates (the hash includes Name and Source).
5. On air: identical to 4.1.

Contract: candidate identity by content hash (§3.2); cue values copied at prepare time. Today: a
Sheet cannot reach the inbox at all.

### 4.3 Choose YouTube input

1. Messages › "Add YouTube". Two choices, named plainly: "Live chat of a stream" and "Comments
   on a video". Both ask for the video link and the operator's own API key; the UI states the
   quota cost: live chat about 3,600 units an hour at the five-second floor against a 10,000 unit
   daily default, comments 1 unit per fetch of up to 100 (Appendix B).
2. Live chat: candidates arrive as the stream's chat moves, deduplicated by message id
   (`chatIntake.ts:204-219`). Decision to make deliberately (audience AC-9): the first page is
   recent history (Google: "some or all of the chat history"); today it is discarded
   (`youtubeChat.ts:105-108`). For a selection task, showing the last 20 marked "earlier" is more
   useful than dropping them; recommended.
3. Comments: a "Fetch newest comments" button, one call, newest 100 (`commentThreads.list`,
   `order=time`, `textFormat=plainText`), deduplicated by comment id. No polling. A refresh is a
   press. This is the cheapest useful YouTube feature in the whole plan and it needs no runner.
4. Reload: the live source is forgotten (`chatIntake.ts:169-180`) and must be re-added; the inbox
   keeps what arrived (durable provider, §3.2). Candidates that re-arrive are deduplicated by
   `externalId`.
5. Pick, edit, prepare, Take as in 4.1. A new chat message never touches the prepared cue.

Not in this run: server-side intake with a stored key (needs a credential store and a runner that
outlives a function), `streamList` (a held connection; fine in the browser later, 5 units per
call, resumes by `pageToken`).

### 4.4 Fill a ticker, a schedule, standings and credits

1. The operator selects the ticker's cue and presses "Follow… Google Sheet" on its items field.
   A dialog offers "Copy starter rows" (the field's current lines, one per row) and a link box.
2. They paste the tab link; a preview shows the parsed lines on the real graphic and says "Used
   by 1 cue" (connections are per graphic, all its cues follow). Save.
3. The ticker scrolls on. A cell edit is on air within ten seconds while the production page is
   open (browser reader, five seconds). A marquee continues, a flip finishes its item
   (`tickerMotion.ts`, as the research README records; not re-verified here).
4. Schedule: two columns, Time and Programme, joined with " | ". Standings: the header row's
   cells after Team fill "Column headers", body rows fill "Rows", both in one update row (§1).
   Credits: Role and Name columns, "# PRODUCTION" rows for headings, an empty row for a section
   break; a Role with an empty Name becomes "Role:" so the names beneath group under it.
5. Source changes while on air: a failed read keeps the last good list; a read that succeeds and
   finds no rows clears the field (DS18, new behaviour under the source contract only); a row
   edited replaces the whole list, so an operator's manual fix of one line is lost on the next
   change (DS19), which the editor says in one line. Pause holds the fix.

Today: only the frozen graphic-level block (`liveData.ts`) does any of this, by code pasted into
one graphic.

### 4.5 Connect pushed scores

1. Publish (sign-in). On the Data view, "Another system" shows the address, the key behind
   Reveal, and an example built from the production's own names:
   `PATCH /api/data/patch {"match":{"home":{"score":2}}}`.
2. The operator binds the scorebug's Score A to `match.home.score` from the cue field
   ("Follow… existing value"). Today this requires a republish to reach the server
   (`hostedControl.ts:552-558`); the plan's DS17 fix writes the binding to the row at once.
3. The sender pushes. "Received 2 s ago" appears. Take the scorebug. Later pushes follow on air.
4. Operator wins: a ± press moves the shared value through the operator's door
   (`ProductionPage.tsx:3212-3229`, `patchBoundValues`, migration 0060); the next push overwrites
   it. Pause (new) stops pushes from reaching air; Resume applies the difference (§6 R4).
5. Two scoreboards on one score: bind both to the same path. Two graphics with a Name field do not
   share a person unless both are bound to the same path on purpose.

### 4.6 Add an RSS feed

1. Ticker cue, "Follow… News feed", paste the feed address. NoaCG's server fetches it (browsers
   cannot read most feeds cross-origin), parses titles to plain text, shows the newest 20.
2. Save; Take. New headlines arrive within about five minutes; the feed's `ttl` or `Retry-After`
   slows it further.
3. A headline such as "Weather: storm warning" airs as kicker "Weather" and story "storm
   warning" (`tickers/shared.ts:118-121`); the preview shows it; the reader never alters text.
4. A failed fetch keeps the last list and the sources line says since when.
5. Local productions: works signed out through a public route (DS5) with SSRF guards (data AC-5).
   This is a new function or catch-all segment; `check:function-budget` is at 12 of 12 and must be
   raised on purpose (`api/AGENTS.md`).

### 4.7 No compatible graphic

A production with one scoreboard. The operator pastes a message (4.1) or presses "Prepare cue" in
the inbox. Expected: "No graphic here can show a message. Add a question card?" with the four
catalog cards; one press adds the card and a prepared cue on it; nothing airs. Today: a scoreboard
cue is created with the question as Team A (#1313, `ProductionAudienceWorkspace.tsx:598-609`).
Verification: the issue's own steps as an e2e journey; the mutation test is restoring the fallback.

### 4.8 Two prepared messages on one graphic

Cue A and cue B both on `House Q&A`. Take A. Prepare B from a new message. Take B: the card's one
renderer instance replaces A's text with B's, because a pool graphic airs on one layer
(`model/pool-graphic-airs-layer-number-carried`). A's cue still holds A's text; re-Take A brings
it back. Editing A's broadcast text in the inbox after staging changes nothing in cue A. If the
card's Question field were bound to a path, both Takes would air the tree's value instead, and
every tree change would move the on-air card (`ProductionPage.tsx:2320-2340`; `0048:163-203`).
That is why the picker refuses bound destinations and why the binding table should warn when the
operator binds a field that prepared cues use.

Operator expectation to state in the UI once: "Take replaces what this graphic shows."

## 6. Ranked risks and contradictions

Each with a failure example, evidence, the smallest fix or decision, and a verification case.

**R1. A live binding on a message graphic's field airs the wrong message.**
Failure: a student binds the Q&A card's Question field to `show.title` while learning bindings;
every prepared message cue then airs the title, and every title change moves the on-air card.
Evidence: `withBoundValues` at Take (`ProductionPage.tsx:3034`), dispatch (`:2320-2340`),
server (`0048:163-203`). The candidate's answer (refuse later bindings on fields used by
prepared/on-air messages; also protect against `/update`) needs the client to scan cues at bind
time and the server to know which cue is a snapshot, which the row does not record.
Smallest fix: the message picker and "Fill from Paste" refuse graphics whose body or name field is
bound and say "unbind first or add a card"; the Data view's binding row warns "N prepared cues use
this field". Keep "a bound field is not a cue value" as the one rule.
Verification: e2e: bind the card's Question, open the picker, assert the card is listed as
incompatible with the reason; unbind, prepare two cues, Take each, assert PROGRAM text; bind
again, assert the warning names two cues.

**R2. The unrelated-graphic fallback (#1313).**
Failure: as the issue. Evidence: `ProductionAudienceWorkspace.tsx:598-609`.
Fix: remove both fallbacks; the picker of §3.1; the catalog-card offer.
Verification: the issue's steps as a journey; the mutation is restoring `show.graphics[0]`.

**R3. D1 and D3 together demand infrastructure the deployment lacks.**
Failure: phase 18 promises a cell edit on air within ten seconds with every page closed; the
runner is a once-a-minute Vercel cron or a database scheduler; the promise fails or a new worker
tier is built mid-run. Evidence: `vercel.json:14`; `pg_cron` retention only; Vercel cron minimum
once per minute on Pro (Appendix B). Google export rate limits unmeasured.
Decision: the browser reads at five seconds while a page is open and holds a lease on the source
row; the server tick reads sources without a fresh lease at about a minute. Report closed-page
latency as measured. Ask the owner once whether a minute with pages closed is acceptable; this
review expects yes, because the teaching case has the page open.
Verification: configured test: lease held, server tick skips; lease expired, tick reads once; a
value changed once is written once (AC-5 kept).

**R4. Pause for pushed data with held partial patches and null deletions.**
Failure: a sender pushes `{"match":{"home":{"score":3}}}` then `{"match":{"away":null}}` while
paused; a naive "hold newest per name" drops one; Resume airs a stale away team. Evidence: DS20's
own correction; `/update` rows bypass the tree (`0047:66-96`), so two held streams exist.
Smallest design: while paused, `control_data_patch` still merges into `data` (the tree stays the
authority) and skips resolve-diff-append; the row stores `dispatched` (the resolved field strings
last appended). Resume diffs `resolve(data)` against `dispatched` and appends one row per graphic.
Held `/update` values are a per-graphic field map, last write wins, applied on Resume after the
tree diff. Alternatively defer Pause for pushed data to a later run and state today's doctrine on
the card ("to freeze, stop the sender").
Verification: DB conformance cases in `0048`'s self-check style: two patches with a null while
paused; interleaved `/update`; Resume emits exactly the final values once.

**R5. Candidate identity and persistence.**
Failure: Sheet rows keyed by position; the author inserts a row at the top; the operator approves
"row 3", which is now a different person's message. Or: pasted messages vanish on reload mid-show
(`localAudience.ts:65-73`, pinned by `production-audience.spec.ts:96-121`).
Fix: content-hash identity including Name, Message, Source and Reference; a changed row is a new
candidate, visibly; the durable local provider for authored and imported rows; simulated rows
stay in memory and the test's assertion is split in two with its reason.
Verification: journeys for insert-at-top, edit, delete, identical text from two names, reload with
an already on-air snapshot.

**R6. Bindings pinned at publish (DS17).**
Failure: a connection saved after publish moves nothing on air; the operator republishes mid-show
and the publish refuses because air is newer (`PublishBehind`, `hostedControl.ts:540`).
Fix: an owner-authenticated write of `control_shows.bindings` (RLS already grants the owner the
row), optionally emitting the diff rows for newly bound fields.
Verification: configured test: publish, bind, push, assert the row without republish.

**R7. Refactor-first delays the owner's main outcome and raises churn.**
Failure: fourteen sequential landings, each with configured dispatch and assessments, before any
student can paste a message; `ProductionPage.tsx` keeps receiving live-show fixes meanwhile
(the spec records 88 pull requests since 2026-08-12). Fix: §5.1. Verification: R0 landed and used.

**R8. The Sheet export address is not a documented API; edit latency and limits unmeasured.**
Failure: Google changes caching or throttles one reader at five seconds; every Sheet source stalls.
Evidence: sheet spec "Measured" (export CSV answered cross-origin with `no-store` on
2026-10-16); Google documents only "Publish to the web" with "the automatic update might take a
few minutes" (Appendix B). Fix: measure in R1; keep "Publish to the web" CSV as a documented
fallback the dialog can accept; status says since when a read fails. Verification: the 20-edit
and one-hour records in `evidence/`.

**R9. YouTube quota and credential handling.**
Failure: a two-hour stream exhausts the key by the second hour; or a stored key leaks on a shared
classroom machine. Evidence: 5 units per `liveChatMessages.list`, 10,000 units default (Appendix
B); key in memory today. Fix: keep in-memory by default with an explicit "remember on this
browser" opt-in; one-shot comments at 1 unit; show the spend. Verification: unit test of the spend
line; a receipt from a real stream in R1.

**R10. Credits and standings adapter details.**
Failure: "# PRODUCTION" with an empty Name cell joins to "# PRODUCTION | " and the heading text
becomes "PRODUCTION |"; "Camera" with an empty Name becomes a name, not a role.
Evidence: `endCredits/shared.ts:210-233`. Fix: trim trailing empty cells before the join; a
role-only row emits "Role:". Verification: the Node fixtures listed in §3.3.

**R11. Private metadata on air.**
Failure: " · YouTube" rides the author line to air (`chatIntake.ts:135-140`); a Source cell
"WhatsApp +358…" lands in the Name field. Fix: Source and Reference never map to fields; the
platform word becomes a provenance label, not part of `broadcastAuthor`, unless the owner wants
it kept. Verification: a journey asserting the Name field after prepare.

**R12. Entry instability.** Setup items appear and vanish (`ProductionSetupMenu.tsx:129-132`);
the Audience tab shows only when a message graphic exists or something arrived
(`ProductionPage.tsx:4591-4608`). Fix: a stable Messages entry and a stable Data entry (A1's
intent, now the shared-workflow wording). Verification: journey on a fresh production.

**R13. Double press creates two cues.** `sendToRundown` has no pending guard (§1). Fix: disable
while pending; dedupe prepare by (submission id, graphic) within a few seconds; deliberate reuse
through a separate "Prepare again". Verification: the AC-2 held-persistence journey.

Contradictions to resolve in the reconciliation:

- Audience AC-6's `/update` protection versus "preserve existing integration compatibility" and
  the documented "later rows win" doctrine. Recommendation: drop the protection (R1).
- D1 server reader plus D3 ten seconds versus AC-5 one reader and the absent scheduler (R3).
- DS19 "a list is one value" versus D4 operator override as students will understand it: say it
  in the editor, and make Pause the tool.
- "No new general store" versus audience AC-8 persistence and "one logical candidate record":
  a store decision is unavoidable; §3.2 makes the smallest one.
- Refactor behaviour preservation versus the owner's wish to use paste soon: resolved by R0 as a
  declared feature change before phase 1.

## 7. Prototype and user-trial plan

Purpose: settle the entry point, the destination gesture and the starter-sheet format before the
expensive phases. Disposable prototypes on the dev build behind a flag, or R0's build for the
message tasks.

Participants: three to five students who have used NoaCG's Playout tab but not the Data tab; one
operator who has. Fresh unpublished production per task. No instruction beyond the task sentence.

Tasks:

1. "Put this text message on air as a viewer question" (production with one scoreboard, text in
   a chat window on the same screen). Measures the no-compatible-graphic path.
2. "Air the second message from this Sheet, without the sender's surname" (link-shared Sheet
   with five rows).
3. "Make this ticker show the lines in this Sheet, then change one line and watch it update."
4. "Fill this standings board from a Sheet you make yourself from the starter rows." Measures
   whether the starter sheet is understood.
5. Optional: "Connect this scoreboard to a test sender" with a prepared curl window.

Two variants for tasks 1 to 3, counterbalanced: B (field-led) and A (shared workspace), as
click-through prototypes if the real screens are not ready.

Measures, in priority order:

- Unaided completion (a hint fails the trial for that task).
- Comprehension, asked before Take: "What will happen when you press Take?" and after: "If the
  sender edits their message now, what changes on air?" and "If someone adds a row to the Sheet,
  what happens to the cue you prepared?" A wrong answer is a design finding even when the task
  completed.
- Errors: wrong destination, airing before intending to, editing the original instead of the
  broadcast text.
- Time, recorded but secondary. The proposed two-minute and five-minute targets measure speed,
  and speed without comprehension is the failure mode this product must avoid. Suggested pass:
  four of five complete unaided and answer the three comprehension questions correctly; medians
  reported, no target.

Decisions the trial settles: where the task starts (field versus workspace); whether a remembered
destination is understood; whether "one row is one line" is enough for the four list shapes;
whether the Data view is needed at all for these tasks; the wording of the Pause and "list is one
value" lines.

Measurements alongside, not with students: 20 real Sheet edits timed to the export reflecting
them, from one browser at five seconds for an hour (does Google refuse?); five public feeds for
conditional request support and markup; one YouTube stream and one video with the operator's key.

## 8. The eight questions, answered

**Q1. Simplest coherent operator model.** Content lives at the cue, in the editor the operator
already uses; a Messages inbox for candidates; one Sources line on Playout; the existing Data view
trimmed to an overview plus Advanced. Compared in §2.2 with the shared workspace and the
Sheet-as-editor alternatives.

**Q2. Manual messages and Sheets first-class; can paste land before 23?** The candidate makes
paste first-class in words but schedules it after feeds and API (21, 23). Yes, it can land first:
R0 depends on nothing in the refactor or the data work. The reason the spec gives for waiting
(the cue editor moves in 13) argues for a props-only extraction, not for waiting.

**Q3. Which refactor phases are essential?** Essential for reliability now: 1 (S1, S3). Essential
for the new workflows: 7 (with 2), and a props-only cue editor extraction. Optional maintenance:
3, 4, 6, 8, 9 (the spec agrees). Reliability but unrelated to content: 5, 10, 11, 12, the draft
half of 13, 14. Ordered poorly: the whole refactor before any product change. Avoidable risk: 11
and 13 are safety-sensitive moves scheduled inside a run that also changes the cue editor's
behaviour; keep them in a window of their own.

**Q4. Can updates, collisions, precedence, reordering, reconnect or retry air the wrong message?**
Yes, through three paths, traced in §6: a live binding on the destination's field (R1), the
unrelated-graphic fallback (R2), and position-keyed Sheet identity (R5). Reconnect and retry do
not: chat dedupes by platform id (`chatIntake.ts:204-219`), and a prepared cue is a copy. The
smallest protective contract is three sentences: a message destination must have no live binding
on its body or name field; a destination is chosen explicitly or offered as a new card, never
guessed; a candidate's identity is its content, never its position.

**Q5. Are starters and six formats practical?** Four shapes are (§3.3), because they are the
graphics' own text formats and the starter rows are the graphic's current content. Migration: no
persisted format changes; `sources` and `externalId` are additive optional; name-keyed bindings
stay the resolution contract and gain a `graphicId` beside them for later rename handling.
Existing `liveData.ts` blocks keep running; new graphics stop being offered the panel.

**Q6. YouTube: needed and feasible.** Needed now: pick a chat message or a video comment and air
it. Feasible in the browser with the operator's own key: live chat as today (5 units a poll),
comments one-shot (1 unit). Decide the history page deliberately. Authorization for public content
is an API key; the reference pages do not state it and R1 confirms it with a receipt. Runtime: a
browser tab; nothing server-side in this run. Twitch: keep the anonymous IRC reader as is, note
that Twitch documents only an authenticated flow and recommends EventSub (Appendix B), and build
nothing new.

**Q7. Pause, failure, empty content, override, ownership.** Failure and empty content are precise
(last good holds; valid empty clears under the new contract only). Override is precise for values
and honest for lists (DS19). Pause is precise for the browser Sheet reader and underspecified for
pushed data; §6 R4 gives the smallest design. Ownership: D1's server-only published reader is the
imprecise part; the lease model of R3 replaces it. Both `/patch` and `/update` must honour Pause
if Pause exists at all; `/update` cannot be made to respect message snapshots without a contract
change and should not be.

**Q8. Do the checks prove the outcome?** Partly. Strong on contracts and races; thin on: a
ticker, schedule, standings and credits updating live on a real player (OBS browser source at
least, CasparCG if the owner can); comprehension in the trials; a bindings-plus-sources migration
test on a record saved by today's build; a check that no Source or Reference reaches a field; a
check that a message destination with a bound field is refused on both local and published
productions. Phase 26 should list each route with its evidence or its "not run".

## Appendix A. Independent proposal, as written before reading the proposed specs

Written to a scratch file after the code read and before `docs/work-specs/*` were opened.

> **Operator model.** Two concepts only, named in the UI as "Fill" and "Follow": FILL = copy content
> into a cue once (paste, pick a Sheet row, pick a message, load a table row). The cue owns the
> values afterwards. This is what the cue editor already does for `ShowDataset` rows
> (cueDataRows/loadRow) and what the Audience "Send to rundown" does for a message. FOLLOW = a
> graphic field follows a live value (the existing binding to a production-data path), and a source
> keeps that value current (push API, Sheet poll, RSS poll, operator press). Where it lives: AT THE
> CUE/GRAPHIC. The cue editor is the one place a non-technical operator already fills fields. Each
> field (or field group) gets a small "Fill from… / Follow…" menu. A production-level "Sources" list
> (Setup › Sources, or the existing Data view trimmed) shows status/Pause for live sources and the
> Google links. No separate Audience setup system: the inbox is one source kind ("Messages") whose
> only exit is FILL into a chosen compatible graphic.
>
> **Messages.** Inbox = existing AudienceSubmission model (original vs broadcast, anonymize). Keep
> it. Add a "Paste" intake: a textarea → one submission (name optional). That alone covers WhatsApp,
> SMS, X, email. Sheet-as-inbox: a tab with Name/Message columns → submissions keyed by a stable id
> (hash of row contents or an explicit Ref column), not by row position. Exit: "Prepare cue" with an
> explicit graphic picker limited to compatible graphics (has a text field titled
> Message/Question/Comment/Body/Text, and is not a vote board). No fallback to graphics[0] (fixes
> #1313). Snapshot = plain `ShowCue.values`; nothing links back. Protection: because a prepared cue
> is plain values, later arrivals cannot touch it. The only live routes into a graphic's on-air
> fields are (a) bindings and (b) /update by graphic name. Make (a) safe by never auto-binding
> message fields and by showing "this graphic has live fields" in the picker; leave (b) alone (an
> integrator addressing a graphic by name is deliberate).
>
> **Sheets.** One link per content set (a tab). Read via the gviz CSV URL on a link-shared sheet (no
> OAuth) or Publish-to-web CSV; starter CSV generated from the graphic's own sample text so the sheet
> mirrors the text format the graphic already parses (one row = one line; cells joined " | ").
> Formats: ticker one column; schedule Time | Programme; standings header row → "Column headers",
> rows → "Rows"; credits Role/Name with "Role:" and "#" rules the parser already reads. Small
> per-type formatter, no generic adapter framework. Runner: browser-owned poll while the production
> page is open (the liveData.ts precedent, but owned by the production, written through
> setLiveData/patch); server-side poll only as a later phase, at 1/min on Vercel cron or a Supabase
> scheduler. Do not promise 5 s with the page closed.
>
> **Pushed scores and API.** Keep /patch + bindings as is. Make the Data key and a worked curl visible
> from the Sources list. **RSS.** Needs a server fetch (CORS). One guarded function, cached 5 min,
> writes a path in the tree; the ticker field follows that path. Later phase. **YouTube.** Keep
> live-chat polling as is (browser, key in memory). Add "Paste" for comments now. Qualify
> `commentThreads.list` (1 unit, API key) as a separate "video comments" source later.
>
> **Refactor.** Only what the new flows touch: cue editor extraction (fill menu), the data session

## Appendix B. Provider facts fetched today

- YouTube Data API quota: `liveChatMessages.list` 5 units; `liveChatMessages.streamList` 5
  units; `commentThreads.list` 1 unit; `videos.list` 1 unit; default 10,000 units per day for
  these endpoints. Source: developers.google.com/youtube/v3/determine_quota_cost and the method
  pages. The `list` page: the first request returns "some or all of the chat history" and later
  pages only new messages; `pollingIntervalMillis` is the wait the client should honour;
  `maxResults` 200 to 2000, default 500. The `streamList` page: a server-streaming connection
  that "will only contain the most recent events" on first connect and resumes from
  `nextPageToken`. Neither page states whether an API key or OAuth is required.
- Google Sheets "Publish to the web": changes republish automatically by default and "the
  automatic update might take a few minutes". Source: support.google.com/docs/answer/183965. The
  Visualization `gviz/tq` guide: sheets shared "anyone who has the link can view" need no
  credentials; private sheets need an OAuth token; the guide does not label the endpoint a stable
  public API. Source: developers.google.com/chart/interactive/docs/spreadsheets.
- Twitch IRC: the current page describes only an authenticated flow ("you must authenticate with
  Twitch and get a User Access Token with chat:read") and recommends EventSub; it does not mention
  anonymous nicknames. Source: dev.twitch.tv/docs/chat/irc.
- Vercel: cron jobs at most once per minute on Pro and Enterprise, once per day on Hobby;
  functions 300 s default, 800 s maximum on Pro (1800 s in beta). Sources:
  vercel.com/docs/cron-jobs/usage-and-pricing and vercel.com/docs/functions/limitations.
