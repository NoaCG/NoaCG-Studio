4.2 Resolving the Graphic-Shared vs. Cue-Owned Binding Conflict (Code flaw → Recommendation)

This is the single most important architectural gap in the current codebase and spec set:

What Code does today:
Show.bindings (Record<string, Record<string, string>>) is indexed by graphicName, not cue.id. Every cue that uses "Candidate Card" shares the exact same Show.bindings["Candidate Card"] map.
cueDataRows (Fill from sheet) creates one ShowCue per row by copying a static snapshot of strings into cue.values, with no live binding.
In ProductionPage.tsx, resolveBindings(showData, bindings[graphicName]) overwrites fieldValues globally for that graphic name.
Why this fails YLE Election (E7) and Sports Player Cards:
Suppose the operator prepares Cue 1: Candidate #42 (Sanna) and Cue 2: Candidate #88 (Pekka), both using the "Candidate Card" graphic.
If they use Fill (cueDataRows), Cue 1 and Cue 2 have different candidates, but their vote counts and percentages are frozen at cue-creation time and will never update when the 21:00 result snapshot arrives!
If they use Connect (Show.bindings["Candidate Card"]), both Cue 1 and Cue 2 resolve to the exact same JSON path (candidates.0.*), so Cue 1 and Cue 2 show the same person!
The exact contract fix (KeyedCollectionBinding): Extend Show with a graphic-scoped collection binding template that is parameterized by a cue-owned key value:
ts
export interface KeyedCollectionBinding {
  sourceId: string
  collectionPath: string          // e.g. "candidates"
  keyProperty: string             // e.g. "candidateId" (stable ID in source row/object)
  selectorFieldKey: string        // e.g. "f_candidate_id" (stored per-cue in ShowCue.values)
  fieldMap: Record<string, string> // graphicFieldKey -> item property path, e.g. { f_name: "name", f_votes: "votes", f_pct: "sharePct" }
}
How resolution works:
Graphic-shared (Show.keyedBindings[graphicName]): Declares which collection and which item properties map to the graphic's fields.
Cue-owned (cue.values[selectorFieldKey]): Stores only the selected stable entity key (e.g., "HEL-042" for Cue 1, "HEL-088" for Cue 2), plus any explicit manual per-cue overrides (cue.manualOverrides).
Coherent per-entity resolution: When Cue 1 is in Preview or Program, the resolver looks up the single item in resolvePath(showData, collectionPath) whose item[keyProperty] === cue.values[selectorFieldKey]. All bound fields (f_name, f_party, f_votes, f_pct, f_photo) are read atomically from that single item object in the current snapshot revision.
Missing-key / partial-update safety: If a new feed snapshot arrives and "HEL-042" is missing or the snapshot fails validation, the resolver retains the last-known-good resolved record for "HEL-042" and marks the source badge Stale — never falling back to row index 0 or mixing fields across two candidates.
4.3 Live-operation invariant preservation
No auto-Take / auto-advance / auto-stop on data arrival: Already enforced in ProductionPage.tsx for Show.data updates (which only emit {t:'update', data} when a layer is on-air and liveUpdate is on). E4, E5, and E7 must preserve this invariant: incoming snapshots update Show.data (and push {t:'update'} if live-update is unpaused), never triggering take, next, clear, or cue selection changes.
Explicit manual override precedence: When an operator edits a live-bound field in a cue (C3), that override must be recorded per-cue (or in pausedFields) so the next poll tick does not silently clobber the operator's manual correction on air, with a one-click "Resume live" restore.

5.2 Trusted external connector (E4) and bounded API mapper (E5)
Why browser-only fetch is not enough (Code): src/control/dataSources.ts fetches URLs directly from the operator's browser tab. That fails when:
The upstream API blocks browser CORS headers.
The upstream API requires a secret bearer token / API key or mTLS/IP allowlisting that must not be exposed in client-side Show.dataSources.
Multiple operator tabs are open (causing duplicate polling or inconsistent snapshots if not coordinated).
Required E4 architecture (Recommendation): Build a small, stateless Snapshot Relay / Connector contract (usable both from a local CLI/service sidecar on the broadcast LAN and from a Supabase Edge Function):
Accepts normalized snapshots pushed to show.data[namespace] or a dedicated production_data_snapshots table/channel with metadata { rev: number, sourceTimestamp: string, ingestedAt: string, sha256: string, recordCount: number, data: JsonObject }.
Validates schema & non-empty record counts before replacing the active revision; if an upstream response is truncated HTML/502 or drops required keys, the connector logs a warning, increments consecutiveErrors, and leaves the last valid rev intact (last-good snapshot retention).
