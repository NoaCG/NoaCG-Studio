# @noacg/cli 0.3.1 was NOT published, and the reason is not in this repository

Branch `claude/ah-publish-0-3-1`, from `main` at `ed87060e`. Two files: an owner item and a backlog
item. No product code, no build.

**The one line that matters: npm's trusted publisher for `@noacg/cli` still names the OLD
repository owner, `miwco`, and the repository moved to `NoaCG` on 2026-09-06.** Every publish now
fails. Fixing it takes the owner about two minutes on npmjs.com and cannot be automated, because
npm demands an interactive 2FA challenge to change that configuration.

## What was verified before anything was attempted

AE's handoff on `main` says 0.3.1 is ready, in those words, so the gate opened. Then, independently:
PR 203 is merged at `ed87060e` (2026-09-09T21:33Z); `cli/package.json` on `main` says `0.3.1`;
`npm view @noacg/cli version` said `0.3.0`. The documented route and the workflow agree with each
other - `npm run release:cli` automates exactly the tag-and-push the workflow header prescribes -
so there was nothing to choose between.

## The rehearsal, which passed, and could not have caught this

`npm run release:cli -- --check`: all six version stamps agree, `0.3.1` free. Then the workflow's
own dry run, dispatch `34407862741` on `main`, green in 42s with every step read individually:
guards passed, `check:skill` clean, typecheck, build, `git diff --exit-code` clean, tests 70 / 65
pass / 0 fail / 5 skipped, `npm pack --dry-run` at 63.9 kB across 32 files, `npm publish --dry-run`
reaching the registry, and the release-notes rehearsal printing real notes.

**A dry run cannot authenticate.** `npm publish --dry-run` never sends a credential, so the
rehearsal the workflow offers - and which `docs/AGENT_CLI.md` presents as proving the path - is
blind to the entire class of failure that then happened three minutes later. That is in the backlog
item, because the docs currently oversell it.

## What happened, in order

1. `npm run release:cli` tagged `cli-v0.3.1` at `ed87060e`, pushed it, and watched run
   `34408194386`. It failed at `Publish`: `npm error code E404`, `404 Not Found - PUT
   https://registry.npmjs.org/@noacg%2fcli`. The script refused and said the version was not
   published.
2. **First check was the registry, not the log.** `npm view @noacg/cli versions` -> `0.2.0, 0.3.0`.
   Nothing was published, so nothing was unrecoverable, and there was time to think.
3. Re-drove it the way `docs/AGENT_CLI.md` says to re-drive a tagged run: `gh workflow run
   release-cli.yml --ref main -f dry_run=false`, run `34408479669`. **Identical failure**, which
   ruled out the trigger. My first hypothesis - that the tag-push path had never actually
   authenticated - was wrong, and it took one 55-second run to prove it wrong.
4. Ruled out the toolchain by diffing the failing runs against the run that published 0.3.0 on
   2026-09-05: same npm 12.0.2, same node v24.20.0, `actions/setup-node@v5` and `actions/checkout@v5`
   resolving to the same SHAs, the same `.npmrc` warning, the same placeholder `NODE_AUTH_TOKEN`.
   npm's status page: operational, no incidents.
5. So the change was in the repository's IDENTITY, not its content. `git log` on the workflow file
   found `ea7f569c`, 2026-09-06: "The repository moved from miwco/NoaCG-Studio to
   NoaCG/NoaCG-Studio."

## The evidence is two-sided, which is why this is a diagnosis and not a guess

The job carries its own fork guard, and that guard is a literal string:

- 2026-09-05, 0.3.0 publishes. The guard then read `github.repository == 'miwco/NoaCG-Studio'`, and
  the job RAN. So GitHub's token said `miwco` that day.
- 2026-09-09, both failures. The guard reads `'NoaCG/NoaCG-Studio'`, and the job RAN. So the token
  says `NoaCG` now.

The registry says the same thing from its own side: `npm view @noacg/cli@0.3.0 repository.url`
answers `git+https://github.com/miwco/NoaCG-Studio.git`, and that version carries a SLSA provenance
attestation - so the last successful publish was demonstrably a trusted publish from the OLD owner.

npm matches a trusted publish on organisation-or-user + repository + workflow filename, exact and
case-sensitive. One of the three changed under it. npm's stored copy did not follow, the token
exchange returned nothing, and - this is the part that made it expensive - **npm swallows a failed
exchange at the default log level**, keeps the placeholder token `actions/setup-node` wrote into the
`.npmrc`, sends that, and lets the registry mask the 403 as a 404 that reads like the package does
not exist (`npm/cli#9923` and `#9088`, both open, both verified by hand tonight).

## What needs the owner

`docs/acceptance/owner-queue/2026-09-09-ah-npm-still-thinks-the-repository-is-yours.md`,
`kind: owner-action`, `needs: account`. It carries the exact npmjs.com path, the five field labels
and the values, checked against npm's current documentation rather than remembered: **Packages ->
@noacg/cli -> Settings -> Trusted publishing**, delete the `miwco` entry, add one for `NoaCG` /
`NoaCG-Studio` / `release-cli.yml`, and tick **direct `npm publish`** under Allowed actions - since
2026-09-03 a new configuration allows staging only by default, and a staging-only configuration
refuses in exactly the same way, so missing that box looks like the fix not working.

This is a real `needs: account`, not a permission question. The owner's instruction tonight was to
publish without him and he was right to want that; the mechanism is simply not reachable from here.
Once he has done it, the CLI publishes without him again, permanently.

## The state this leaves behind

- **Nothing is on npm.** `0.3.1` is still free. No version was burned and nothing can need taking
  back.
- **The tag `cli-v0.3.1` IS on origin**, at `ed87060e`, with two failed runs behind it. **Leave
  it.** It points at the right commit, the re-run uses it, and the release step will attach the
  GitHub Release to it. I did try to delete it before the relay reached me, on the reasoning that it
  frees the one-command route; the harness classifier refused the deletion, which turned out to be
  the right answer, and I did not work around it.
- Because that tag exists, `npm run release:cli` will now REFUSE with "the tag cli-v0.3.1 already
  exists on origin". That refusal is correct and its advice is the route below.

**To publish once the owner has fixed npm** (one command, from any checkout):

```
gh workflow run release-cli.yml --ref main -f dry_run=false
```

Then re-derive the result rather than trusting the run, which is the whole point of the script's
second half: `npm view @noacg/cli version` must say `0.3.1`, `npm view @noacg/cli dist-tags` must
put `latest` on it, `gh release list` must show `cli-v0.3.1`, and `npx -y @noacg/cli@0.3.1
--version` must answer `0.3.1`. Do those four by hand, because with the tag already on origin
`npm run release:cli` refuses before it reaches them.

## The owner asked why he has to do this manually, and the answer has two halves

He does not, and he has not since 0.2.0. That was the last version published by hand, from a laptop
holding a token that bypassed 2FA; 0.3.0 went out on 2026-09-05 from a workflow with no secret
anywhere, and the only human act in it was a click that verified nothing, which is exactly what he
said when he asked the question. That click is already gone: `scripts/release-cli.mjs` replaced it
with checks on both sides of the publish.

The second half is tonight's. Moving the repository to the organisation on 2026-09-06 quietly cut
the road, and the next person down it would have hit this wall whoever they were - him on his phone
included. So the answer is not "you still have to publish manually". It is "you have to reconnect
npm to the new address once, and then nobody publishes manually again".

## The finding that outlives tonight

`docs/backlog/the-release-path-cannot-say-why-a-publish-was-refused.md`. Three fixes, smallest
first: `NPM_CONFIG_LOGLEVEL: verbose` on the publish step, which converts this entire session into
one line of log and should land WITH a real publish so it is exercised; a preflight in
`scripts/release-cli.mjs` that states the owner and workflow filename npm must be holding; and the
trap written down where it belongs. The file ends with a paragraph drafted for `npm run learn`,
because "moving a repository silently breaks publishing, and the error names the wrong thing" is
exactly the shape of thing that will cost somebody another hour in a year.

I did not run `npm run learn` myself. This row's TOUCHES was its own handoff, the two documentation
files are already a stretch of it that I think is justified, and the learn mechanism rewrites
compiled contract files that a release-blocked branch has no business carrying.
